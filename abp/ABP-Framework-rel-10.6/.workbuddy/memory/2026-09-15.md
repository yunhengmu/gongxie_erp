## PagedResultDto 的字段在 TS 里是可选的

`node_modules/@abp/ng.core/types/abp-ng.core.d.ts:297-300`：

```ts
declare class ListResultDto<T> { items?: T[]; }
declare class PagedResultDto<T> extends ListResultDto<T> { totalCount?: number; }
```

`items` 和 `totalCount` 都带 `?`，所以严格模式下直接赋值报

```ts
this.warehouses = res.items ?? [];
this.totalCount = res.totalCount ?? 0;
```

## ⚠️ 踩坑：浏览器 XHR 报 status 0 = HTTPS 开发证书未信任

**症状**：Angular 页面弹出 ABP 错误页

```
Http failure response for https://localhost:44362/api/abp/application-configuration?includeLocalizationResources=false: 0 undefined
```

`status: 0` 表示浏览器层面就没拿到响应（不是 4xx/5xx）。

**排查顺序**（别一上来就怀疑 CORS）：

1. `curl -sk` 两个接口 → 都是 200 ⇒ 服务没挂
2. 模拟 CORS 预检：
   ```bash
   curl -sk -i -X OPTIONS "<接口URL>" -H "Origin: http://localhost:4200" \
     -H "Access-Control-Request-Method: GET" -H "Access-Control-Request-Headers: authorization,content-type"
   ```
   返回 `204` + `Access-Control-Allow-Origin: http://localhost:4200` ⇒ **CORS 是好的**
3. `dotnet dev-certs https --check --trust`
   → `The following certificates were found, but none of them is trusted` ⇒ **根因找到**

**根因**：浏览器对「页面导航」遇到不受信任证书会给「继续前往」按钮，**对 XHR/fetch 不给**，直接判失败 → status 0。
而 `curl -k` 跳过了校验，所以命令行一直是通的，极具迷惑性。

**修复**（会弹一次 Windows 确认框，需点「是」）：
```bash
dotnet dev-certs https --trust
```
验证：
```powershell
$ProgressPreference='SilentlyContinue'
Invoke-WebRequest 'https://localhost:44362/api/abp/application-configuration?includeLocalizationResources=false' -UseBasicParsing
# 不加 -SkipCertificateCheck 也能 200 ⇒ 已信任
```
（本题用 `Invoke-WebRequest` 比 curl 准确：curl 用自带 CA 包，读不到 Windows 证书存储。）

证书落在 `Cert:\CurrentUser\Root`（`LocalMachine\Root` 为 0，够用）。

**修完必须完全重启浏览器**——Chrome/Edge 会缓存证书错误，只刷新页面不一定生效。

> 注意：本机 `dotnet dev-certs https --check` 与 PowerShell 工具的输出经常被吞（exit 0 但无 stdout），
> 用 `Set-Content $env:TEMP\xxx.txt` + Read 工具读回来更可靠。

## 用户对「新建仓库」方案的 4 点质疑（2026-09-15，全部成立）

### ① DTO 默认 `= true` 是 fail-open，我给的方案有错

我写 `public bool IsActive { get; set; } = true;`，用户指出不安全。
**成立**：`bool` 是非空值类型，无法区分「客户端传了 false」和「客户端没传」——
漏传/字段名拼错会静默创建出**已启用**的仓库。且与实体构造函数里的 `IsActive = false` 自相矛盾，
同一概念在两层有两个相反的默认值。

- `[Required]` 对 `bool` **无效**（值类型永远算「有值」），只有 `bool?` 才拦得住。
- 正确做法（二选一）：
  - 删掉 `= true` → 默认 false，fail-closed，与实体构造函数一致；
  - 或 `public bool? IsActive { get; set; }` + `[Required]`，客户端必须显式表态，漏传 400。
    代价：代理生成出来是 `isActive?: boolean`，映射处要写 `input.IsActive == true`。

### ② `input.IsActive` 和 `warehouse.IsActive` 是两个毫不相干的东西

我上一版注释把「IsActive 的 setter 是 private」这句话贴在了读 `input.IsActive` 的旁边，
造成用户误以为在说同一个字段。**是我的注释歧义。**

| | `input.IsActive` | `warehouse.IsActive` |
|---|---|---|
| 所属类 | `CreateUpdateWarehouseDto` | `Warehouse`（聚合根） |
| 层 | Application.Contracts | Domain |
| setter | `public set` 谁都能改 | `private set` 只有类内能改 |
| 本质 | 数据搬运的口袋 | 受业务规则保护的状态 |

C# 靠**变量名**解析，不靠属性名；两者只是名字撞了。
**用户 Java/MyBatis-Plus 背景里没有这个心结**——那边通常是 Entity 一个类兼表映射 + 接口入参（贫血模型），
「DTO 与实体分离」在那边不常见。ABP/DDD 拆开的唯一目的就是**让领域状态从外部改不动**（`private set`）。

### ③ 构造函数写 false 又调 `Activate()` —— 不是编译错，但确实是坏味道

用户直觉正确。执行顺序 `new`(false) → `Activate()`(true)，能跑；
但构造函数那句 `IsActive = false` 立刻被覆盖，等于废话。
更深的问题：**「新建时能否指定启用状态」是领域规则，不该由 AppService 的 `if` 决定**（应用层替领域层做决策）。

两个干净方向：
- **A（推荐）**：领域规则定为「新建一律停用」。DTO 里删掉 `IsActive` 字段，AppService 不调 `Activate()`；
  启用/停用做成独立接口（`POST /api/app/warehouse/{id}/activate`）。构造函数的 `false` 才有意义。
  代价：前端新建表单没有状态勾选框。
- **B**：允许新建即指定状态 → 应由构造函数一次性确定，而不是「先 false 再翻 true」。

### ④ `MapToEntityAsync` 不是自由命名，是框架钩子

源码实测 `framework/src/Volo.Abp.Ddd.Application/Volo/Abp/Application/Services/AbstractKeyCrudAppService.cs`：

- `:139` `protected virtual Task<TEntity> MapToEntityAsync(TCreateInput createInput)`
- `:178` `protected virtual Task MapToEntityAsync(TUpdateInput updateInput, TEntity entity)`
- `:88` `CreateAsync()` 里 `var entity = await MapToEntityAsync(input);`
- `:103` `UpdateAsync()` 里 `await MapToEntityAsync(input, entity);`
- 注释原文：`It can be overriden for custom mapping.`

子类写 `override`，签名必须逐字一致。名字与业务无关，因为它是**通用 CRUD 机器的通用零件**。
想要业务方法名（如 `RegisterWarehouseAsync`），**就不能继承 `CrudAppService`**，得手写 AppService，
代价是 5 个免费 CRUD 方法（含分页/排序/权限校验）全部自己实现。
这是 ABP 的取舍：通用 CRUD ↔ 业务语义，二选一。
折中：在子类加薄壳 `public Task<WarehouseDto> RegisterAsync(input) => CreateAsync(input);`

## 官方 Identity 模块的 IsActive 全链路（2026-09-15 实测，重要参照）

用户追问「DTO 该不该默认 true / 该不该叫 IsChange / if 只写一半是不是废函数」，
把 ABP 官方 Identity 模块的同一件事扒了一遍，结论如下：

| 位置 | 文件:行 | 写法 |
|---|---|---|
| **API 契约 DTO** | `modules/identity/.../IdentityUserCreateOrUpdateDtoBase.cs:29` | `public bool IsActive { get; set; }` ← **无默认值** |
| **UI 层 PageModel** | `modules/identity/.../Web/Pages/Identity/Users/CreateModal.cshtml.cs:82` | `public bool IsActive { get; set; } = true;` ← **有默认值** |
| 实体属性 | `modules/identity/.../IdentityUser.cs:88` | `public virtual bool IsActive { get; protected internal set; }` |
| **实体构造函数** | `IdentityUser.cs:198` | `IsActive = true;` ← 领域默认就是「启用」 |
| 实体方法 | `IdentityUser.cs:407` | `public virtual void SetIsActive(bool isActive)` ← **带参数** |
| **应用层映射** | `modules/identity/.../IdentityUserAppService.cs:207` | `user.SetIsActive(input.IsActive);` ← **一行，无 if/else** |

三条可以直接引用的结论：

1. **`IsActive` 同名是对的**，官方 DTO 和实体完全同名。字段语义是「**目标状态**」不是「是否变更」，
   所以叫 `IsChange` 是错的（改成什么状态？信息不全）。`isActive` 就是「这个实体应不应该处于 active 状态」。
2. **默认值 `= true` 属于 UI 层，不属于 API 契约层**。官方 API DTO 无默认值，`= true` 只出现在 PageModel。
   → 彻底印证用户第一轮的批评：我原来把 `= true` 放进 `CreateUpdateWarehouseDto` 是**放错层**。
3. **官方应用层之所以能一行搞定，是因为实体给的是带参方法 `SetIsActive(bool)`**；
   我们的 `Warehouse` 是无参的 `Activate()` / `Deactivate()`，才被逼出 `if/else`，且只写 `if` 显得半截。
   这是**实体 API 形状**决定的，不是应用层写错。

### 顺带纠正我之前的一句话

我之前说「实体构造函数应该默认 false（fail-closed）」。官方 `IdentityUser` 构造函数明确写 `IsActive = true`。
所以要把两层分开：

- **API 契约层**：不该有隐形默认（客户端不传就别乱猜）→ 官方 DTO 无默认值，这条成立
- **领域层**：默认值就是业务规则本身，选 true（官方：新用户默认启用）或 false（我们：新仓库默认停用）**都可以**，
  但必须是有意识的选择，且与上层解释保持一致。不是「false 才安全」的硬规矩。

## 定论：`IsActive` 之争的根因与最终决定（2026-09-15）

用户连着 4 轮在同一个点上打转（「构造函数是 false 还调 Activate 是不是写反了」→「input.IsActive 是用户期望还是仓库状态」）。
**根因不是用户没听懂，是一个名字承担了两种语义：**

| 位置 | 名字 | 语义性质 | 读法 |
|---|---|---|---|
| `Warehouse.IsActive` | IsActive | **事实**（陈述） | 这个仓库现在是不是启用的 |
| `CreateUpdateWarehouseDto.IsActive` | IsActive | **指令**（祈使） | 这个仓库应该被置成什么状态 |

同概念、不同副本、同名。这是 CRUD DTO 的通行惯例（官方 Identity 也这样），但**惯例 ≠ 好设计**，
它天然让人串——用户 4 轮的困惑就是这条设计缺陷的实证。

### 提炼出的判定原则（以后讲状态字段直接用）

> **布尔字段描述「事实」，动词方法表达「指令」。别让一个布尔同时承担两件事。**

官方 `IdentityUser.SetIsActive(bool)` 违反这条（本质是改名的 setter），ABP 是为了省事付了语义代价。

### 决定：走方向 A（用户让我拍板）

- `CreateUpdateWarehouseDto` **删掉 `IsActive`**，只留 `Code` / `Name`
- `MapToEntityAsync` 简化到两行（new + return），`input.IsActive` 与 `warehouse.IsActive` 不再照面
- 启用/停用做成独立接口，**用动词表达指令**：`POST /api/app/warehouse/{id}/activate` / `/deactivate`
- `Warehouse` 构造函数里的 `IsActive = false` 从此含义明确（领域规则：新建一律停用），不再被上层覆盖
- 顺带：`Learn.Warehouses.Activate` 可以成为独立权限（新建和启用是两种能力）
- 删掉实体里多余的 `Doactivate()`

代价：前端新建表单没有状态勾选框（只剩 Code + Name，反而更简单）；列表页后续要加「启用/停用」按钮才能让 `IsActive` 变成 true。

**待办更新**：`WMS领域设计-ABP-DDD.html` 里若提到「新建时指定启用状态」，也应按方向 A 修正（尚未动，等用户发话）。

用户给出的顺序 → 修正为：

1. **用例**：用业务语言写一句话（不出现字段名、技术词）
2. **归属**：这件事动一个对象还是几个？→ **定聚合边界**（最难改的一步）
3. **方法**：每个聚合根暴露哪些业务动词（不是 setter）
4. **编排**：跨聚合 / 需要外部信息 → 领域服务 / 应用层
5. **落地**：最后才轮到 DTO、表结构、前端

关键认知：**越靠前越难改**。表结构改一次一个迁移；聚合边界划错，整个领域模型返工。

### 自检四问（给用户讲设计时可以直接用）

1. 这句话的主语是谁？（仓库自己变了 vs 别人让仓库变）→ 主语即聚合根
2. 哪些东西必须同时正确？→ 事务边界 = 聚合边界
3. 这个动作必须遵守什么规则？→ 规则写进方法里，不写进注释
4. 有没有别的路能绕过去？→ `private set`，把不变量变成**编译错误**而非代码规范

第 4 条是 IsActive 那一串讨论的最终收获。

### 与芋道的顺序对比（用户最熟的参照）

芋道：建表 → `WarehouseDO` → Mapper → Service（`saveOrUpdate`）→ Controller ＝ **字段先行**
DDD：用例 → 归属 → 业务动词 → 编排 → 表 ＝ **行为先行**（字段是行为留下的痕迹）

### 什么时候不要套这五步

纯字典表 / 纯查询 / 无状态流转的需求，`CrudAppService` 直接上。
判断标准：**这个对象会不会「从一个状态合法地变到另一个状态」**。会 → 值得按五步想；不会 → CRUD。

### 顺带：「仓库编码不能重复」该放哪（还没落地）

按五步看属于 ②③：它是 `Warehouse` 自己的不变量，但**需要查全表才能判定**，
而实体**不能访问仓储** → 所以不能写在构造函数或 `Rename()` 里。
正解：应用层先查重再调构造函数（或在领域服务里查），DB 唯一索引兜底。
这条规则目前在 `LearnDomainErrorCodes` 里还是空的，未实现。

## Create / Update 该不该共用 DTO（2026-09-15）

用户问「为什么往 `CreateUpdateWarehouseDto` 追加字段而不是新建一个」。

**前提纠正**：不是不能拆。ABP 本来就给了两个重载，我们是**主动选了共用版**。

`framework/src/Volo.Abp.Ddd.Application.Contracts/.../ICrudAppService.cs`：

```csharp
// 4 参数版 → 内部把 TUpdateInput 设成 TCreateInput（我们用的就是这个）
public interface ICrudAppService<TEntityDto, in TKey, in TGetListInput, in TCreateInput>
    : ICrudAppService<TEntityDto, TKey, TGetListInput, TCreateInput, TCreateInput> { }

// 5 参数版 → Create / Update 可以用两个不同的 DTO
public interface ICrudAppService<TEntityDto, in TKey, in TGetListInput, in TCreateInput, in TUpdateInput> { }
```

`CrudAppService.cs` 也有对应两版：`:33`（5 泛型）与 `:44`（6 泛型）。

共用 vs 拆开的成本：共用改字段动 1 处；**拆开要动泛型链上的 4 处**
（`IWarehouseAppService` 泛型、`WarehouseAppService` 基类泛型、Mapperly 映射、前端代理重新生成）。

### ⚠️ 但本项目已经踩到「该拆」的信号了：`Code`

`CreateUpdateWarehouseDto` 里声明了 `Code`，但更新路径上：

```csharp
protected override Task MapToEntityAsync(CreateUpdateWarehouseDto input, Warehouse entity)
{
    entity.Rename(input.Name);   // ← 只搬了 Name，input.Code 被静默忽略
    return Task.CompletedTask;
}
```

实体 `Code` 是 `private set` 且没有改名方法 → **编码确实不可改**，规则本身是对的。
问题在于**契约说的和实现做的不一致**：前端生成的 `update(id, input)` 签名里带着 `code`，
调用方会以为能改编码，传了却没用。这是典型的「DTO 该拆」信号。

### 该拆的信号（出现任一就拆）

1. Create / Update 的**字段集不同**（尤其「只读字段」：编码、创建人）
2. 校验规则不同（Create 必填、Update 允许不传）
3. 权限粒度不同（改编码 vs 改名称是两种能力）

### 拆了之后的价值 —— 和 `private set` 是同一个手法

```csharp
public class CreateWarehouseDto { public string Code {get;set;} public string Name {get;set;} }
public class UpdateWarehouseDto { public string Name {get;set;} }
```

「编码不可改」这条规则从「靠 AppService 少写一行」提升到「**编译期这个字段根本不存在**」，
连带前端 `update()` 的入参类型里也没有 `code` —— 谁都没法绕。
**把不变量变成编译错误，而不是代码规范**，与 `private set` 完全同源。

### 结论建议

方向 A 改 DTO 时**一次性拆到位**（`CreateWarehouseDto` / `UpdateWarehouseDto`），
反正都要动 DTO + 重生成代理，顺手拆比以后单独拆便宜。
