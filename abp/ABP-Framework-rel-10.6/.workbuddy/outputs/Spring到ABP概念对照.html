01整体架构对位

Spring 世界ABP 世界
Spring Boot 单体应用-t app 分层模板 / -t app-nolayers 单层模板
Spring Modulith（模块化单体）modules/ 机制 + abp new-module
Spring Cloud（微服务全家桶）-t microservice 模板 + API Gateway + 服务发现
Maven <modules> / Gradle 多项目.slnx 解决方案 + 项目引用

application.yml / application.propertiesappsettings.json / appsettings.Development.json

心智切换：ABP 的分层和 Spring 项目的 controller / service / repository / entity 分层本质相同，只是切得更细——把「service」拆成了 Application.Contracts（接口+DTO）和 Application（实现），把「repository」拆成了 Domain（接口）和 EntityFrameworkCore（实现）。

02启动与装配

SpringABP
@SpringBootApplicationProgram.cs（宿主入口）+ 各层 *Module.cs
@Configuration + @BeanAbpModule.ConfigureServices(context)
@Import(XxxConfig.class)[DependsOn(typeof(XxxModule))]
spring.factories / @AutoConfiguration模块的 [DependsOn] 链（递归收集 + 拓扑排序）
@ConditionalOnProperty / @ProfileConfigure<XxxOptions>(opt => ...)
Spring Boot 自动配置类ABP 各模块的 ConfigureServices（同一套思路）
@Value("${app.xxx}")IConfiguration / Options 模式

模块类对应关系最直观：

// Spring
@Configuration
@Import({DomainConfig.class, ContractsConfig.class})
public class ApplicationConfig {
    @Bean public BookAppService bookAppService(BookRepository r) { ... }
}

// ABP
[DependsOn(
    typeof(BookStoreDomainModule),
    typeof(BookStoreApplicationContractsModule))]
public class BookStoreApplicationModule : AbpModule
{
    public override void ConfigureServices(ServiceConfigurationContext context) { ... }
}

差异点：ABP 模块的生命周期有 三个 阶段而不是一个——PreConfigureServices → ConfigureServices → PostConfigureServices。顺序很重要：Pre 用于「声明参与」（如把当前程序集注册为 MVC ApplicationPart），Post 用于「等所有模块就绪后收尾」（如应用扩展配置）。

关键便利：ABP 里 IBookAppService → BookAppService、IBookRepository → EfCoreBookRepository 这类约定会自动建立接口与实现的绑定，你不用写任何注册代码——**相当于 Spring 里省掉了每个 @Service 类的 @Bean 方法**。

04Web 层

SpringABP
@RestControllerHttpApi 层的 *Controller
@RequestMapping("/api/books")[Route("api/books")]
@GetMapping / @PostMapping[HttpGet] / [HttpPost]
@RequestBody / @ResponseBodyDTO 参数自动绑定 + 自动序列化
Spring Data REST（自动暴露 Repository 为 REST）动态 API：AbpServiceConvention 自动把 AppService 暴露成 REST 端点
@Valid + BindingResultDTO 上的 DataAnnotations，失败自动抛标准异常

重要简化：ABP 里多数情况你不需要写 Controller——只要你的 AppService 实现了 IApplicationService，动态 API 会按约定自动生成 /api/app/book 这类端点。HttpApi 层的 Controller 只在需要自定义路由/特殊绑定时才写。

这在 Spring 里最接近 Spring Data REST，但 ABP 暴露的是 Service 而不是 Repository，粒度更合适。

05业务层

SpringABP
@ServiceApplication 层的 *AppService
接口 + 实现（同包或分模块）Application.Contracts（接口+DTO）/ Application（实现）强制分项目
DTO + MapStructDTO + Mapperly
Feign Client 接口HttpApi.Client 层的 *ClientProxy
@Transactional（手动标注）Unit of Work 自动生效，多数情况不用标；需要精细控制时用 [UnitOfWork]
Service 之间互相注入调用同模块内禁止 AppService 互调（架构约束，见下方说明）

这条约束和 Spring 习惯冲突，容易踩：ABP 规定同一模块内不要把逻辑写成 AppService 调 AppService。需要复用的逻辑要下沉到 Domain 层（领域服务）或提取成独立方法。跨模块调用则只允许通过对方模块的 Application.Contracts。

Spring 项目里 OrderService 直接注入 UserService 很常见，在 ABP 里这是被明确反对的。

06领域与持久化

Spring / JPAABP
@Entity (JPA)Domain 层的实体类

JpaRepository<T, ID>IRepository<T, TKey> / IBasicRepository<T, TKey>
@Repository + @QueryDomain 层 IBookRepository + EntityFrameworkCore 层 EfCoreBookRepository
JPQL / Criteria API / EntityManagerLINQ / IQueryable
@CreatedDate / @LastModifiedDate / @CreatedBy审计字段内置于 FullAuditedAggregateRoot，继承即有
@SoftDelete（Hibernate 6.4+）ISoftDelete —— 内置，且查询自动过滤已删数据
Flyway / LiquibaseEF Core Migrations（dotnet ef migrations add）
Hibernate 懒加载ABP 明确禁用懒加载，用 includeDetails 显式控制
@Version（乐观锁）IHasConcurrencyStamp + ConcurrencyStamp

两个和 JPA 习惯明显不同的点：

① 禁用懒加载。JPA 里靠 @OneToMany(fetch=LAZY) + Session 自动加载很常见；ABP 要求显式指定——仓储方法带 includeDetails 参数，实现里 Include() 出来。这避免了 N+1 和 Session 边界问题，但写法不同。

② 实体不生成 Id。@GeneratedValue 在 ABP 里对应的是「调用方用 IGuidGenerator 生成后传给构造器」。实体构造器里 new Guid() 是被明确禁止的。

多租户是 ABP 相对 Spring 生态最省事的地方。Spring 里你要自己实现 TenantContext + 拦截器 + 所有 SQL 手动加租户条件，还要小心异步丢失上下文。ABP 里这些都内建好了：实体打个 IMultiTenant 标记，之后所有查询自动隔离，异步也不会丢上下文。

09几个「差异较大」的点

这些不是换名字的问题，是设计哲学不同，建议重点记。

① 契约层是硬性拆分，不是可选项

Spring 里接口和实现放同一个包很常见。ABP 强制分成 .Application.Contracts 和 .Application 两个项目，原因是契约要能独立分发给客户端。所有消费者（HttpApi / Web / Blazor / HttpApi.Client）只依赖 Contracts，不依赖实现。

② Unit of Work 是自动的

Spring 里不加 @Transactional 就没有事务。ABP 的 UoW 中间件在请求进入时自动开启、退出时自动提交——你甚至不需要知道它存在。反过来，如果你的逻辑依赖「没事务」的行为，要显式关闭。

③ 约定优于配置的力度更大

事情Spring 你要做ABP
注册 Bean加 @Service加接口标记（如 ITransientDependency），或什么也不加（约定匹配）
暴露 REST写 @RestController什么都不用做（动态 API 自动生成）
实体审计字段加 @EntityListeners(AuditingEntityListener.class) + 4 个注解继承 FullAuditedAggregateRoot
软删除过滤手写 @Where 或 Hibernate 配置实现 ISoftDelete 即可，自动过滤
多租户隔离全部自己实现实现 IMultiTenant 即可

④ 模块既是包，也是部署单元

Spring Modulith 的模块是同一个构建产物内部的包边界。ABP 的模块是独立打包、独立版本、可独立发布到 NuGet 的组件——一个模块对应多个 NuGet 包（每层一个）。所以 ABP 的模块边界比 Spring Modulith 更"硬"，也更容易跨项目复用。

⑤ 动态 API 取代手写 Controller

这是从 Spring 过来最容易「找不到 Controller 在哪」的原因。不是没有 Controller，是运行时生成的。想看实际路由，启动后看 Swagger，而不是去翻代码。

建议的切入方式：拿一个你熟悉的 Spring 项目结构，在脑子里做一次映射——controller 对应 HttpApi、service 对半拆成 Contracts + Application、repository 对半拆成 Domain 接口 + EFCore 实现、entity 对应 Domain。七层里你能一眼认出来的至少四层，剩下三层（Domain.Shared、HttpApi.Client、DbMigrator）是 ABP 特有的补充。
