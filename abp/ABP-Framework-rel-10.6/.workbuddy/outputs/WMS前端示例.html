00一个页面由哪些文件拼成

先给结论：一个 ABP Angular 页面最后会被拆成 6 类文件，分布在 3 个目录层。 你的心智模型「知道接口 → 配请求函数 → 配页面组件 → 按模块找目录 → 分析业务流 → 设计组件通信 → 写代码」里的每一步，都对应下面具体的一份文件。

你的步骤对应文件目录层手写 or 生成
知道接口（DTO / URL）proxy/wms/inbound-orders/models.ts + inbound-order.service.tsapp/proxy/generate-proxy 生成
按模块找目录app/wms/inbound-orders/（你自己的业务目录，与后端 Domain 的 Wms/InboundOrders/ 同名对齐）app/wms/手写
配请求函数inbound-order.service.ts（封装状态机动作的「页面业务服务」）app/wms/inbound-orders/手写
配页面组件inbound-order.component.{ts,html,scss}app/wms/inbound-orders/手写
注册路由inbound-order.routes.ts + 改 app.routes.tsapp/wms/ + app/手写
菜单 + 权限 + 本地化route.provider.ts + 后端 Localization/zh-Hans.jsonapp/ + Domain.Shared手写
前提：proxy 必须先存在，否则后面全编译不过

本项目的 app/proxy/ 目录现在还不存在（模板生成时没有它）。所以第一步永远是先跑 abp generate-proxy，把后端 Application.Contracts 里的 DTO 和 AppService 接口扫成 TS 文件。这一步不做，下面所有 import 'proxy/...' 都会报「找不到模块」。

01前置：生成 proxy，接口层从哪来

请求函数不是手写的，是命令生成的。它扫描后端 Acme.Learn.Application.Contracts 的 DTO 与 AppService 接口，一比一翻译成 TS。

命令

abp generate-proxy -t ng -m Wms -u https://localhost:44362　（-m Wms 只生成 Wms 这个模块，-u 指后端地址）

关键事实

每一个后端方法都会在生成的 service 里变成一个箭头函数属性，内部统一走 restService.request(...)。{ apiName: 'Default' } 对应 environment.apis.default —— RestService 靠它解析 baseUrl（https://localhost:44362）、附上 OAuth token、把后端 BusinessException 翻译成前端错误提示、并管理 loading。

02新目录：Wms 模块落在哪

对应你「按模块找目录」这一步。关键规律：前端业务目录名与后端 Domain 目录名保持一致（都叫 inbound-orders）。后端是 src\Acme.Learn.Domain\Wms\InboundOrders\，前端就建 angular\src\app\wms\inbound-orders\。名字对齐后，你在前端写接口文件时，照着后端目录横向一搜就能定位。

注意一个容易踩的坑

app/proxy/wms/ 与 app/wms/ 是两个不同的地方。proxy 下面是生成的纯 HTTP 层（不改），wms 下面是你自写的业务状态层（复杂页面才需要）。混用是高频错误 —— 业务方法写进 proxy 文件，下次 regenerate 就被覆盖了。

03请求函数：自写业务 service（状态机动作）

对应你「配请求函数」一步。因为入库单有状态机，页面要做的不只是一般的增删改查，还有「确认 / 开始收货 / 取消」这类业务动作。这些动作在 proxy 里各是一个 POST 接口。我们把它们集中到一个「页面业务服务」里，组件就不直接摸 proxy，职责更清楚。

d:\yudao\abp\Acme.Learn\angular\src\app\wms\inbound-orders\inbound-order.service.ts 
import { Injectable } from '@angular/core';
import { InboundOrderService as ProxyInboundOrderService } from '../../proxy/wms/inbound-orders/inbound-order.service';
import { CreateInboundOrderDto, ReceiveInputDto } from '../../proxy/wms/inbound-orders/models';

// 这个 service 区别于 proxy 下的同名 service：它承载「页面业务语义」，不是纯 HTTP
@Injectable({ providedIn: 'root' })
export class InboundOrderBusinessService {
  constructor(private readonly proxy: ProxyInboundOrderService) {}

  // ── 状态机动作：每个动作背后是一个带状态守卫的后端接口 ──
  confirm(id: string)            { return this.proxy.confirm(id); }
  startReceiving(id: string)       { return this.proxy.startReceiving(id); }
  receive(id: string, input: ReceiveInputDto) { return this.proxy.receive(id, input); }
  cancel(id: string)              { return this.proxy.cancel(id); }

  // ── CRUD 透传 ──
  getList = (input: any) => this.proxy.getList(input);
  getById = (id: string) => this.proxy.getById(id);
  create = (input: CreateInboundOrderDto) => this.proxy.create(input);
  delete = (id: string) => this.proxy.delete(id);
}
为什么这里用 providedIn: 'root'，而列表状态用组件级 provider

业务 service 是无状态的（只是转发），全局单例没问题。而 ListService 是有状态的（保存当前页/排序/过滤），绝不能全局单例，否则切换页面状态会串 —— 所以它必须在组件里 providers: [ListService]。（对照口语记忆：业务方法 root 全局，列表状态 provider 局部。）

04页面组件：列表 + abp-modal 内联表单

d:\yudao\abp\Acme.Learn\angular\src\app\wms\inbound-orders\inbound-order.component.ts 
import { Component, OnInit, inject } from '@angular/core';
import { CommonModule } from '@angular/common';
import { FormsModule } from '@angular/forms';
import { ListService, PermissionDirective, LocalizationPipe } from '@abp/ng.core';
import { ModalComponent, ButtonComponent } from '@abp/ng.theme.shared';
import {
  InboundOrderDto, CreateInboundOrderDto,
  InboundOrderStatus, InboundType,
} from '../../proxy/wms/inbound-orders/models';
import { InboundOrderBusinessService } from './inbound-order.service';

@Component({
  selector: 'app-inbound-order',
  templateUrl: './inbound-order.component.html',
  standalone: true,
  imports: [CommonModule, FormsModule, PermissionDirective, LocalizationPipe, ModalComponent, ButtonComponent],
  providers: [ListService],          // ★ 组件级 provider：列表状态唯一的「真源」
})
export class InboundOrderComponent implements OnInit {
  readonly list = inject(ListService);
  private readonly service = inject(InboundOrderBusinessService);

  orders: InboundOrderDto[] = [];
  isModalVisible = false;
  isSaveBusy = false;
  selected: CreateInboundOrderDto = this.emptyForm();

  readonly InboundType = InboundType;          // 暴露给模板用
  readonly InboundOrderStatus = InboundOrderStatus;

  ngOnInit() {
    // hookToQuery：把 ListService 的查询状态（页/排序/过滤）喂给后端接口，
    // 返回的 Observable 可以直接渲染。任何 setter 变化都会自动重新拉数据。
    this.list.hookToQuery(query => this.service.getList(this.toInput(query)))
      .subscribe(result => { this.orders = result.items; });
  }

  // ListService 的 query 字段 → 后端 DTO 字段名（大小写映射在这做）
  private toInput(q: any) {
    return {
      filter: q.search,                                  // 搜索框
      skipCount: (q.page - 1) * q.maxResultCount,
      maxResultCount: q.maxResultCount,
      sorting: q.sortKey ? `${q.sortKey} ${q.sortOrder}` : 'creationTime desc',
    };
  }

  openCreate() {
    this.selected = this.emptyForm();
    this.isModalVisible = true;
  }

  edit(id: string) {
    this.service.getById(id).subscribe(dto => { this.selected = dto; this.isModalVisible = true; });
  }

  save() {
    this.isSaveBusy = true;
    (this.selected.id
      ? this.service.update(this.selected.id, this.selected)
      : this.service.create(this.selected))
      .subscribe({ next: () => { this.isModalVisible = false; this.list.get(); },
                   error: () => { this.isSaveBusy = false; } });
  }

  // ── 状态机动作：Draft 才能确认；动作成功后调 list.get() 刷新，不要手动重拉 ──
  confirm(id: string) { this.service.confirm(id).subscribe(() => this.list.get()); }
  cancel(id: string)   { this.service.cancel(id).subscribe(() => this.list.get()); }

  // 状态标签（真实项目里用 abpLocalization + 本地化 key，见 07 节）
  statusText(s: InboundOrderStatus) { return InboundOrderStatus[s]; }

  private emptyForm(): CreateInboundOrderDto {
    return { type: InboundType.Purchase, lines: [] };
  }
}
三个易错点（对照记忆里的「组件通信四模式」）
  • ListService 必须 providers 在组件里，漏了它会回退为全局实例，列表状态在页面间串。
  • 保存/删除后调 this.list.get() 刷新，不要自己重新绑数据 —— get() 会用当前页/排序/过滤重新请求，这才是单一数据源。
  • 新增与编辑共用同一个 abp-modal，靠 selected.id 是否存在区分，不拆子组件、不用 @Input/@Output 传参（ABP 惯用，回避父子耦合）。

模板浓缩了「组件通信四模式」里的前两条

*abpPermission 是结构性指令，它内部订阅 PermissionService.getGrantedPolicy$()，没有权限时用 vcRef.clear() 移除 DOM 而不是禁用。因此「按钮能不能点」靠权限指令决定，「在哪个状态下显示哪个动作」靠 *ngIf 按 status 决定 —— 权限管「能不能」，状态机管「显示啥」，两者正交。

abp-modal 打开/关闭是标准的 [visible] + (visibleChange) 双向风格，内容用 #abpHeader / #abpBody / #abpFooter 四个自由槽投影，表单就内联在 body 里，不拆子组件。

08核心机制复盘：ListService 单向数据流

ListService组件级 provider
→
get()query 变化自动触发
→
Service.getList(input)proxy → HTTP
→
PagedResultDtoitems + totalCount
→
模板渲染

这张图是把「ABP-前端工作流」记忆里那版画在这里，因为它是理解整个页面的钥匙：

  • 方向永远是单向的：查询状态 → 请求 → 结果 → 渲染。你不手动改列表数据。
  • 回路的唯一写法是 list.get()：保存成功、删除成功、状态机动作成功之后，一律 this.list.get() 让它用当前状态重新请求。不要又去赋值 this.orders = ...，那会破坏单向流。
  • 分页/排序/搜索框：这些控件绑定的是 ListService 的字段（page / maxResultCount / sortKey / sortOrder / search），它们每一个的 setter 都会自动触发一次 get()。你在 hookToQuery 里做的只是「把那个 query 翻译成后端 DTO 字段名」。
  • Loading 也不必自己管：ListService.requestStatus$ 直接给模板里用（*ngIf 显示骨架屏），RestService 负责 HTTP 层 loading。

09对比：只读库存页（轻量变体）

入库单因为带状态机，页面动作多。如果只是一个只读的实时库存页（对应 WMS 的 Inventory 聚合根，核心是计算属性 AvailableQuantity），代码会大幅缩短。关键差异：没有 modal、没有业务动作，组件更薄。

          <td>{{ it.quantity }}</td><td>{{ it.allocatedQuantity }}</td>
          <td><strong>{{ it.availableQuantity }}</strong></td>   <!-- 后端计算属性 -->
        </tr>
      </tbody>
    </table>`,
  standalone: true,
  providers: [ListService],
})
export class InventoryComponent {
  readonly list = inject(ListService);
  items: any[] = [];
  constructor(private readonly service: InventoryService) {
    this.list.hookToQuery(q => this.service.getList(this.toInput(q)))
      .subscribe(r => { this.items = r.items; });
  }
  private toInput(q: any) { return { skipCount: (q.page - 1) * q.maxResultCount, maxResultCount: q.maxResultCount }; }
}
结论：页面复杂度与「业务动作数量」正相关，而不是与「实体复杂度」正相关

库存页比入库单页简单得多，不是因为 Inventory 实体简单，而是因为它只有查询、没有状态机动作。这也印证了记忆里的判断框架：主数据（Warehouse/Material）贫血化、页面就是列表+modal；出入库单+库存这种有状态机/有一致性的，页面才会出现「按状态显隐的动作按钮 + 刷新回路」。

高频坑（对照记忆逐条核对过）

坑1ListService 忘了 component providers，列表状态串页

ListService 默认不是全局单例，但一旦你在某处 providedIn:'root' 或漏了组件 providers，它就会变成共享实例。排查方式：切换分页后 get() 带着上一页的页码请求 → 就是它。

坑2把业务方法写进了 proxy 文件，regenerate 后被覆盖

proxy/ 是生成目录，别在里面加自己的逻辑。需要页面级业务状态（状态机动作、派生状态）就在 wms/inbound-orders/ 自写 service，内部再注入 proxy。

坑3权限字符串只改了菜单处，路由守卫和第 3 处按钮漏了

一个权限字符串有 3 个出现位置（路由 data.requiredPolicy、菜单 requiredPolicy、模板 *abpPermission）。前端记得三角对齐，而枚举值本身以后端 InboundOrderPermissions.cs 为准，那才是真源。

坑4找不到 proxy，或 proxy 里没有想要的方法

最常见原因是还没跑 generate-proxy，或后端 AppService 接口没在 Application.Contracts 里声明（ABP 动态 API 只暴露接口上声明的方法）。先确认后端 Swagger 里 /api/app/inbound-order 存在，再生成。

坑5保存后界面不刷新，或手动重新绑数据导致重复请求

统一用 this.list.get()。它带当前查询状态刷新，且只发一次请求。手动再赋值 this.orders = ... 会打破单向数据流，还会和自动请求打架。
