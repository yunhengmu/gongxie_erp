01这个仓库到底是什么

打开 ABP-Framework-rel-10.6 你看到的不是一个业务应用，而是 ABP 框架本体 + 周边生态的 monorepo。这一点必须先说清楚，否则目录结构会让人困惑。仓库根部的 .cursorrules 第一行就写明了：

D:\yudao\abp\ABP-Framework-rel-10.6\.cursorrules（第 2 行）# Scope: ABP Framework repository (abpframework/abp) — for developing ABP itself, not ABP-based applications.

根目录的主力目录各自承担不同职责：

目录是什么你什么时候会看它
framework/src/框架内核，几百个 Volo.Abp.* 包（DI、授权、本地化、审计、EventBus、DDD 基类…）想知道「这个能力框架怎么实现的」
modules/官方预置应用模块：blogging、identity、cms-kit、audit-logging…学业务代码怎么写的最佳范本
templates/app/「单应用」启动模板（前后端完整脚手架）照着它搭自己的项目
templates/module/「可复用模块」启动模板写跨项目复用的业务模块
templates/app-nolayers/、console、maui、wpf单层极简版 / 控制台 / 桌面端模板按需选择架构复杂度
npm/ng-packs/Angular 侧的全部 @abp/ng.* 包（identity、tenant-management、theme-basic…）写 Angular 页面时用到的现成组件
docs/、studio/、schemas/、tools/文档、ABP Studio 桌面端、模型 schema、CLI 工具工具链与配置参考

一句话定位：ABP 是架在 ASP.NET Core 之上的「企业级应用架构脚手架」。它把分层、模块化、多租户、横切关注点（授权/校验/异常/本地化/审计）全部做成了基础设施，让你只写业务。

02六根支柱：ABP 的核心机制

不先理解这六个机制，后面看分层会觉得「为什么到处是 DependsOn / 为什么没写 new 就能用」。它们解释了 ABP 里几乎所有「约定优于配置」的魔法。

① 模块化（Modularity）

每个程序集必须有且仅有一个 AbpModule 子类，用 [DependsOn(typeof(...))] 声明它依赖哪些模块。框架启动时按依赖图做拓扑排序，依次调用各模块的 ConfigureServices / OnApplicationInitialization。

templates/app/.../MyProjectNameDomainModule.cs[DependsOn(
    typeof(MyProjectNameDomainSharedModule),
    typeof(AbpIdentityDomainModule),
    typeof(AbpTenantManagementDomainModule),
    typeof(AbpAuditLoggingDomainModule)
)]
public class MyProjectNameDomainModule : AbpModule
{
    public override void ConfigureServices(ServiceConfigurationContext context)
    {
        Configure<AbpMultiTenancyOptions>(options =>
            options.IsEnabled = MultiTenancyConsts.IsEnabled);
    }
}

这套机制带来的直接结果是：业务模块可以独立开发、独立测试、按需装配，也是后面「模块化单体 / 微服务」两条架构路线的共同地基。

② 依赖注入的约定式注册

ABP 不要求你写 services.AddTransient<IFoo, Foo>()。实现了这些接口的类会自动注册：

  • ITransientDependency / ISingletonDependency / IScopedDependency —— 按生命周期自动注册
  • IApplicationService、IDomainService、IRepository 等 —— 有专属约定

所以你会看到 PostAppService 构造函数里直接注入 IPostRepository，却没有任何地方写注册代码。

③ 仓储抽象（Repository）

领域层只依赖仓储接口（如 IPostRepository），实现放在 ORM 集成层（EfCorePostRepository）。这意味着：换数据库（EF Core ↔ MongoDB）不影响领域逻辑。框架还提供 IRepository<T, TKey> 泛型基座，自定义仓储继承它即获得 GetAsync/InsertAsync/UpdateAsync/DeleteAsync/GetListAsync 全套能力。

④ 横切关注点自动化

关注点你怎么用框架做什么
授权方法上打 [Authorize(权限名)]自动拦截、校验当前用户是否拥有该权限
校验DTO 上打 [Required] [DynamicStringLength]进入应用服务前自动验证，失败抛标准异常
异常处理领域里抛 BusinessException("码")统一转成规范的 JSON 错误响应 + 本地化消息
本地化JSON 资源文件 + L["Key"]按请求语言自动切换
审计实体继承 FullAuditedAggregateRoot自动记录创建人/时间/修改人/软删除
数据过滤无感自动追加多租户、软删除过滤条件

⑤ 多租户（Multi-Tenancy）

一个部署实例服务多个租户，数据自动隔离。开关就一行：MultiTenancyConsts.IsEnabled；实体实现 IMultiTenant 后，框架自动在所有查询上加租户过滤。

⑥ 事件总线（Event Bus）

ILocalEventBus（进程内、同模块解耦）与 IDistributedEventBus（跨服务）。ETO（事件传输对象）放 Domain.Shared。blogging 模块里 PostChangedEvent 就是用它做缓存失效的。

03解决方案分层与依赖方向

这是整个框架最关键的一张图。ABP 强制「依赖单向向下」，越往下越稳定、越往上越易变。规则直接来自 .cursorrules 的 Layering 一节。

层职责可以依赖严禁出现
Domain.Shared常量、枚举、错误码、多语言资源、ETO —— 所有层和第三方客户端都能安全引用的东西无（最底层）实体、仓储、领域服务、业务对象
Domain实体/聚合根、仓储接口、领域服务、领域事件Domain.SharedEF Core、Web、DTO
Application.Contracts应用服务接口、DTO、权限定义Domain.Shared实体、仓储实现
Application应用服务实现、对象映射、用例编排Domain + Application.ContractsWeb 类型（IFormFile/Stream）
EntityFrameworkCoreDbContext、实体映射、仓储实现、迁移DomainApplication、HttpApi
HttpApiREST 控制器（薄适配器）仅 Application.ContractsApplication（实现）
HttpApi.Client远程调用代理仅 Application.ContractsApplication
Web / BlazorUI 宿主与页面仅 HttpApi直接碰 Domain

记住这条链，90% 的设计问题都能自检：
Web → HttpApi → Application.Contracts ← Application → Domain → Domain.Shared
ORM 集成 → 只指向 Domain。

为什么 HttpApi 只能依赖 Contracts 而不能依赖 Application？因为「接口与实现分离」是这套架构的命门。控制器对着 IPostAppService（接口）编程，运行时由 DI 注入实现。这样同一套契约既能被本地应用服务实现，也能被 HttpApi.Client 拿去生成远程代理——微服务拆分时才不用改前端。

05端到端开发工作流

把上面所有规则收束成一条可执行的流水线。假设业务需求是「管理产品目录」，一个功能从 0 到界面上线要走这 9 步——顺序很重要，因为依赖是单向的。

  1. 领域建模：识别聚合根与不变量
    在纸上想清楚：Product 是一个聚合根吗？它有哪些必须成立的规则（标题非空、编码唯一）？哪些字段是它自己管的，哪些该引用别的聚合（只存 Id）？
  2. Domain.Shared：先立常量与错误码
    写 ProductConsts（MaxNameLength 等），错误码写进 *DomainErrorCodes。常量先行的好处是各层都能引用同一份契约。
  3. Domain：写实体
    提供带参构造器（强制不变量）+ protected 无参构造器（给 ORM）；子集合在构造器里初始化；Id 不由实体内生成，从外部传入 IGuidGenerator 生成的值。
  4. Domain：定义仓储接口 +（可选）领域服务
    只说「我需要什么查询能力」，不说怎么查。复杂领域规则放进 *Manager。
  5. EntityFrameworkCore：注册进 DbContext + 配置映射
    加 DbSet<Product>，在 ConfigureMyProjectName() 扩展方法里配表名/字段长度/索引。然后生成迁移。这一步完成，数据库就通了。
  6. EntityFrameworkCore：实现仓储
    继承 EfCoreRepository<TDbContext, Product, Guid>，把接口里的查询用 LINQ 实现。
  7. Application.Contracts：定义 DTO 与 AppService 接口
    输入 DTO 与输出 DTO 分开、不复用；接口里只出现 DTO 和原始类型，绝不出现实体。顺手把权限定义加上。
  8. Application：实现 AppService
    用仓储取实体 → 调领域方法改状态 → UpdateAsync 落库 → 用 ObjectMapper 映射成 DTO 返回。查询逻辑不写在这层。
  9. HttpApi + 前端：暴露 API、写页面
    控制器只是把 HTTP 转成对 AppService 的调用（几行）。前端则基于生成的代理写列表页 + 编辑弹窗。

顺序不能乱。常见错误是「先写前端、再补后端接口」，这会逼你把 DTO 设计成前端字段的堆砌，破坏契约层。按 1→9 走，每一步只依赖上一步的产出。

06后端：从业务到 Model，再到业务代码

这一节全部用真实可编译的写法，范式取自仓库中两个来源：templates/module/.../Samples/（官方最小范例）与 modules/blogging/src/.../Posts/（真实完整业务）。下面以「产品 Product」为例，走完整条链路。

6.1 第一步：业务 → 模型（怎么"想"出实体）

ABP 用 DDD 的聚合根（Aggregate Root）概念。判断标准很简单：

问题如果是落法
这个东西有生命周期、被独立增删改查吗？是它是聚合根，继承 AggregateRoot<Guid>（或审计版），单独建仓储
它必须依附于另一个聚合根存在吗？（如订单明细）是它是子实体，属于父聚合，不单独建仓储
我只是需要引用另一个聚合吗？是只存对方的 Id，不要加导航属性（.cursorrules 明确禁止）
它有「不能为空的字段 / 不能违反的规则」吗？是这些进入构造器，让「创建即合法」

以 Product 为例：它有独立生命周期 → 聚合根；必须继承审计能力（谁建的/谁改的/软删除）→ 用 FullAuditedAggregateRoot<Guid>；Name 不能为空且必须在构造器校验。

6.3 Domain：写实体（聚合根）

src/MyCompanyName.MyProjectName.Domain/Products/Product.csusing System;
using JetBrains.Annotations;
using Volo.Abp;
using Volo.Abp.Domain.Entities.Auditing;

namespace MyCompanyName.MyProjectName.Products;

// FullAuditedAggregateRoot 自带：CreationTime/CreatorId/LastModificationTime/
// IsDeleted/DeleterId —— 审计与软删除全部自动。
public class Product : FullAuditedAggregateRoot<Guid>
{
    // 非公开 setter：外部无法绕过领域方法直接改状态
    public virtual string Code { get; protected set; }
    public virtual string Name { get; protected set; }
    public virtual string Description { get; set; }
    public virtual bool IsActive { get; protected set; }

    // 【必须】给 ORM 用的无参构造器，用 protected 挡住业务代码
    protected Product() { }

    // 【必须】带参构造器：Id 由外部传入，不在这里 new Guid()
    public Product(Guid id, [NotNull] string code, [NotNull] string name)
    {
        Id = id;
        Code = Check.NotNullOrWhiteSpace(code, nameof(code));
        Name = Check.NotNullOrWhiteSpace(name, nameof(name));
        IsActive = true;
    }

    // 领域方法：表达业务动作，而非暴露 setter。返回 this 便于链式调用
    public virtual Product SetName([NotNull] string name)
    {
        Name = Check.NotNullOrWhiteSpace(name, nameof(name));
        return this;
    }

    public virtual void Activate() => IsActive = true;
    public virtual void Deactivate() => IsActive = false;
}

三条硬红线（.cursorrules 明确要求）：① 聚合根只能用单一 Id，禁止复合主键；② 禁止在构造器里生成 Guid——由调用方用 IGuidGenerator 生成后传入；③ 引用其他聚合根只允许存 Id，禁止导航属性。

6.4 Domain：仓储接口

src/MyCompanyName.MyProjectName.Domain/Products/IProductRepository.csusing Volo.Abp.Domain.Repositories;

namespace MyCompanyName.MyProjectName.Products;

// IBasicRepository 只暴露基础 CRUD，不把 IQueryable 泄给上层
public interface IProductRepository : IBasicRepository<Product, Guid>
{
    // 约定：全部 async + CancellationToken；返回集合的 includeDetails=false
    Task<List<Product>> GetListByCodeAsync(
        string code,
        bool includeDetails = false,
        CancellationToken cancellationToken = default);

    // 返回单个实体的 includeDetails=true
    Task<Product> FindByCodeAsync(
        string code,
        bool includeDetails = true,
        CancellationToken cancellationToken = default);

    Task<bool> IsCodeInUseAsync(
        string code,
        Guid? excludedId = null,
        CancellationToken cancellationToken = default);
}

注意接口里没有出现任何 IQueryable / EF 类型——这是为了将来能换成 MongoDB 实现。博客模块的 IPostRepository 就是这个写法的真实样本。

6.5 EntityFrameworkCore：注册 DbContext 与实体映射

src/.../EntityFrameworkCore/EntityFrameworkCore/MyProjectNameDbContext.cs（节选）public class MyProjectNameDbContext : AbpDbContext<MyProjectNameDbContext>
{
    // 聚合根才有资格出现在 DbSet 上
    public DbSet<Product> Products { get; set; }

    protected override void OnModelCreating(ModelBuilder builder)
    {
        base.OnModelCreating(builder);
        // 不要在这里直接配实体，调用扩展方法
        builder.ConfigureMyProjectName();

}
src/.../EntityFrameworkCore/EntityFrameworkCore/MyProjectNameDbContextModelCreatingExtensions.cspublic static class MyProjectNameDbContextModelCreatingExtensions
{
    public static void ConfigureMyProjectName(this ModelBuilder builder)
    {
        Check.NotNull(builder, nameof(builder));

        builder.Entity<Product>(b =>
        {
            // 表名 = 前缀 + 复数，前缀来自 MyProjectNameDbProperties.DbTablePrefix
            b.ToTable(MyProjectNameDbProperties.DbTablePrefix + "Products",
                      MyProjectNameDbProperties.DbSchema);

            b.ConfigureByConvention();   // 自动配好基类属性（审计、并发戳等）

            b.Property(x => x.Code)
             .IsRequired()
             .HasMaxLength(ProductConsts.MaxCodeLength);

            b.Property(x => x.Name)
             .IsRequired()
             .HasMaxLength(ProductConsts.MaxNameLength);

            b.Property(x => x.Description)
             .HasMaxLength(ProductConsts.MaxDescriptionLength);

            b.HasIndex(x => x.Code).IsUnique();   // 编码唯一
        });
    }
}

6.6 EntityFrameworkCore：实现仓储

src/.../EntityFrameworkCore/Products/EfCoreProductRepository.cspublic class EfCoreProductRepository
    : EfCoreRepository<IMyProjectNameDbContext, Product, Guid>,
      IProductRepository
{
    public EfCoreProductRepository(IDbContextProvider<IMyProjectNameDbContext> provider)
        : base(provider) { }

    public async Task<List<Product>> GetListByCodeAsync(
        string code, bool includeDetails = false,
        CancellationToken cancellationToken = default)
    {
        return await (await GetDbSetAsync())
            .Where(p => p.Code == code)
            .ToListAsync(GetCancellationToken(cancellationToken));
    }

    public async Task<Product> FindByCodeAsync(
        string code, bool includeDetails = true,
        CancellationToken cancellationToken = default)
    {
        return await (await GetDbSetAsync())
            .FirstOrDefaultAsync(p => p.Code == code,
                              GetCancellationToken(cancellationToken));
    }

    public async Task<bool> IsCodeInUseAsync(
        string code, Guid? excludedId = null,
        CancellationToken cancellationToken = default)
    {
        var query = (await GetDbSetAsync()).Where(p => p.Code == code);
        if (excludedId != null) query = query.Where(p => p.Id != excludedId);
        return await query.AnyAsync(GetCancellationToken(cancellationToken));
    }
}

6.7 Application.Contracts：DTO 与接口

src/.../Application.Contracts/Products/ProductDto.csusing Volo.Abp.Application.Dtos;

namespace MyCompanyName.MyProjectName.Products;

// 输出 DTO：继承审计 DTO，附带 IHasConcurrencyStamp 支持乐观并发

6.8 Application：实现应用服务（业务代码主战场）

src/.../Application/Products/ProductAppService.csusing Microsoft.AspNetCore.Authorization;
using Volo.Abp.Application.Dtos;
using Volo.Abp.Domain.Repositories;

namespace MyCompanyName.MyProjectName.Products;

public class ProductAppService : MyProjectNameAppService, IProductAppService
{
    private readonly IProductRepository _productRepository;

    // 构造器注入仓储接口 —— 无需手写 DI 注册，ABP 自动完成
    public ProductAppService(IProductRepository productRepository)
        => _productRepository = productRepository;

    public virtual async Task<ProductDto> GetAsync(Guid id)
    {
        var product = await _productRepository.GetAsync(id);
        return ObjectMapper.Map<Product, ProductDto>(product);
    }

    public virtual async Task<PagedResultDto<ProductDto>> GetListAsync(GetProductListDto input)
    {
        // 仓储只需暴露 IQueryable 的用法在实现层；这里用基础能力
        var totalCount = await _productRepository.GetCountAsync();
        var items = await _productRepository.GetPagedListAsync(
            input.SkipCount, input.MaxResultCount, input.Sorting);

        return new PagedResultDto<ProductDto>(
            totalCount,
            ObjectMapper.Map<List<Product>, List<ProductDto>>(items));
    }

    [Authorize(MyProjectNamePermissions.Products.Create)]
    public virtual async Task<ProductDto> CreateAsync(CreateProductDto input)
    {
        // 业务规则：编码不能重复 —— 违反时抛带错误码的业务异常
        if (await _productRepository.IsCodeInUseAsync(input.Code))
        {
            throw new BusinessException(MyProjectNameDomainErrorCodes.ProductCodeAlreadyExists)
                .WithData("Code", input.Code);
        }

        // Id 由 IGuidGenerator 生成（ApplicationService 基类已提供 GuidGenerator）
        var product = new Product(GuidGenerator.Create(), input.Code, input.Name)
        {
            Description = input.Description
        };

        await _productRepository.InsertAsync(product);
        return ObjectMapper.Map<Product, ProductDto>(product);
    }

    [Authorize(MyProjectNamePermissions.Products.Update)]
    public virtual async Task<ProductDto> UpdateAsync(Guid id, UpdateProductDto input)
    {
        var product = await _productRepository.GetAsync(id);

        // 通过领域方法改状态，而不是直接 set 属性
        product.SetName(input.Name);
        product.Description = input.Description;
        product.SetConcurrencyStampIfNotNull(input.ConcurrencyStamp);

        // 显式落库：不依赖 EF 变更跟踪，保证语义清晰
        product = await _productRepository.UpdateAsync(product);
        return ObjectMapper.Map<Product, ProductDto>(product);
    }

    [Authorize(MyProjectNamePermissions.Products.Delete)]
    public virtual async Task DeleteAsync(Guid id)
        => await _productRepository.DeleteAsync(id);
}

6.9 HttpApi：暴露 REST 接口

src/.../HttpApi/Products/ProductsController.csusing Microsoft.AspNetCore.Mvc;
using Volo.Abp;
using Volo.Abp.Application.Dtos;

namespace MyCompanyName.MyProjectName.Products;

[Area(MyProjectNameRemoteServiceConsts.ModuleName)]
[RemoteService(Name = MyProjectNameRemoteServiceConsts.RemoteServiceName)]
[Route("api/my-project-name/products")]
public class ProductsController : MyProjectNameController, IProductAppService
{
    private readonly IProductAppService _service;

    // 注意：注入的是【接口】，不是 ProductAppService 实现类
    public ProductsController(IProductAppService service) => _service = service;

    [HttpGet]
    [Route("{id}")]
    public Task<ProductDto> GetAsync(Guid id) => _service.GetAsync(id);

    [HttpGet]
    public Task<PagedResultDto<ProductDto>> GetListAsync(GetProductListDto input)
        => _service.GetListAsync(input);

    [HttpPost]
    public Task<ProductDto> CreateAsync(CreateProductDto input)
        => _service.CreateAsync(input);

    [HttpPut]
    [Route("{id}")]
    public Task<ProductDto> UpdateAsync(Guid id, UpdateProductDto input)
        => _service.UpdateAsync(id, input);

    [HttpDelete]
    [Route("{id}")]
    public Task DeleteAsync(Guid id) => _service.DeleteAsync(id);
}

控制器要"薄"。它只做三件事：声明 HTTP 动词与路由、接收参数、转发给应用服务。任何业务判断写在这里都是错的——因为业务逻辑要能被非 HTTP 场景（后台任务、gRPC）复用。另外，控制器实现应用服务接口是 ABP 的惯用技巧：框架据此自动补齐路由约定与参数绑定。

angular/src/app/products/list/list.component.tsimport { Component, inject, OnInit } from '@angular/core';
import { ListService, PermissionService } from '@abp/ng.core';
import { ConfirmationService, ToasterService } from '@abp/ng.theme.shared';
import { ProductService } from '../../proxy/products/product.service';

@Component({
  selector: 'app-product-list',
  templateUrl: './list.component.html',
})
export class ListComponent implements OnInit {
  private readonly productService = inject(ProductService);
  private readonly list = inject(ListService);
  private readonly confirmation = inject(ConfirmationService);
  private readonly toaster = inject(ToasterService);
  permissions = inject(PermissionService);

  data: PagedResultDto<ProductDto> = { items: [], totalCount: 0 };

  ngOnInit() { this.hookToQuery(); }

  // ListService 自动把分页、排序、筛选的 query 变化推过来
  private hookToQuery() {
    this.list.hookToQuery('products')
      .subscribe(query =>
        this.productService.getList(query).subscribe(res => (this.data = res)));
  }

  delete(id: string) {
    this.confirmation
      .warn('::AreYouSureToDelete', '::AreYouSure')
      .subscribe(status => {
        if (status === 'confirm') {
          this.productService.delete(id).subscribe(() => {
            this.toaster.success('::DeletedSuccessfully');
            this.list.get()
          });
        }
      });
  }
}

7.5 前端的通用规律（无论哪种形态）

  • 页面 = 薄壳：负责展示与交互，业务规则一律在后端应用服务里。前端不重复实现校验逻辑，但要用上 DTO 上带下来的元数据做即时反馈。
  • 菜单与权限绑定：菜单项的 requiredPolicy / RequirePermissions 必须与后端权限常量同名，否则会出现「看得见点不动」或「有权限没入口」。
  • 本地化 key 复用后端资源：::Menu:Products 这类 key 最终读的还是后端 Localization/*.json 或前端 src/assets/i18n/*.json，保持同一份文案来源。
  • OpenAPI 是第一公民：后端一改 Application.Contracts，前端重新跑一次 generate-proxy 即可。契约层就是前后端的唯一接口。

08命名与编码约定速查

以下全部摘自仓库 .cursorrules，是 ABP 官方的硬性规范。写代码时对着自检。

类别约定
模块类每程序集恰好一个 AbpModule，命名 Abp[模块][层]Module，用 [DependsOn] 声明依赖
实体聚合根单一 Id，优先 Guid；protected 无参构造器给 ORM；带参构造器强制不变量；Id 不在构造器内生成；成员尽量 virtual
聚合边界保持小而精；引用其他聚合只存 Id，不加导航属性
仓储每个聚合根一个专属仓储；接口继承 IBasicRepository；全异步 + CancellationToken；单条查询带 includeDetails=true，列表带 =false；对外不暴露 IQueryable
领域服务命名 *Manager；默认不建接口；只收领域对象，不收 DTO；违反规则抛 BusinessException + 命名空间错误码
应用服务接口 I*AppService 继承 IApplicationService；方法名不重复实体名（GetAsync）；GetListAsync(QueryDto)；UpdateAsync(id, dto)——Id 不进 DTO；实现类方法全部 virtual；不用泛型仓储；LINQ 查询留在仓储而不在应用服务
DTO放 .Contracts；输入 DTO 不复用、不继承；用 DataAnnotations + 复用 Domain.Shared 常量；输出分 Basic / Detailed 两档；禁止 [Serializable]
EF Core每模块独立 DbContext 接口 + 实现；禁用懒加载；DbSet 只暴露聚合根；实体配置写在 ModelBuilder 扩展方法里，不写进 OnModelCreating；每个实体调 ConfigureByConvention()
权限定义在 .Contracts/Permissions；命名 [模块].[权限]；用常量不用裸字符串
本地化资源放 Domain.Shared/Localization/；类名 [模块]Resource；错误码命名 模块:错误名；用户可见文案一律本地化
事件同进程用 ILocalEventBus，跨服务用 IDistributedEventBus；ETO 放 Domain.Shared，命名 [实体][动作]Eto；处理器放 Application 层
测试基类 AbpIntegratedTest<T> / AbpApplicationTestBase<T>；断言用 Shouldly；方法名 Method_Scenario_Expected
