01边界与聚合划分

先给结论：这个精简 WMS 需要 7 个聚合根、2 个聚合内实体和 3 个领域服务。其中，出入库单的设计是否正确，直接决定整个系统的成败。

为什么库位要「妥协」成独立聚合根

这是本设计里唯一的判断难点：业务上库位依附于仓库，技术上却必须独立。

判断依据Location 的实际情况指向
有独立生命周期吗随仓库创建/删除，不单独存在聚合内
会被单独大量查询吗会 —— 库存查询、上架推荐都按库位查倾向独立
业务不变量跨库位吗「同一仓库内库位编码唯一」，边界在 Warehouse 内聚合内
设计决策

把 Location 独立成聚合根。理由是查询频率压倒了其他一切考量：作为聚合内实体，你无法独立分页查询库位，只能先加载 Warehouse 再逐个遍历。DDD 允许为了性能在边界上做妥协，但要意识到这是妥协，而不是「本来就这么设计」。

反过来，单据行（OrderLine）必须是聚合内实体：它和单头共享同一条不变量（「一张单不能有重复物料」），而且从不被单独查询。

{

    public string Name { get; private set; }
    public string Address { get; private set; }
    public bool IsActive { get; private set; }

    protected Warehouse() { }

    public Warehouse(Guid id, string code, string name) : base(id)
    {
        SetCode(code);
        SetName(name);

    }

    {
        Check.NotNullOrWhiteSpace(code, nameof(code), maxLength: 32);
        Code = code;
        return this;
    }

    public Warehouse SetName(string name)
    {
        Check.NotNullOrWhiteSpace(name, nameof(name), maxLength: 128);
        Name = name;
        return this;
    }

    public void Activate()   => IsActive = true;    // 状态变更必须走业务动词，而不是公开 setter
    public void Deactivate() => IsActive = false;
}
要点

编码校验（非空、长度）放在领域方法里，而不是放在 AppService。这是充血模型与贫血模型最直观的分界线。

状态字段同理，而且更严格：一律 private set + 成对的业务动词（Activate() / Deactivate()）。只要留了公开 setter，自动映射器（ObjectMapper.Map，等价于 BeanUtils.copyProperties）就能绕过规则直接改状态；换成 private set，这条路会被编译器堵死 —— 把不变量变成编译错误，而不是靠代码规范。所以有 IsActive 这个字段，就必须有成对的动词方法；只声明字段不给方法，等于这个状态谁也改不了。

再记一条：布尔字段描述「事实」，动词方法表达「指令」，不要让一个布尔同时承担两件事。顺带看三个实体的构造函数 —— 默认值不同是刻意的：仓库建好后要配库位、配设备，所以新建即停用（false）；物料和库位建好即可用（true）。默认值本身就是业务规则，必须是有意识的选择，不能随手写。

03入库单与状态机

状态机先行

设计单据的第一步不是写类，而是画状态机。入库单的状态流转如下：

Draft草稿
→
Confirmed已确认
→
Receiving收货中
→
Completed已完成

↳ 另外，Draft / Confirmed / Receiving 三个状态均可取消，转入 Cancelled（已取消）；Completed 是终态，不可取消

状态含义允许的操作能否编辑行
Draft草稿，刚创建增删行、确认、取消可以
Confirmed已确认，等待收货开始收货、取消禁止
Receiving收货进行中继续收货、完成禁止
Completed收货完成，库存已增加仅查询禁止
Cancelled已取消仅查询禁止

InboundOrder 实体

D:\yudao\abp\Acme.Learn\src\Acme.Learn.Domain\Wms\InboundOrders\InboundOrder.cs 
public class InboundOrder : FullAuditedAggregateRoot<Guid>
{
    public string OrderNo { get; private set; }              // IN20260911001
    public Guid WarehouseId { get; private set; }            // 跨聚合 → Id
    public InboundType Type { get; private set; }            // 采购/退货/调拨
    public string SourceOrderNo { get; private set; }        // 来源单号
    public InboundOrderStatus Status { get; private set; }   // 状态机

    private readonly List<InboundOrderLine> _lines = new();
    public IReadOnlyCollection<InboundOrderLine> Lines => _lines.AsReadOnly();  // ← 只读暴露

    protected InboundOrder()
    {
        _lines = new List<InboundOrderLine>();               // EF Core 需要
    }

    public InboundOrder(Guid id, string orderNo, Guid warehouseId,
                        InboundType type, string sourceOrderNo) : base(id)
    {
        SetOrderNo(orderNo);
        WarehouseId = warehouseId;
        Type = type;
        SourceOrderNo = sourceOrderNo;
        Status = InboundOrderStatus.Draft;                    // 初始状态
    }

    // ── 领域方法（业务规则集中在这里）──────────────────
    public InboundOrderLine AddLine(Guid materialId, decimal quantity,
                                     Guid? locationId = null)
    {
        EnsureEditable();                                     // 状态守卫
        Check.Positive(quantity, nameof(quantity));

        if (_lines.Any(x => x.MaterialId == materialId))      // 不变量：不可重复物料
            throw new BusinessException(WmsErrorCodes.DuplicateMaterialInOrder);

        var line = new InboundOrderLine(
            GuidGenerator.Create(), Id, materialId, quantity, locationId);

        _lines.Add(line);
        return line;
    }

    public void RemoveLine(Guid lineId)
    {
        EnsureEditable();
        var line = _lines.FirstOrDefault(x => x.Id == lineId)
            ?? throw new BusinessException(WmsErrorCodes.LineNotFound);
        _lines.Remove(line);
    }

    public void Confirm()                                     // Draft → Confirmed
    {
        if (Status != InboundOrderStatus.Draft)
            throw new BusinessException(WmsErrorCodes.InvalidStatusTransition);
        if (!_lines.Any())
            throw new BusinessException(WmsErrorCodes.OrderHasNoLine);

        Status = InboundOrderStatus.Confirmed;
    }

    public void StartReceiving()                              // Confirmed → Receiving
    {
        if (Status != InboundOrderStatus.Confirmed)
            throw new BusinessException(WmsErrorCodes.InvalidStatusTransition);
        Status = InboundOrderStatus.Receiving;
    }

    public void Complete()                                    // Receiving → Completed
    {
        if (Status != InboundOrderStatus.Receiving)
            throw new BusinessException(WmsErrorCodes.InvalidStatusTransition);

        // 不变量：所有行必须收满
        if (_lines.Any(x => x.ReceivedQuantity < x.ExpectedQuantity))
            throw new BusinessException(WmsErrorCodes.NotAllLinesReceived);

        Status = InboundOrderStatus.Completed;
    }

    public void Cancel()                                      // 任意非完成态 → Cancelled
    {
        if (Status == InboundOrderStatus.Completed)
            throw new BusinessException(WmsErrorCodes.CannotCancelCompletedOrder);
        Status = InboundOrderStatus.Cancelled;
    }

    private void EnsureEditable()
    {
        if (Status != InboundOrderStatus.Draft)
            throw new BusinessException(WmsErrorCodes.OrderNotEditable);
    }
}

public enum InboundType { Purchase = 1, Return = 2, Transfer = 3, Other = 9 }

public enum InboundOrderStatus
{
    Draft     = 0,    // 草稿
    Confirmed = 1,    // 已确认（待收货）
    Receiving = 2,    // 收货中
    Completed = 3,    // 已完成
    Cancelled = 9     // 已取消
}
这个类是全系统最关键的
  • _lines 是 private readonly List<>，对外只暴露 IReadOnlyCollection —— 外部不能直接调用 order.Lines.Add(...)，必须走 AddLine()
  • 所有状态流转都是领域方法，并且都带守卫（EnsureEditable）
  • 业务异常用 BusinessException 加错误码常量，AppService 不用管，ABP 会自动转成 HTTP 400

public class InboundOrderLine : Entity<Guid>          // ← Entity，不是 AggregateRoot
{
    public Guid InboundOrderId { get; private set; }  // 指回父聚合
    public Guid MaterialId { get; private set; }      // 跨聚合 → Id
    public Guid? LocationId { get; private set; }     // 目标库位
    public decimal ExpectedQuantity { get; private set; }   // 应收
    public decimal ReceivedQuantity { get; private set; }   // 实收

    protected InboundOrderLine() { }

    internal InboundOrderLine(Guid id, Guid inboundOrderId, Guid materialId,
                              decimal expectedQuantity, Guid? locationId) : base(id)
    {
        InboundOrderId = inboundOrderId;
        MaterialId = materialId;
        LocationId = locationId;
        ExpectedQuantity = expectedQuantity;
        ReceivedQuantity = 0;
    }

    /// <summary>收货 —— 只能由父聚合调用</summary>
    internal void Receive(decimal quantity, Guid locationId)
    {
        Check.Positive(quantity, nameof(quantity));
        if (ReceivedQuantity + quantity > ExpectedQuantity)
            throw new BusinessException(WmsErrorCodes.OverReceive);

        ReceivedQuantity += quantity;
        LocationId = locationId;
    }
}
关键设计

构造器和 Receive 方法都是 internal —— 只有同程序集（Domain 项目内部）才能调用。这意味着 InboundOrder 调得到，而 AppService 调不到。这是聚合封装的硬约束：外部只能通过聚合根操作聚合内的实体。

04出库单与状态机

结构与入库单完全对称，但状态机多了一个 Allocated（已分配） 阶段 —— 这是 WMS 出库与入库最大的区别。

Draft草稿
→
Confirmed已确认
→
Allocated已分配库存
→
Picking拣货中
→
Shipped已发货
→
Completed已完成
为什么需要 Allocated 阶段

如果没有「分配」这一步，两个出库单会同时看到同一批库存都显示「可用」，等双双确认后才发现货不够。Allocate 的作用就是把库存「锁定」下来 —— 增加 Inventory.AllocatedQuantity，使 AvailableQuantity（= 在库量 − 已分配量）相应减少。

public class OutboundOrder : FullAuditedAggregateRoot<Guid>
{
    public string OrderNo { get; private set; }
    public Guid WarehouseId { get; private set; }
    public OutboundType Type { get; private set; }        // 销售/领料/调拨/报废
    public string SourceOrderNo { get; private set; }
    public OutboundOrderStatus Status { get; private set; }

    private readonly List<OutboundOrderLine> _lines = new();
    public IReadOnlyCollection<OutboundOrderLine> Lines => _lines.AsReadOnly();

    // 状态机：Draft → Confirmed → Allocated → Picking → Shipped → Completed
    // 关键领域方法：Confirm / Allocate / StartPicking / Ship / Complete / Cancel

    public void Allocate(Guid lineId, Guid inventoryId, decimal quantity)
    {
        if (Status != OutboundOrderStatus.Confirmed)
            throw new BusinessException(WmsErrorCodes.InvalidStatusTransition);

        var line = _lines.First(x => x.Id == lineId);

        line.Allocate(inventoryId, quantity);       // 记录分配到哪条库存记录
    }
}

OutboundOrderLine 出库单行

出库行比入库行多两个字段：AllocatedQuantity（已分配量）和 InventoryId（锁定的是哪条库存记录）。

public class OutboundOrderLine : Entity<Guid>
{
    public Guid OutboundOrderId { get; private set; }
    public Guid MaterialId { get; private set; }
    public decimal RequiredQuantity { get; private set; }   // 需求
    public decimal AllocatedQuantity { get; private set; }  // 已分配
    public decimal ShippedQuantity { get; private set; }    // 已发货

    }
}

05库存一致性模型

这是最需要你拍板的地方。共有三个选项：

方案说明适用选择
A. 纯流水只存所有出入库流水，库存 = SUM(入) − SUM(出)数据量小、查询少不推荐
B. 流水 + 实时库存表流水做账，另有 Inventory 表冗余实时量绝大多数 WMS推荐
C. 只存实时库存无流水不可追溯不要用

Inventory 实时库存

D:\yudao\abp\Acme.Learn\src\Acme.Learn.Domain\Wms\Inventories\Inventory.cs 
public class Inventory : FullAuditedAggregateRoot<Guid>
{
    public Guid WarehouseId { get; private set; }
    public Guid LocationId { get; private set; }
    public Guid MaterialId { get; private set; }
    public string BatchNo { get; private set; }             // 批次号（可空）
    public decimal Quantity { get; private set; }            // 在库量
    public decimal AllocatedQuantity { get; private set; }   // 已分配（被出库单锁定）

    public decimal AvailableQuantity => Quantity - AllocatedQuantity;   // 计算属性

    // ── 领域方法 ──
    public void Allocate(decimal quantity)
    {
        Check.Positive(quantity, nameof(quantity));
        if (quantity > AvailableQuantity)                        // 不变量：不能超可用量
            throw new BusinessException(WmsErrorCodes.InsufficientStock);
        AllocatedQuantity += quantity;
    }
}
关键在 AvailableQuantity

出库分配时必须校验可用量，而不是在库量。AvailableQuantity 作为计算属性（无 setter、不落库），恰好表达了「在库量减去已被其他单据锁定的部分」这一业务语义。

基类选择的业务含义

注意流水表继承的是 CreationAuditedAggregateRoot，而不是 FullAuditedAggregateRoot。两者的差异在于前者没有软删除，也没有修改审计 —— 因为流水只能追加，不能改也不能删。这是「基类选择体现业务语义」的典型案例，也是 ABP 相比 MyBatis-Plus 的一个便利之处。

ABP 基类带来什么适用
AggregateRoot<Guid>只有 Id + 并发戳纯业务对象
CreationAuditedAggregateRoot<Guid>+ 创建人/创建时间流水、日志
AuditedAggregateRoot<Guid>+ 修改人/修改时间不需软删的业务数据
FullAuditedAggregateRoot<Guid>+ 软删除（IsDeleted）主数据、单据（默认选择）

为什么是领域服务而不是 AppService

因为它需要跨聚合读写，而且全是纯业务规则 —— 既不含 DTO 转换，也不含权限校验。放到 Application 层，既会让领域规则污染应用层，也会让它无法被其他领域服务复用。

    private readonly IInboundOrderRepository _orderRepo;

    /// <summary>生成单号：IN + 日期 + 4位流水</summary>
    public async Task<string> GenerateOrderNoAsync()
    {
        var datePart = DateTime.Now.ToString("yyyyMMdd");
        var count = await _orderRepo.CountAsync(
            x => x.OrderNo.StartsWith($"IN{datePart}"));
        return $"IN{datePart}{(count + 1):D4}";
    }
}
并发缺陷警告

上面的实现存在并发问题 —— 两个请求可能拿到同一个 count，从而生成重复单号。生产环境必须改用数据库序列或 Redis 原子自增。

这恰好划出了「领域服务承载业务规则」与「基础设施问题」之间的边界：并发控制属于基础设施，不该硬塞进领域服务。正确做法是在领域服务里注入一个 IOrderNumberGenerator 抽象，实现交给基础设施层。

@Injectable({ providedIn: 'root' }) 是什么

先看它长什么样，再逐部分拆开：

@Injectable({ providedIn: 'root' })
export class WarehouseService { }

这行装饰器回答的是一个很具体的问题：这个服务类由谁创建、在哪里创建、创建几个实例？ Angular 的依赖注入容器需要先知道这些信息，才能把它交给需要它的组件。

拆成两部分看：

  • @Injectable() —— 告诉 Angular「这个类可以被注入到别处」，相当于给类打上「可被容器管理」的标记；没有它，即使写了 providedIn 也不会生效。
  • providedIn: 'root' —— 指定注册到根注入器。这样一来整个应用共享同一个实例（单例），任何组件注入它拿到的都是同一份。

providedIn:'root' 的 root 指什么？

它指的是根注入器（Root Injector），而不是「根组件」。这两个是不同的东西：

  • 根组件 —— 就是 AppComponent，页面上的根 DOM 节点；
  • 根注入器 —— 应用的顶层 DI 容器，在 Angular 启动时创建，providedIn:'root' 的服务就挂在它下面。

关键在于，根注入器位于根组件之上 —— 所有组件（包括根组件自己）都从它那里取服务：

一句话总结

@Injectable({providedIn:'root'}) ≈ Spring 的 @Service；@Component ≈ Spring 的 @RestController + 模板。前者管 DI 注册，后者管 UI 定义，两者互不替代。

selector —— 这个组件在 HTML 里叫什么

selector: 'app-warehouse-table' 定义了组件的标签名。父组件模板里写 <app-warehouse-table></app-warehouse-table>，Angular 就知道要把这个位置渲染成子组件。

类比 Spring，它像 @RequestMapping("/warehouse") —— 都是「让外界能找到我」的标识符。区别在于 Spring 找的是 HTTP 路径，Angular 找的是 HTML 标签。

providers —— 这个组件负责提供哪些服务

父组件的 providers: [WarehouseService]，含义是：父组件自己创建一个 WarehouseService 实例，供自己及子孙组件使用。

这是 Angular 和 Spring 差别最大的地方。Spring 只有一个全局容器，Bean 定义在哪里都一样；Angular 的容器是一棵组件树，每个组件都是一个小注入器。providers 写在哪个组件上，实例就在哪里创建，作用域也到哪里为止。

所以父组件只要写了 providers，子组件就什么都不用写，只要在构造函数里声明参数就能拿到 —— Angular 会自动向上查找，最终在父组件那一层找到实例，父子共享同一个：

constructor(private svc: WarehouseService) { }   // 父：拿到自己 providers 里的那个
constructor(private svc: WarehouseService) { }   // 子：向上查找，拿到同一个 ✓

反过来说，如果子组件也写一遍 providers: [WarehouseService]，它就会创建一个新的实例，父子各持一份，数据不再共享。这不会报错，但会变成一个很难查的静默 bug —— 详细展开见后文「层级注入器」一节。

inputs —— 这个组件对外接收什么数据

子组件写的 inputs: ['data']，含义是：允许父组件通过 [data]="..." 往我这里传值，传进来的值会绑定到子组件的 data 字段上。

父组件模板里的 [data]="items" 与之配套：方括号代表数据从父流向子。子组件如果不声明 inputs，父组件就没法写这个方括号，双方对不上。

// ── 子组件：接收什么，写在元数据里 ──
@Component({
  selector: 'app-warehouse-table',
  inputs: ['data'],
})
export class WarehouseTableComponent {
  data: WarehouseDto[] = [];        // ← 字段仍要自己定义，否则运行时是 undefined
}

// ── 父组件模板：把数据传下去 ──
<app-warehouse-table [data]="items"></app-warehouse-table>
写法方向含义
[data]="items"父 → 子方括号 = 输入绑定，把父的 items 传进子的 data
(saved)="onSaved($event)"子 → 父圆括号 = 输出绑定，子组件 emit() 什么，这里就收到什么
[(ngModel)]双向方 + 圆 = 双向绑定

这三种绑定基本覆盖了日常的组件通信。子组件要往外发消息，就在自己身上声明 @Output() saved = new EventEmitter<string>()，需要时 this.saved.emit(id)，父组件用圆括号接住。至于兄弟组件、或者隔了好几层的组件，没有直接相邻的父子关系可走，有两条路：把 state 提到它们的共同父组件，再由父组件用 @Input 分发、用 @Output 收消息；或者注入同一个 service 中转（作用域由 providers 决定）。

// ── 子 → 父：子组件声明事件，父组件用圆括号接住 ──
@Component({ selector: 'app-warehouse-table' })
export class WarehouseTableComponent {
  @Output() saved = new EventEmitter<string>();

  save(id: string) {
    // ...调用生成出来的 API 保存
    this.saved.emit(id);                    // 把消息抛给父组件
  }
}

// ── 父组件模板：方括号传下去，圆括号接回来 ──
<app-warehouse-table
  [data]="items"
  (saved)="onSaved($event)">
</app-warehouse-table>
// onSaved(id) 里通常是刷新列表

// ── 兄弟 / 跨层级：注入同一个 service 中转，不必层层往下传 ──
@Injectable()                                  // 不写 providedIn，作用域交给 providers 决定
export class TableSelectionService {
  selectedId = '';
}

@Component({
  selector: 'app-warehouse-list',
  providers: [TableSelectionService],       // ← 在共同祖先上声明一次
})
export class WarehouseListComponent { }

// 它下面任意层级的组件注入 TableSelectionService，拿到的都是同一份
两个组件要共享同一份数据：状态提升

当两个组件需要显示同一份数据、并且一起更新时（比如表格和分页器共用当前页码），做法是把这份数据「向上」提到它们共同的那层父组件里，再由父组件分发给两边 —— 这就是状态提升（lifting state up）。

对照 React：React 把 state 提上去后，用 count={count} 往下传值，同时把 handleClick 当 prop 往下传函数。Angular 前半段一样（[data]="items" 往下传），后半段不同 —— 不传函数，而是让子组件 emit，父组件在模板里用 (saved)="onSaved($event)" 绑定。两者本质是同一个模式：数据往下流，事件往上报。

所以 Angular 里的选择比 React 简单：数据只涉及一对父子时，直接 @Input / @Output，压根不用谈「提升」；需要两个兄弟共用、层级又浅时，把 state 提到共同父组件；层级深、或同一份数据被多处使用时，直接用 service —— Angular 有 DI，service 能注入到任意层级，不必像 React 那样为了绕开层层传 props 才动用 Context（Angular 的 service + providers 就对应 React 的 Context）。

inputs 是老写法，新代码用 @Input()

inputs: ['data'] 是在元数据里批量声明的旧语法，既没有类型提示，也不能设默认值。现代 Angular 一律改用装饰器：

@Input() data: WarehouseDto[] = [];   // 推荐：自带声明 + 类型 + 默认值

注意：inputs: ['data'] 只是「允许父组件传值」的声明，子组件仍然要在类里定义 data 字段，否则运行时它是 undefined。@Input() 写法则把这两步合成了一步。

三个字段的分工，一句话记住
  • selector —— 解决「怎么被引用」（HTML 标签名）
  • providers —— 解决「依赖从哪来」（实例在哪创建、作用域多大）
  • inputs —— 解决「数据怎么进来」（父组件传值的入口）

三者互不相关：providers 管依赖注入，inputs 管数据绑定，这是两条独立的线，别混在一起理解。

关键辨析：共享的是「代码」，不是「实例」

这一点正好和前面的 providers 对照，别混：

先说清前提：写在哪个组件里，谁才能用

这一段的前提要先说清：谁需要 ListService、providers 该写在哪个组件上。回到前面那对父子组件 —— 父组件是 WarehouseListComponent（列表页），子组件是 WarehouseTableComponent（表格）。假设两个组件都要用 ListService，而它没有 providedIn。

✓ 写在父组件（推荐）

  selector: 'app-warehouse-list',
  providers: [ListService],          // ← 只有这里声明
})

  constructor(private listService: ListService) { }

  constructor(private listService: ListService) { }

✗ 写在子组件（用不了）

  constructor(private listService: ListService) { }
  // ❌ 向上找到 Root Injector，两个都没有 → 报错
}

// 子组件：表格 —— 在这里声明管不到父组件

  selector: 'app-warehouse-table',
  providers: [ListService],          // ← 只能自己用
})

为什么写在父组件里，子组件就能用？因为 Angular 查找依赖是沿组件树向上冒泡的。子组件要 ListService 时，先看自己的 providers（没有），再往上看父组件的（找到了），于是就用父组件创建的那一份。所以声明的位置决定了「谁能用」：写在父组件，父组件及其所有子孙都能用；写在子组件，只有子组件自己（及其子孙）能用，父组件用不到。

判断口诀

谁用谁声明，往上写一层更保险。如果只有某个组件用，就写在它自己身上；如果父组件和子组件都要用（并且需要共享同一份数据），就写在它们共同的那个父组件上。

这就是 Abp 的 ListService 需要注意的地方

Abp 自动生成的 ListService 就没有 providedIn: 'root'，所以必须在组件的 providers 里手动声明，否则会报错。这也是它和其他服务唯一的区别 —— 记住这一条就够了。

落到 WMS 场景：列表页父组件 WarehouseListComponent 声明一次，它下面的表格子组件就能共用同一份分页状态。「分页与 ListService」一节会再结合真实代码讲一遍。

  templateUrl: './inbound-order-list.component.html',
  imports: [CommonModule, LocalizationPipe, PermissionDirective],
})
export class InboundOrderListComponent implements OnInit {
  // 注入生成出来的 service（不是手写的）
  private inboundOrderService = inject(InboundOrderService);

  orders: InboundOrderDto[] = [];
  totalCount = 0;
  loading = false;

  // 把枚举挂到组件上，模板里就能直接用 Status.Draft（否则模板访问不到）
  readonly Status = InboundOrderStatus;

  ngOnInit() {
    this.load();
  }

  load() {
    this.loading = true;
    this.inboundOrderService
      .getList({ maxResultCount: 10, skipCount: 0 })
      .subscribe(res => {
        this.orders = res.items ?? [];
        this.totalCount = res.totalCount ?? 0;
        this.loading = false;
      });
  }

  // ── 业务操作：全部调用生成的 API，不写任何业务规则 ──
  confirm(id: string) {
    this.inboundOrderService.confirm(id).subscribe(() => {
      this.load();          // 重新加载（状态变了）
    });
  }

  // 按钮能不能点 —— 复刻后端状态机（前端只做「显隐」，不做「校验」）
  canConfirm(order: InboundOrderDto): boolean {
    return order.status === InboundOrderStatus.Draft;
  }

  canReceive(order: InboundOrderDto): boolean {
    return order.status === InboundOrderStatus.Confirmed
        || order.status === InboundOrderStatus.Receiving;
  }
}

10设计陷阱与检查清单

最容易设计错的四个地方

陷阱 1

把单据行独立成聚合根。 这样就会失去「一张单不能有重复物料」这一不变量的保证 —— 因为校验需要跨聚合查询，而这种查询在并发下并不可靠。

陷阱 2

把 Material 对象塞进 InboundOrderLine。 也就是写成 public Material Material { get; set; }。这会模糊聚合边界，使「一次事务只改一个聚合」的约束失效。

陷阱 3

把库存加减写在 AppService 里。 库存的变化规则（可用量校验、批次维度、流水记录）属于领域层，而不属于应用层。写在 AppService 里，会导致这些规则无法被其他场景复用。

陷阱 4

给状态字段留公开 setter，或者让 DTO 也带一个同名的状态字段。 留公开 setter，自动映射器就能绕过领域方法直接改状态，规则形同虚设；而 DTO 再带一个同名的 IsActive，就变成一个名字承担两种语义 —— 实体里是事实（现在是不是启用），DTO 里是指令（应该被改成什么）。混在同一个名字下，读代码的人必然串。

做法：状态字段 private set；DTO 里不放状态字段；启用/停用做成独立接口（POST /api/app/warehouse/{id}/activate）—— 用动词表达指令，用布尔描述事实，两者分开，混淆就没有立足点。

11关键设计问答

Q1一张入库单能不能跨仓库？

不能。 WarehouseId 放在单头上。跨仓库属于调拨业务，应该拆成「出库单 + 入库单」两张单据，而不是在一张单上写两个仓库。

这符合「一次事务只改一个聚合」的原则 —— 跨仓库落库必然要修改两个仓库的库存，天然违反聚合边界。

Q2批号（BatchNo）放在哪一层？

放在库存（Inventory）和单据行上，不放在物料主数据上。

物料只声明「是否批次管理」（IsBatchManaged 开关），具体的批号则属于业务运行数据。这正是「主数据描述类型，业务数据描述实例」的划分。

Q3要不要做库存预留（Allocated）？

要。 否则两个出库单会同时抢同一批货。

AllocatedQuantity 就是为此而存在的：出库单确认时分配（Allocate），发货完成时扣减（Decrease）。在这中间的一段时间里，库存被「锁定」，AvailableQuantity 相应减少，其他单据就抢不到了。

Q4收货时库位怎么定？

有两种模式：① 在单头上指定（简单）　② 收货时人工指定 / 系统推荐（真实 WMS）

本设计采用的是行级 LocationId，两种模式都能支持。如果要做「系统推荐库位」，那只是 InventoryManager 里的一个算法方法，属于领域服务。

Q5Inventory 表会不会成为热点？

会。 同一个「库位 + 物料 + 批次」的记录会被高频更新，单行锁会成为瓶颈。

生产级 WMS 通常按「库位 + 物料 + 批次」分片，或者用 Redis 做缓存加异步落库。但你现在是在学框架，用最简单的实现即可 —— 先把领域模型跑通，性能优化是后面的事。

设计顺序

一句话总结

这个 WMS 的核心不是表，而是 两个状态机（入库单、出库单）加上一个库存一致性模型。设计顺序应该是：画单据状态机 → 确定库存的加减时机 → 定聚合边界 → 最后才轮到写实体类。
