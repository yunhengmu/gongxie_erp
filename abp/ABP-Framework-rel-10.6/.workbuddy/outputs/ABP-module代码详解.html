ABP Framework rel-10.6 · module 详解

module 代码到底是什么：以 identity 模块为标本

一个 ABP 应用模块的完整解剖——物理骨架、两个描述文件、19 个项目、真实依赖链、前端变体、以及模块类到底在做什么。所有数据取自 D:\yudao\abp\ABP-Framework-rel-10.6\modules\identity 实际源码。

先纠正一个前提：modules\ 是让你「读」的，不是让你「写」的。

你的项目里引用的是编译好的 NuGet / npm 包——module 的源码根本不会出现在你的项目里。改它没有意义，升级时会被覆盖。

准确的表述是：约 90% 的「参考阅读」在 modules\，而「编写」在你自己的项目里（用 abp new 生成，结构同 templates\app\）。

01module 的物理骨架

打开任意一个模块（以 blogging 为例），顶层永远是这几个东西：

D:\yudao\abp\ABP-Framework-rel-10.6\modules\blogging\

├── test\       ← 各层对应的测试项目
├── app\        ← 本地调试宿主（一个能跑起来的小应用，把这模块装进去）

├── NuGet.md

├── Volo.Blogging.abpsln        ← ABP Studio 解决方案描述

不同模块的骨架会有增删，对照如下：

模块顶层目录特点

「app」和「host」是什么？它们是把这个模块装进去跑起来的调试宿主。因为模块本身是个类库，不能直接 dotnet run。比如 blogging 的 app\Volo.BloggingTestApp\ 就是个 Razor Pages 小应用，你可以打开它看效果。这也是「模块可独立开发」的体现——每个模块自带一个最小可运行环境。

02两个描述文件：.abpmdl 与 .abppkg

这两个文件在普通 .NET 项目里没有，是 ABP 特有的元数据，用于工具链（主要是 ABP Studio）。

.abpmdl —— 模块清单

位于模块根目录，列出这个模块包含的所有包项目。blogging 的真实内容（节选）：

  "packages": {
    "Volo.Blogging.Domain": {
      "path": "src/Volo.Blogging.Domain/Volo.Blogging.Domain.abppkg",
      "folder": "src"
    },
    "Volo.Blogging.Application": {

作用：告诉工具「这个模块由哪些包组成、分别在哪个目录」。ABP Studio 靠它来画模块依赖图、做可视化。

每个项目目录下有一个，内容极简：

关键观察：6 个前端项目，但后端只有 1 套。这就是上一轮说过的「后端一套、前端多套」。你的项目只会引用其中一个前端项目（或对 Angular 而言是 npm 包），其余不需要。

项目内的目录规律：类文件不在项目根，而在镜像命名空间的目录下。例如：

src\Volo.Abp.Identity.Application\Volo\Abp\Identity\AbpIdentityApplicationModule.cs
                                    └──────┬──────┘
                                  镜像命名空间 Volo.Abp.Identity

所以看到 Volo\Abp\Identity\ 这样的深层目录不要意外——那是 C# 的命名空间目录惯例。

04真实依赖链（这是 module 代码的骨架）

下面是从 identity 各模块类的 [DependsOn] 实际读出来的数据。这张表就是 module 的架构真相：

AbpIdentityDomainSharedModuleAbpUsersDomainShared、AbpValidation、AbpFeatures
AbpIdentityDomainModuleAbpDddDomain、Domain.Shared、AbpUsersDomain、Mapperly
AbpIdentityApplicationContractsModuleDomain.Shared、AbpUsersAbstraction、AbpAuthorization、PermissionManagement.Contracts
AbpIdentityApplicationModuleDomain、Application.Contracts、Mapperly、PermissionManagement.Application
AbpIdentityHttpApiModuleApplication.Contracts + AbpAspNetCoreMvc　不依赖 Application

一条贯穿全表的铁律：所有「消费者」——HttpApi、HttpApi.Client、Web、Blazor——清一色只依赖 Application.Contracts，没有任何一个依赖 Application。

只有 Application 自己同时依赖 Domain（拿实体和仓储）和 Application.Contracts（实现接口）。

这就是「接口与实现分离」在模块里的落地：契约层是唯一的稳定边界，消费者只认契约。

06模块类在做什么

模块类（*Module.cs）是每个项目的入口。它看起来只是几行 [DependsOn]，但里面藏着这个项目全部的装配逻辑。以 AbpIdentityWebModule 为例，三个生命周期方法各司其职：

方法做什么为什么放这里
PreConfigureServices • AddAssemblyResource(...) —— 把这个程序集的本地化资源接进框架
• AddApplicationPartIfNotExists(...) —— 把本程序集的 Razor Pages 注册进宿主 MVC 		Pre 阶段执行得最早，此时还没构建容器，适合「告诉框架我要参与」
ConfigureServices • AbpNavigationOptions.MenuContributors.Add(...) —— 注册菜单贡献者
• FileSets.AddEmbedded<>(...) —— 把 wwwroot 等静态资源挂到虚拟文件系统
• AddMapperlyObjectMapper<>(...) —— 注册对象映射
• RazorPagesOptions.Conventions.AuthorizePage("/Identity/Users/Index", IdentityPermissions.Users.Default) —— 逐页声明权限
• AbpPageToolbarOptions —— 给列表页加「新建」按钮，并绑定 requiredPolicyName
• DynamicJavaScriptProxyOptions.DisableModule(...) —— 关掉不需要的动态 JS 代理 		主体配置阶段，DI 容器正在构建
PostConfigureServices ModuleExtensionConfigurationHelper.ApplyEntityConfigurationToUi(...) —— 把「实体扩展配置」应用到 UI 表单上 Post 阶段，等所有模块都配置完再收尾——因为要确保其它模块的扩展已就位

源码（节选）

modules\identity\src\Volo.Abp.Identity.Web\AbpIdentityWebModule.cs[DependsOn(typeof(AbpIdentityApplicationContractsModule))]   // ← 只依赖契约
[DependsOn(typeof(AbpPermissionManagementWebModule))]
[DependsOn(typeof(AbpAspNetCoreMvcUiThemeSharedModule))]
public class AbpIdentityWebModule : AbpModule
{
    public override void ConfigureServices(ServiceConfigurationContext context)
    {
        // 1. 菜单
        Configure<AbpNavigationOptions>(options =>
            options.MenuContributors.Add(new AbpIdentityWebMainMenuContributor()));

        // 2. 静态资源进虚拟文件系统
        Configure<AbpVirtualFileSystemOptions>(options =>
            options.FileSets.AddEmbedded<AbpIdentityWebModule>());

        // 3. 对象映射
        context.Services.AddMapperlyObjectMapper<AbpIdentityWebModule>();

        // 4. ★ 逐页声明权限 —— 页面级鉴权
        Configure<RazorPagesOptions>(options =>
        {
            options.Conventions.AuthorizePage("/Identity/Users/Index",       IdentityPermissions.Users.Default);
            options.Conventions.AuthorizePage("/Identity/Users/CreateModal", IdentityPermissions.Users.Create);
            options.Conventions.AuthorizePage("/Identity/Users/EditModal",   IdentityPermissions.Users.Update);
        });

        // 5. 列表页工具栏按钮 + 权限
        Configure<AbpPageToolbarOptions>(options =>
            options.Configure<Users.IndexModel>(toolbar =>
                toolbar.AddButton(
                    LocalizableString.Create<IdentityResource>("NewUser"),
                    icon: "plus",
                    name: "CreateUser",
                    requiredPolicyName: IdentityPermissions.Users.Create)));
    }
}

这解释了一个你可能疑惑的事：为什么模块的权限「自动就生效了」？因为权限不是靠页面里写 if 判断，而是在模块类里集中声明——AuthorizePage 管页面能不能进，AddButton 的 requiredPolicyName 管按钮显不显示，方法上的 [Authorize] 管接口能不能调。三处都指向同一个权限常量。

07模块如何被装配进项目

模块写完了，怎么让它在一个应用里生效？靠依赖链传导——你只需要在自己的宿主模块里 DependsOn 一次，整条链会自动装配。

// 你自己项目的宿主模块（比如 MyApp.HttpApi.Host 的模块类）
[DependsOn(
    typeof(AbpIdentityApplicationModule),      // ← 引入服务端实现
    typeof(AbpIdentityEntityFrameworkCoreModule),// ← 引入 EF 实现
    typeof(AbpIdentityHttpApiModule),          // ← 暴露 REST 接口
    typeof(AbpIdentityWebModule)               // ← 引入 MVC 界面（如果用 MVC）
)]
public class MyAppHttpApiHostModule : AbpModule { }

框架启动时会：

  1. 读你的 [DependsOn]，递归收集所有间接依赖（FillModules）
  2. 按依赖关系拓扑排序，保证被依赖的先初始化
  3. 依次调用每个模块的 PreConfigureServices → ConfigureServices → PostConfigureServices

这就是为什么「装了 Identity 模块，用户管理和角色管理页面就直接有了」——页面、权限、菜单、REST 接口全在模块里配好了，你只是把它接了进来。

注意 Angular 不一样：Angular 侧的「装配」不走 [DependsOn]，而是走 app.config.ts 的 provider + app.routes.ts 的 loadChildren。这是两个体系，别混。

08你该怎么用 modules 学代码

既然不能改，那读的时候带着什么问题去读？给你四个具体任务：

  1. 学「一个业务功能怎么落地」 → 读 blogging 的 Post 垂直切片（实体→仓储→DTO→AppService→控制器），共 16 个文件。这是全仓库最干净的范例。
  2. 学「一个功能怎么拆成 19 个项目」 → 读 identity 的 src\ 目录列表 + 各 .abppkg 的 role。重点理解「为什么前端要拆成 6 个项目」。
  3. 学「模块类怎么写」 → 打开 AbpIdentityWebModule.cs，看它是怎么把菜单、静态资源、对象映射、页面权限、工具栏按钮一次性配完的。你写自己项目的 Web 层时，照这个结构抄。
  4. 学「页面长什么样」 → 读 Volo.Abp.Identity.Web\Pages\Identity\Users\ 下的 Index + CreateModal + EditModal 三件套（MVC），或 npm\ng-packs\packages\identity\ 的 users 组件（Angular）。二者对照看，能明白 ABP 的页面模式是技术栈无关的。

最后强调一次边界：读 modules → 抄它的结构和方法；写代码 → 在你自己的项目里。如果你确实需要改模块行为，用 ABP 的三个正规手段：配置（Configure<XxxOptions>）、替换服务（[Dependency(ReplaceServices = true)]）、扩展点（贡献者模式，如 MenuContributors）。不要去改 modules 目录里的源码。
