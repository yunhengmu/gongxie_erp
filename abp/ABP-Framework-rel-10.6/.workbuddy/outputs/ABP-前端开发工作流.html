00先校准：你的模型对不对

你提出的流程是：知道后端接口 → 在某某文件配置请求函数 → 配置页面组件 → 按模块找对应目录 → 分析业务流 → 设计组件通信 → 写代码。

主线是对的，有 1 处认知偏差、1 处顺序颠倒、3 步缺失：

你的步骤校准结果说明
知道后端接口 对 但不只是「知道」，而是后端 Application.Contracts 必须已经就绪——因为下一步是从它自动生成前端代码
在某某文件配置请求函数 需修正 不是手写，是生成的。abp generate-proxy 扫描后端契约，自动产出 src/app/proxy/**/*.service.ts。手写只在极少数场景需要
按模块找到对应目录 顺序要提前 应排在「配置页面组件」之前。先定好文件落哪儿，再往里填内容
分析业务流 对 它的产出是「页面该拆成几个组件」的决策，不只是理解业务
设计组件通信 对 但 ABP 的答案和通用 Angular 不同——主要靠 ListService 和 modal 内嵌表单，而不是层层 @Input
写代码 对 补一个收尾动作：权限绑定 + 本地化
遗漏 注册路由 不注册 *.routes.ts 并挂进 app.routes.ts，页面根本访问不到
遗漏 注册菜单 + 权限 ABP 的侧边栏菜单不是写 HTML，而是往 RoutesService 注册；且必须带 requiredPolicy，否则有权限的人看不见入口
遗漏 权限与本地化收尾 *abpPermission 控制按钮显隐、abpLocalization 处理多语言——这俩不做，功能算没完成

一句话总结偏差：你的模型里「请求函数」是一个需要你配置的东西；而在 ABP 里它是后端契约的镜像产物。这意味着前端工作的起点不是「我要调哪个 URL」，而是「后端有哪些 DTO 和 AppService 接口」。

01① 确认后端契约（前提）

打开后端项目，确认这几样东西已存在。它们是前端一切代码的来源：

要确认的位置为什么前端需要
应用服务接口*.Application.Contracts/Products/IProductAppService.cs决定生成哪些请求函数、函数名是什么
DTO 定义同目录 ProductDto.cs、CreateProductDto.cs…决定前端拿到什么字段、字段类型
权限常量*.Application.Contracts/Permissions/*Permissions.cs决定前端路由与按钮的 requiredPolicy / *abpPermission 该填什么字符串
本地化 key*.Domain.Shared/Localization/<项目>/*.json决定界面文案的 key 名

契约即前端的「设计稿」。后端接口名 GetListAsync → 前端生成 getList()；后端 CreateProductDto → 前端生成同名 interface。命名规范（GetAsync / GetListAsync / CreateAsync / UpdateAsync / DeleteAsync）不只是后端整洁，它直接决定了前端 API 的手感。

02② 生成请求函数（这一步是"生成"，不是"配置"）

命令

abp generate-proxy -t ng -m MyProjectName -u https://localhost:44305

产出（真实样例，来自框架自带 identity 包）

npm/ng-packs/packages/identity/proxy/src/lib/proxy/identity/identity-role.service.tsimport { GetIdentityRolesInput, IdentityRoleCreateDto, IdentityRoleDto, IdentityRoleUpdateDto } from './models';
import { RestService } from '@abp/ng.core';
import { Injectable, inject } from '@angular/core';

@Injectable({ providedIn: 'root' })
export class IdentityRoleService {
  private restService = inject(RestService);
  apiName = 'AbpIdentity';   // 对应 environment.apis 里的键

  // 后端 IIdentityRoleAppService.GetListAsync → 这里 getList
  getList = (input: GetIdentityRolesInput) =>
    this.restService.request<any, PagedResultDto<IdentityRoleDto>>({
      method: 'GET',
      url: '/api/identity/roles',
      params: { filter: input.filter, sorting: input.sorting,
                skipCount: input.skipCount, maxResultCount: input.maxResultCount },
    }, { apiName: this.apiName });

  get = (id: string) => this.restService.request<any, IdentityRoleDto>({ method: 'GET', url: `/api/identity/roles/${id}` }, { apiName: this.apiName });
  create = (input: IdentityRoleCreateDto) => /* POST /api/identity/roles */ null;
  update = (id: string, input: IdentityRoleUpdateDto) => /* PUT  /api/identity/roles/${id} */ null;
  delete = (id: string) => /* DELETE /api/identity/roles/${id} */ null;
}

同时生成 models.ts，把后端 DTO 一比一翻译成 TypeScript 接口：

.../proxy/identity/models.ts（节选）export interface GetIdentityRolesInput extends PagedAndSortedResultRequestDto {
  filter?: string;
}

export interface IdentityRoleDto extends ExtensibleEntityDto<string> {
  name?: string;
  isDefault: boolean;
  isPublic: boolean;
  concurrencyStamp?: string;
}

为什么强烈建议用生成的、而不是手写？因为 RestService 不只是发 HTTP——它还负责：从 environment.apis[apiName] 解析 baseUrl、附加认证 token、把后端返回的错误码翻译成本地化提示、统一处理 loading 状态。ApiName 这个字符串就是「这个服务属于哪个后端」的声明，手写极易漏。

那「手写请求函数」什么时候用？

确实存在手写形态，出现在可复用模块里——因为模块不能假设宿主应用一定跑过 generate-proxy。模板给了一个标准写法：

templates/module/angular/projects/my-project-name/src/lib/services/my-project-name.service.ts@Injectable({ providedIn: 'root' })
export class MyProjectNameService {
  apiName = 'MyProjectName';

  constructor(private restService: RestService) {}

  sample() {
    return this.restService.request<void, any>(
      { method: 'GET', url: '/api/MyProjectName/sample' },
      { apiName: this.apiName }
    );
  }
}

注意它和生成版的差别：只多了服务类这层壳，内部机制完全一样——都是 RestService.request + apiName。所以你的理解「在某个文件里确定请求函数」方向没错，只是这个文件的定位是生成产物所在的 proxy/ 目录，而不是你新建的文件。

场景做法文件
业务应用（`templates/app`）生成src/app/proxy/**/*.service.ts（自动，勿手改）
可复用模块（`templates/module`）手写src/lib/services/xxx.service.ts

03③ 按模块规划目录（必须先做）

你说「按模块找到对应目录」——对，但要先建好目录再写代码。ABP Angular 的目录是按业务模块切分的，一个模块一个顶层目录：

angular/src/app/
├── app.routes.ts          # 根路由表：每个业务模块挂一条 loadChildren
├── route.provider.ts      # 菜单注册中心
├── products/              # ← 你的业务模块
│   ├── products.routes.ts     # 本模块子路由
│   ├── product.service.ts     # （可选）本模块自有的状态/辅助服务
│   ├── list/
│   │   ├── list.component.ts
│   │   ├── list.component.html
│   │   └── list.component.scss
│   └── create-edit/
│       ├── create-edit.component.ts
│       └── create-edit.component.html
└── proxy/                 # 生成产物，不手工编辑
    └── products/
        ├── product.service.ts
        └── models.ts

区分两个同名的 product.service.ts：proxy/products/ 下那个是生成的、只做 HTTP 转发；products/ 下那个是你写的业务侧服务，用来放跨组件共享的状态。混用会让代码迅速失控——这是新手最常见的坑。

补充一点：ABP 对「页面复杂到一定程度」的模块，会给每个组件配一组 defaults/ 配置（列定义、表单定义、工具栏动作），把「表格显示哪些列」变成数据而不是模板代码。identity 包就是这么做的：

npm/ng-packs/packages/identity/src/lib/
├── components/users/          # 页面组件
├── defaults/
│   ├── default-users-entity-props.ts    # 列表显示哪些列
│   ├── default-users-form-props.ts      # 表单显示哪些字段
│   ├── default-users-entity-actions.ts  # 行内操作按钮
│   └── default-users-toolbar-actions.ts # 工具栏按钮
├── enums/components.ts        # 组件标识枚举
└── tokens/extensions.token.ts # 扩展点注入令牌

一般业务从简单的 list/ + create-edit/ 起步就够了，等页面确实膨胀了再引入这套 defaults 机制。

04④ 注册路由（容易漏的第一步）

分两处写。先在模块内定义子路由：

angular/src/app/products/products.routes.tsimport { Routes } from '@angular/router';

export const productRoutes: Routes = [
  {
    path: '',
    loadComponent: () =>
      import('./list/list.component').then(m => m.ListComponent),
  },
];

再挂到根路由表（这里是 loadChildren 懒加载，模块级代码分割）：

angular/src/app/app.routes.tsexport const appRoutes: Routes = [
  { path: '', pathMatch: 'full', loadChildren: () => import('./home/home.routes').then(m => m.homeRoutes) },
  { path: 'account', loadChildren: () => import('@abp/ng.account').then(m => m.createRoutes()) },
  { path: 'identity', loadChildren: () => import('@abp/ng.identity').then(m => m.createRoutes()) },
  // ↓ 新增这一条
  { path: 'products', loadChildren: () => import('./products/products.routes').then(m => m.productRoutes) },
];

如果这一页需要权限守卫，可以像框架自带模块那样在路由 data 上声明（identity 包的真实写法）：

npm/ng-packs/packages/identity/src/lib/identity.routes.ts（节选）{
  path: 'users',
  component: ReplaceableRouteContainerComponent,
  data: {
    requiredPolicy: 'AbpIdentity.Users',   // 无此权限则进不来
    replaceableComponent: { key: eIdentityComponents.Users, defaultComponent: UsersComponent },
  },
  title: 'AbpIdentity::Users',
}

顶层还挂了 canActivate: [authGuard, permissionGuard]——authGuard 管「登录没」，permissionGuard 读 requiredPolicy 管「有权限没」。

05⑤ 注册菜单 + 权限（ABP 特有，最容易漏）

侧边栏菜单不是 HTML。ABP 的导航是运行时由 RoutesService 数据驱动的。不注册，页面即使能访问也不会出现在菜单里。

angular/src/app/route.provider.tsimport { eLayoutType, RoutesService } from '@abp/ng.core';

export const APP_ROUTE_PROVIDER = [
  { provide: APP_INITIALIZER, useFactory: configureRoutes, deps: [RoutesService], multi: true },
];

function configureRoutes(routesService: RoutesService) {
  return () => {
    routesService.add([
      {
        path: '/products',
        name: '::Menu:Products',              // :: 前缀 = 走本地化资源
        iconClass: 'fas fa-box',
        order: 10,
        layout: eLayoutType.application,
        requiredPolicy: 'MyProjectName.Products',  // ← 关键：权限
      },
    ]);
  };
}

模块模板用的是更现代的写法（provideAppInitializer），效果一致：

templates/module/angular/projects/my-project-name/config/src/providers/route.provider.tsexport const MY_PROJECT_NAME_ROUTE_PROVIDERS = [
  provideAppInitializer(() => { configureRoutes(); }),
];

export function configureRoutes() {
  const routesService = inject(RoutesService);
  routesService.add([
    {
      path: '/my-project-name',
      name: eMyProjectNameRouteNames.MyProjectName,
      iconClass: 'fas fa-book',
      layout: eLayoutType.application,
      order: 3,
    },
  ]);
}

权限字符串必须和后台权限常量逐字符一致。后端 MyProjectNamePermissions.Products.Default 的值是 "MyProjectName.Products"，前端写错一个大小写就会出现两种典型 bug：菜单不显示（requiredPolicy 不匹配），或页面能进但接口 403（@Authorize 不通过）。

06⑥ 分析业务流 → 决定页面拆分

这一步的产出不是「我懂了业务」，而是一张页面结构决策表。三步走：

  1. 列出用户在这个模块里的动作
    查列表、筛选、翻页、排序、新建、编辑、删除、批量操作、查看详情、导出……
  2. 判断每个动作的"重量"
    字段少（≤10 个）且无嵌套子表 → 弹窗足够；字段多、有分步、有子表编辑 → 需要独立页面
  3. 决定组件数与路由数
    大多数 CRUD 的答案是「1 个列表页路由 + 1 个弹窗组件（不占路由）」
业务特征页面拆分方案路由数
标准 CRUD，字段少列表页 + 同页 modal 弹窗做新增/编辑1
字段很多 / 有子集合编辑列表页 + 独立详情页（带 :id 路由）2
多步骤流程（如向导）列表页 + 分步路由（step/1、step/2）2+
只读报表 / 看板单页，多区块1

框架自带模块的答案基本都是第一行。identity 的用户管理就是一个列表组件里内嵌 modal 弹窗，连编辑表单都没拆成独立组件——它把「用户信息」「角色」两块做成 modal 里的两个 tab。这个选择很关键，它直接决定了第 7 步的通信设计。

07⑦ 设计组件通信（ABP 的答案和通用 Angular 不同）

通用 Angular 培训会教你「父传子 @Input、子传父 @Output、兄弟用 service」。ABP 在标准 CRUD 场景下刻意减少组件数量，所以通信设计反而更简单。四种模式按优先级：

模式用途ABP 的机制
① ListService
（首选）		 列表状态与查询的唯一真源 ListService 作为组件级 provider，管 filter/page/sortKey/sortOrder，任一变化自动触发 query$ 重发请求
② Modal 内嵌
（ABP 惯用）		 新增/编辑表单 不拆子组件，表单直接写在列表组件的 <ng-template #abpBody> 里，用 selected 变量切换「新增 vs 编辑」
③ @Input/@Output 确实拆了子组件时 ABP 组件普遍采用 [visible] + (visibleChange) 双向绑定风格，如 abp-modal
④ Service + signal 跨页面共享状态 放在第 3 步那个业务侧 product.service.ts 里，用 signal / BehaviorSubject

① ListService 是通信主干

看它的源码就明白为什么它是核心——每个 setter 都会自动触发重新查询：

npm/ng-packs/packages/core/src/lib/services/list.service.ts（节选）@Injectable()   // 注意：没有 providedIn:'root'，必须由组件 providers 提供
export class ListService<QueryParamsType = ABP.PageQueryParams> {
  set filter(value: string)   { this._filter = value;   this.get(); }
  set page(value: number)     { this._page = value;     this.get(); }
  set sortKey(value)          { this._sortKey = value;  this.get(); }
  set sortOrder(value)        { this._sortOrder = value;this.get(); }
  set maxResultCount(value)  { this._maxResultCount = value; this.get(); }

  // 关键：把 query$ 流和"调哪个接口"绑定，返回可直接渲染的结果流
  hookToQuery<T>(streamCreatorCallback: QueryStreamCreatorCallback<T, QueryParamsType>)
    : Observable<PagedResultDto<T>> {
    return this.query$.pipe(
      tap(() => this._requestStatus.next('loading')),
      switchMap(query => defer(() => streamCreatorCallback(query)).pipe(
        catchError(() => { this._requestStatus.next('error'); return EMPTY; }),
        tap(() => this._requestStatus.next('success')),
      )),
      shareReplay({ bufferSize: 1, refCount: true }),
    );
  }

  get = () => { this.resetPageWhenUnchanged(); this.next(); };  // 保存/删除后调它刷新
  next() { this._query$.next({
      filter: this._filter || undefined,
      maxResultCount: this._maxResultCount,
      skipCount: this._page * this._maxResultCount,
      sorting: this._sortOrder ? `${this._sortKey} ${this._sortOrder}` : undefined,
  } as any); }
}

两个易错点：① ListService 没有 providedIn: 'root'，必须在组件的 providers: [ListService] 里提供，否则多个列表页会互相串状态。② 保存/删除成功后不要手动重新拉数据，调 this.list.get() 即可——它会把 query 重新推一遍。

② Modal 内嵌 = 回避父子通信

identity 的用户页是个好例子：新增和编辑共用同一个 modal，靠 selected 有没有 id 来区分模式。这样不需要任何父子传参：

npm/ng-packs/packages/identity/src/lib/components/users/users.component.ts（节选）@Component({
  selector: 'abp-users',
  templateUrl: './users.component.html',
  providers: [ListService],        // ← 组件级提供，列表状态隔离
})
export class UsersComponent {
  protected readonly list = inject(ListService<GetIdentityUsersInput>);
  protected readonly service = inject(IdentityUserService);   // 生成的 proxy 服务
  protected readonly toasterService = inject(ToasterService);
  protected readonly confirmationService = inject(ConfirmationService);

  // 列表数据 = ListService.query$ 流 → 接口调用（switchMap 自动取消旧请求）
  readonly data = toSignal(
    this.list.hookToQuery(query => this.service.getList(query)),
    { initialValue: { items: [], totalCount: 0 } as PagedResultDto<IdentityUserDto> },
  );

  readonly isModalVisible = signal(false);
  readonly modalBusy = signal(false);
  selected?: IdentityUserDto;

  add()  { this.selected = {} as IdentityUserDto; this.openModal(); }      // 空对象 → 新增模式
  edit(id: string) {                                                              // 取到数据 → 编辑模式
    this.service.get(id).subscribe(user => { this.selected = user; this.openModal(); });
  }

  save() {
    if (!this.form.valid || this.modalBusy()) return;
    this.modalBusy.set(true);
    const { id } = this.selected || {};

    (id ? this.service.update(id, { ...this.selected, ...this.form.value })      // 有 id → 改
        : this.service.create(this.form.value))                                        // 无 id → 增
      .pipe(finalize(() => this.modalBusy.set(false)))
      .subscribe(() => {
        this.isModalVisible.set(false);
        this.toasterService.success('AbpUi::SavedSuccessfully');
        this.list.get();                                    // ← 刷新列表，不手动拉数据
      });
  }

  delete(id: string, userName: string) {
    this.confirmationService
      .warn('AbpIdentity::UserDeletionConfirmationMessage', 'AbpIdentity::AreYouSure',
            { messageLocalizationParams: [userName] })
      .subscribe(status => {
        if (status === Confirmation.Status.confirm) {
          this.service.delete(id).subscribe(() => {
            this.toasterService.success('AbpUi::DeletedSuccessfully');
            this.list.get();
          });
        }
      });
  }

  sort(data: any) {                                    // 表格排序 → 写回 ListService
    const { prop, dir } = data.sorts[0];
    this.list.sortKey = prop;
    this.list.sortOrder = dir;
  }
}

对应的模板——注意 abp-page、abp-extensible-table、abp-modal 这些现成组件承担了大部分通信工作：

npm/ng-packs/packages/identity/src/lib/components/users/users.component.html（节选）<abp-page [title]="'AbpIdentity::Users' | abpLocalization">
  <!-- 搜索框直接双向绑定 ListService.filter，改动即触发查询 -->
  <input type="search" [(ngModel)]="list.filter" />

  <!-- 表格把 ListService 和 data 一起接过去，分页/排序/列渲染全自动 -->
  <abp-extensible-table [data]="data().items" [recordsTotal]="data().totalCount" [list]="list" />

  <!-- 编辑弹窗内嵌在同组件，通过 signal 控制显隐 -->
  <abp-modal [visible]="isModalVisible()" (visibleChange)="isModalVisible.set($event)" [busy]="modalBusy()">
    <ng-template #abpHeader>
      <h3>{{ (selected?.id ? 'AbpIdentity::Edit' : 'AbpIdentity::NewUser') | abpLocalization }}</h3>
    </ng-template>
    <ng-template #abpBody>
      <form [formGroup]="form" (ngSubmit)="save()"> ... </form>
    </ng-template>
    <ng-template #abpFooter>
      <button abpClose>取消</button>
      <abp-button [disabled]="form?.invalid" (click)="save()">保存</abp-button>
    </ng-template>
  </abp-modal>
</abp-page>

看出规律了吗？ABP 用「现成组件 + 数据流」替代了手工的组件通信：搜索框 → ListService.filter → query$ → 接口 → data() 是一条单向数据流；弹窗显隐用 signal 局部控制。所以「设计组件通信」在 ABP 里的实际工作量，往往只是「决定用不用 ListService、弹窗放哪」。

④ 跨组件共享才需要自建 service

angular/src/app/products/product.service.ts（业务侧服务，非 proxy）@Injectable({ providedIn: 'root' })
export class ProductStateService {
  // Angular 17+ 用 signal，比 BehaviorSubject 更简洁
  private readonly _selectedIds = signal<string[]>([]);
  readonly selectedIds = this._selectedIds.asReadonly();

  toggle(id: string) {
    this._selectedIds.update(ids =>
      ids.includes(id) ? ids.filter(x => x !== id) : [...ids, id]);
  }
  clear() { this._selectedIds.set([]); }
}

09权限三重绑定与检查清单

同一个权限字符串，出现在三个地方

这是 ABP 权限体系最需要建立直觉的一点。后端只定义一次，前端要绑三处：

#位置写法作用
1路由 data.requiredPolicyrequiredPolicy: 'MyProjectName.Products'没权限直接进不了页面（permissionGuard 拦截）
2RoutesService.add 菜单项requiredPolicy: 'MyProjectName.Products'没权限侧边栏不显示入口
3模板按钮*abpPermission="'MyProjectName.Products.Create'"没权限按钮不渲染（结构性指令，会移除 DOM）

*abpPermission 的实现是订阅 PermissionService.getGrantedPolicy$()，返回 false 时就把视图清空——所以它是「不渲染」而非「禁用」，这对安全更友好：

npm/ng-packs/packages/core/src/lib/directives/permission.directive.ts（节选）@Directive({ selector: '[abpPermission]' })
export class PermissionDirective {
  readonly condition = input<string | undefined>(undefined, { alias: "abpPermission" });

  private check() {
    this.subscription = this.permissionService
      .getGrantedPolicy$(this.condition() || '')
      .pipe(distinctUntilChanged())
      .subscribe(isGranted => {
        this.vcRef.clear();                          // 先清空
        if (isGranted && this.templateRef) {
          this.vcRef.createEmbeddedView(this.templateRef);  // 有权限才渲染
        }
      });
  }
}

本地化 key 的两种写法

  • '::Menu:Products' —— 双冒号前缀表示「用默认资源」，key 是 Menu:Products
  • 'AbpIdentity::Users' —— 明确指定资源名是 AbpIdentity，key 是 Users

两者都通过 | abpLocalization 管道渲染。文案本体在后端 Localization/<项目>/zh-Hans.json 或前端 src/assets/i18n/*.json 里。
