## 澄清「@Reversible 标给谁」+ 修正说明书遗漏

用户问：`@Reversible` 标正函数还是冲账函数？两者怎么互相识别？

**结论**：标**正函数**（工具方法）。冲账函数**不标**。两套识别机制完全不同：

| | 正函数 | 冲账函数 |
|---|---|---|
| 机制 | 注解驱动（AOP 切点 `@annotation`） | 名字 + 接口驱动 |
| 谁识别 | `ReversibleLedgerAspect` | `ReversibleUndoServiceImpl` |
| 何时机 | 工具被调用时（入账） | 撤回那一刻 |
| 需要注解 | 必须 | **不标** |
| 需要接口 | 不需要 | 必须 `implements ReversibleTool` |

**桥梁 = 账本帧的 `reverse_bean` 字段**。三步：① 切面按注解拦截正函数；② 顺手算冲账 Bean 名
（`@Reversible.reverseBean()` 优先，空则 `resolveBeanName()` 按正函数所在类反查容器）写进帧；
③ 撤回时 `getBean(reverse_bean, ReversibleTool.class).reverse(ctx)`。

## 本轮新查证的事实

1. **`@Reversible` 标在 `BiFunction` 形态的 `apply()` 方法上**（不是自定义私有方法）。必须是 `public`
   —— Spring AOP 拦不到 private 方法，会静默失效。
2. **`ai_tool` 表两种名字形态都有现网先例**（`sql/mysql/ai-2026-04-16-传播违法.sql:412`）：
   - Bean 名形态：`directory_list` / `weather_query` / `user_profile_query`
   - `@Tool` 注解名形态：`ps_get_person_by_id`（Bean 名其实是 `personServiceImpl`）
   → 证实 Spring AI 的 `ToolCallbackResolver` 能按 `@Tool(name=)` 解析，不只是 Bean 名。
3. **`AiToolServiceImpl.validateToolNameExists()`（:75-80）**：后台新增工具时会调
   `toolCallbackResolver.resolve(name)` 校验，填错名字在后台就被拦，不会拖到运行期。

## 追加：用户提出架构质疑 —— `@Reversible` 应标业务层，不该标工具对接层

**用户观点（正确）**：`@Reversible` 应标在**业务方法**上，而不是 `DbQueryToolFunction` 这种 AI 工具对接层。

**为什么用户是对的**：
1. 同一业务操作有多个入口（AI 工具 / REST / 定时任务 / 其他 Service）。标在工具层会导致
   「入账与否取决于调用入口」—— 走 AI 才入账、走 REST 不入账，语义荒谬。
2. 可撤回的语义单元是**业务操作**，业务操作由业务方法定义，不是由 AI 工具定义。
3. 冲账函数天然属于业务层（要写反向分录、需要 Repository / 事务 / 领域规则），工具层没有这些。

**当前实现的硬约束（阻塞点）**：`ReversibleLedgerAspect.around()` 强制要求方法签名里有 `ToolContext`，
拿不到就 fail-fast 抛 `IllegalStateException`。业务方法没有 `ToolContext` → 直接标会炸。

**核实到的事实**：`trade_order` 全项目**只出现在 `DbQueryToolFunction.java` 一个文件里**。
项目只有 `ai`/`agent`/`erp`/`infra`/`system` 五个模块，**没有商城模块**，所以根本不存在 `TradeOrderService`。
`DbQueryToolFunction` 只有 `JdbcTemplate`（`:60`），直接在工具类里写 SQL（`:135`/`:197`）——
**工具层与数据访问层合一，没有业务层可标**。

**给出的方案（三层结构）**：
- AI 工具层：持 `ToolContext`，只做参数翻译 + 桥接，**不标** `@Reversible`
- 中间桥：新增 `ReversibleContextHolder`（TransmittableThreadLocal 存 messageId/conversationId/tenantId）
- 业务层：`@Reversible` 标这里，方法签名纯业务，零 AI 概念

两种落地：
- **方案 A（显式 scope）**：工具层 `ReversibleScope.callWith(toolContext, () -> service.xxx())`
- **方案 B（自动桥接切面）**：切点 `execution(* *(.., ToolContext))` 自动把上下文放进 Holder，
  工具层完全不用改，业务层 `@Reversible` 直接读 Holder

**重要修正我之前的判断**：我曾以「工具在 Flux 线程执行、TTL 不继承」为由否掉 ThreadLocal。
**这个理由在这里不适用** —— 桥接点是工具方法入口（那里既有 ToolContext、又已在工具执行线程上），
业务方法在同线程被普通 Java 调用，**ThreadLocal 100% 可用，不存在跨线程**。
之前担心的跨线程是「请求线程 → 工具线程」这一跳，而桥接是「工具线程内部」，两者不同。

**待用户确认是否落地**（新增 Holder + 桥接切面 + 改 `ReversibleLedgerAspect` 取上下文的两级来源）。

**顺带注意**：用户示例代码里的 `catch (Exception e) { return Response.error(...) }` 模式违反
「不得吞异常」原则（说明书 Step 5 的反例）。当前是只读统计不受影响，但同样的写法搬到写操作上
会让失败被当成成功入账。

## 追加：冲账函数归属分析（用户要求「结合它的性质分析冲账函数应该写在哪」）

**结论：业务层。** 不写框架层，不写 AI 工具层。

### 决定归属的三条性质

1. **运行在「撤回请求」线程，与 AI 调用链无关**。`ReversibleUndoServiceImpl.undo()` 由 REST 接口
   `/ai/chat/message/undo` 触发；此时没有 `ToolContext`，`ReversibleContextHolder` 也是空的
   （桥接切面拦的是带 `ToolContext` 参数的方法，撤回接口没有）。
   → 放 `tool/function/` 是逻辑错位：名字叫 Tool，却跟工具调用链无关。
   → 它的数据来源**只有** `ReversibleContext` 入参。
2. **必须能访问数据层**（追加反向分录、读原单据）。
   → 放 `framework/reversible/` 会让框架反向依赖业务 Mapper。
3. **由正函数定义（配对），且可能调其他 Service / Mapper**（联动库存、通知外部）。
   → 与正函数同业务包，配对关系一眼可见。

### 推荐形态：拆「业务动作」+「技术薄壳」两层

- **业务动作** `reverseXxx(...)` 写在**正函数所在的 Service 里** —— 最清楚「反向」的领域含义，
  可调 Mapper 与其他 Service。这才是「被正函数定义」的那个东西。
- **技术薄壳** `implements ReversibleTool` 独立成类（Adapter），只做
  `ReversibleContext` ⇄ 业务参数 的翻译，无业务逻辑。
- 原因：一个类只能有一个 `reverse()`；Service 有多个可撤方法时薄壳必须分开写。
- 包结构：薄壳与正函数**同包**（`service/wms/WmsReceiveService.java` +
  `service/wms/WmsReceiveReversibleAdapter.java`）。

### 五条硬性注意事项

1. 冲账函数内**不要**标 `@Reversible`（撤回本身不该再入账）
2. 幂等不用自己做 —— `casStatus` 保证同一帧只冲一次；但**非事务性副作用**（外部 HTTP / MQ）仍需自行考虑
3. 冲账链路内部一律用默认 `REQUIRED`，**不要** `REQUIRES_NEW` —— 外层已是
   `TransactionTemplate(REQUIRES_NEW)` 每帧一事务，内部再开新事务会破坏原子性
4. **不要依赖 `ReversibleContextHolder`** —— 撤回不经过 AI 链路，Holder 是空的
5. 逆序冲账由框架保证（`selectListByMessageId` 按 id 倒序）

**边际情况**：若将来把「撤回」也做成 AI 工具，Holder 里会有值，但那是**当前这条撤回消息**的
messageId，不是被撤回消息的 —— 冲账仍只能从 `ReversibleContext` 取数据。

### 发现的问题 1（已修）：`reverseBean` 指向非 `ReversibleTool` 的 Bean

`resolveBeanName()`（`:253-268`）**只按类型反查 Bean 名，不校验是否实现 `ReversibleTool`**。

在「标业务方法」场景下极易踩：业务 Service 通常不实现 `ReversibleTool`（薄壳是独立 Adapter），
若忘了写 `reverseBean`，入账时**毫无异常**（账本帧正常写入），撤回时才在
`ReversibleUndoServiceImpl:128` 的 `getBean(name, ReversibleTool.class)` 抛 `BeanNotOfRequiredTypeException`
—— 而那一帧已在 `:121` 被 CAS 改成 `REVERSING`，随后标 `FAILED`，**永久不可再撤**。

**已修**：`ReversibleLedgerAspect` 新增 `validateReverseBean(reverseBean, joinPoint)`，
在**入账时**校验 `containsBean` + `isTypeMatch(.., ReversibleTool.class)`，有问题当场抛异常。
调用点在 `:106`。

### 发现的问题 2（未修，待用户决定）：多参业务方法的入参快照

`ReversibleLedgerAspect:112-114` 的入参快照规则：

```java
String toolInput = bizArgs.length == 1
        ? JsonUtils.toJsonString(bizArgs[0])   // 单参：存对象
        : JsonUtils.toJsonString(bizArgs);     // 多参：存数组 JSON
```

而 `ReversibleContext.input(Class<T>)` 是 `JsonUtils.parseObject(rawInput, type)`。
**多参时 rawInput 是数组 JSON（如 `["RCV-001",1001,5]`），按 POJO 类型解析会抛 Jackson
`MismatchedInputException`** → 冲账失败、帧标 FAILED。

业务方法常是多参（`createReceive(String, Long, Integer)`），所以这个限制在「标业务层」场景下会碰到。

两个解法（已向用户提出）：
- A. 业务方法参数收敛为单个 DTO（推荐，本身也是好设计）
- B. 框架给 `ReversibleContext` 加 `inputs()` / `inputArray()` 支持多参

### 一处语义变化：账本 `tool_name`

标业务层时 `tool_name` 记的是**业务 Service 的 Bean 名**（如 `wmsReceiveService`），
不再是工具名 —— 因为业务方法没有 `@Tool` 注解，`resolveToolName()` 会走 `resolveBeanName` 兜底。

这**符合字段定义**（`ReversibleLedgerDO.toolName` 定义就是「正函数 Bean 名」），
但**推翻了说明书里「tool_name 与 ai_tool.name 对得上、可以 join」的说法** —— 已修正说明书 Step 6 第 ③ 点。

### 一个意外收获

即使误给冲账方法标了 `@Reversible`，**也不会递归入账**：撤回时 `ReversibleContextHolder` 为空
（撤回是 REST 接口触发的，桥接切面拦的是带 `ToolContext` 参数的方法），切面会走

# 剥离 Java 注释后对比代码骨架
def strip_comments(path):
    src = open(path, encoding='utf-8').read()
    buf, i, n = [], 0, len(src)
    while i < n:
        if src.startswith('/*', i):          # 块注释
            j = src.find('*/', i + 2); i = n if j == -1 else j + 2; continue
        if src.startswith('//', i):          # 行注释
            j = src.find('\n', i); i = n if j == -1 else j; continue
        if src[i] == '"':                    # 字符串字面量整体保留，避免串内 // 被误删
            q = src[i]; buf.append(q); i += 1
            while i < n and src[i] != q:
                if src[i] == '\\': buf.append(src[i]); i += 1
                if i >= n: break
                buf.append(src[i]); i += 1
            if i < n: buf.append(src[i]); i += 1
            continue
        buf.append(src[i]); i += 1
    return [l.strip() for l in ''.join(buf).split('\n') if l.strip()]
# 两版结果相同 → 逻辑未变

### 更正 1（真错误）：`beanNameCache` 注释里的"死循环"说法不准确

我原注释写「HashMap 在多线程下会出问题（数据错乱甚至死循环）」。
**"死循环"是 JDK 7 及以前的问题**：那时扩容用**头插法**，并发扩容可能把链表接成环（A→B→A），
get 一个不存在的 key 会无限打转、CPU 打满。
**JDK 8 改成尾插法后环就形不成了**，死循环不再发生。本项目是 **JDK 25**，所以这个说法是错的。

已改为：区分 JDK 7（死循环）与 JDK 8+（仍存在数据覆盖/计数不准/读到脏值），
并指出后者**更隐蔽**（死循环至少立刻暴露，丢数据是静默的）。

### 图上表达不出来、补进了文件注释的内容

**本方法一共三层 try，容易绕晕**：

| 层级 | 结构 | 作用 |
|---|---|---|
| 最外层 | `try ... finally` | 只为 finally 还原租户上下文，**没有 catch** |
| 中间 | `try ... catch` | 包住 `joinPoint.proceed()`（业务执行阶段） |
| 内层 | `try ... catch` | 包住"记账 + 提交"（记账阶段） |

**一个诚实的观察（已写进注释）**：中间和内层两个 catch 做的事完全一样（回滚 + 原样抛），
**合并成一个大 try 在功能上完全等价**。拆开纯粹是可读性考虑（阶段划分清晰），
附带好处是将来若想给两阶段不同的失败处理，结构已就位。

**三个异常出口的性质不同（重要）**：
- resolveContext 失败 / validateReverseBean 失败 → 发生在**开事务之前** → **不需要回滚**
- 业务 `proceed()` 抛异常 / insert 失败 → 在**事务内** → **需要回滚**
