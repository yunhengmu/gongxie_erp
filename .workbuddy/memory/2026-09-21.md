## 二、实测验证了桥接切面（这是我之前一直标注「未实测」的地方）

**背景**：`ReversibleBridgeAspect` 的切点 `execution(* *(.., org.springframework.ai.chat.model.ToolContext, ..))`
是我推断可用的，标注过「标准 AspectJ 语法但未实测」。用户追问「你确定能拿到所有工具函数吗」，于是做了真实验证。

**方法**：用 JDK 25 写了个测试程序，调 AspectJ 自己的 `PointcutParser.parsePointcutExpression()` +
`matchesMethodExecution()`，对 6 种方法签名逐一测试。

**结果**：

| 测试方法签名 | `(.., Type, ..)` | 对照 `(.., Type)` |
|---|---|---|
| `apply(String, ToolContext)`（BiFunction 形态） | 匹配 | 匹配 |
| `apply(String)`（单参 Function） | **不匹配** | 不匹配 |
| `doQuery(String, ToolContext)` | 匹配 | 匹配 |
| `mixed(ToolContext, String)`（ToolContext 在开头） | **匹配** | 不匹配 |
| `threeArgs(String, ToolContext, String)`（在中间） | **匹配** | 不匹配 |
| `onlyCtx(ToolContext)` | 匹配 | 匹配 |

**结论**：
1. `(.., Type, ..)` **语法合法**（解析成功，不会启动报错）
2. 语义是「参数列表**任意位置**存在该类型」，对位置不敏感 —— **比 `(.., Type)` 强**
3. 正确排除单参形态；而单参形态本来也不可撤回（拿不到 ToolContext）
4. 顺带核实：AspectJ 社区明确说过 **`args(.., e, ..)` 不支持**（要绑定参数，中间位置有歧义），
   但 **`execution` 支持**（只做类型匹配，无歧义）—— 两者不能一概而论

## 三、用户揪出的设计冗余：`resolveContext` 的「来源二」是死代码

**用户的推理链**（很准）：
1. 桥接切面的匹配条件 = 「有 ToolContext 参数的方法」
2. 而「标工具方法」的前提 = 「有 ToolContext 参数」
3. **两个集合重合** → 标工具方法时 Bridging 必然先执行、Holder 必然有值
4. → `resolveContext` 的「来源二（读 ToolContext 参数）」**永远走不到**

**我进一步确认**：即使换回「先参数、后 Holder」的老顺序也不行 —— 那样只是换成「桥接刚 set 的 Holder 被忽略」，
**同样是同一份数据读两遍**，而且桥接那次 set 白做了。

**结论**：`resolveContext` 的两个来源与桥接切面**功能重复**。
「桥接」的本质是**取代**（把两个来源合并成一个），不是**补充**。
最干净的结构是**只读 Holder**，`resolveContext` 可从 30 多行缩到 10 行，
连带 `findToolContext` / `declaresToolContext` 两个辅助方法都能删。

**待办**（未改）：这个简化依赖「桥接切点确实生效」——现在实测证明它生效了，**前提已满足**。
另外顺手该做的还有：`conversationId` 未判空（会让因果闸门静默失效）、
`resolveBeanName` 急切求值（指定了 reverseBean 也照样反查、可能抛不该抛的异常）。

## 五、讲解「bridge 所在线程的一生」（用户提问）

**问题**：`ReversibleBridgeAspect.bridge` 这个线程在它的生命周期中被用来做什么了。

**核实到的事实（有源码依据）**：

1. **工具执行路径**：yudao 是**把 `ToolCallingManager` 注入 ChatModel 构造器**来驱动工具执行的
   —— `AiAutoConfiguration.java:126`（`new DashScopeChatModel(api, options, toolCallingManager, ...)`）、
   `AiModelFactoryImpl.java:487`（`.toolCallingManager(...)`）。全项目**没有** `ToolCallingAdvisor` 引用，
   即不走 ChatClient 的 Advisor 链。所以工具执行发生在 **ChatModel 内部**，而非 ChatClient 层。
2. **两条对话入口**（`AiChatMessageServiceImpl`）：
   - `/send` 非流式 → `:174` `chatModel.call(prompt)`，同步方法 ⇒ 工具执行与 Controller 同线程（Tomcat worker）
   - `/send-stream` 流式 → `:232` `chatModel.stream(prompt)` 返回 Flux ⇒ 工具执行在驱动该 Flux 的线程上
     （具体线程池取决于 provider 的响应式客户端实现，**未逐行核实**）
3. **同线程的根本原因**：`executeToolCalls` → `ToolCallback.call` → `MethodToolCallback` 反射 `method.invoke`
   → bridge → 业务方法，**全程一条同步调用栈，无切换点**。`proceed()` 只是继续往下走这条栈。
   所以 Holder 注释里「写入点即工具执行线程、业务方法是同线程普通调用」成立。
4. **clear 真正防的是「串号」不是「泄漏」**：残留会让**下一个复用到该线程的任务**读到别人的 Snapshot。
   最危险的命中路径是「下一个任务是非 AI 入口（REST/定时任务）调用同一个 `@Reversible` 业务方法」
   → `resolveContext` 第一级读 Holder 读到残留 → 误判为 AI 触发 → 写入挂错 messageId 的账本帧。
   非流式路径下工具与 REST 请求**共用 Tomcat 同一个线程池**，命中概率最高。
5. `TransmittableThreadLocal` 在当前同线程场景下与普通 ThreadLocal 行为等价；它的价值只在
   「业务方法内部再派给**被 TTL 包装过的**线程池」时才体现，裸线程池照样传不过去。

## 六、`(MethodSignature) joinPoint.getSignature()` 这条转换（用户提问）

**源码证据**（spring-framework `aop/aspectj/MethodInvocationProceedingJoinPoint.java`）：
`getSignature()` 返回 **private 内部类 `MethodSignatureImpl`**（惰性创建 + 缓存），它 `implements MethodSignature`；
`MethodSignatureImpl.getMethod()` 直接 `return methodInvocation.getMethod()`。
⇒ 在 Spring AOP 的 `@Around` 里强转永远安全（AOP 只支持方法执行通知）；但**拿到的是"这次被拦截的调用"对应的方法**。

**新发现的潜在隐患**：`ReversibleLedgerAspect.resolveToolName():251-252` 用 `signature.getMethod()` 读 `@Tool`。
- 本项目 `PersonServiceImpl implements PersonService`，`@Tool` 只标在**实现类**方法上（`PersonServiceImpl.java:197/223/...`），
  接口 `PersonService.java` 上**没有** `@Tool`。
- JDK 接口代理下 `getMethod()` 返回**接口方法** → `AnnotatedElementUtils.findMergedAnnotation` 返回 null
  → **静默回退**到 `resolveBeanName`，工具名从 `ps_create_person` 变成 Bean 名（不报错，只是账本帧 `tool_name` 不对）。
- Spring Boot 默认 CGLIB（`proxy-target-class=true`）拿到目标类方法，所以**当前实际不出问题**；
  但标准写法应加 `AopUtils.getMostSpecificMethod(signature.getMethod(), targetClass)` ——
  `AopUtils` 已在 `:20` import（用于 `resolveBeanName`），`resolveToolName` 却没走这层。
- 同文件风格不一致：`:251` 硬转、`:233` 用 `instanceof` 模式匹配。并入上面「待办」清单。

## 七、`ReversibleContextHolder` 该不该改成 Spring 注入（用户提问）

**结论：保持静态工具类**。关键是把问题拆成两层——
- **存储介质**（ThreadLocal）决定「值在并发下归谁」，这是被问题本身强制的；写入方 `ReversibleBridgeAspect`
  与读取方 `ReversibleLedgerAspect` 是**两个不同的 Bean**，只能靠线程级 store 互通，实例字段做不到。
- **引用获取**（static）才是 DI 能改的部分，改完语义零变化。

**反证（三种 Scope 全走不通）**：
- 单例 + 实例字段 → 两个切面注入同一实例，字段被所有线程/租户共用 → **跨租户串数据**（比 ThreadLocal 更糟）。
- `@RequestScope` → 工具在 Flux 线程执行（`AiUtils.java:172` 自证），非 HTTP 请求线程 → 取不到。
- `@Prototype` / 每次 getBean → 写方与读方拿到不同实例 → 读永远 null → 入账全跳过，撤回链路整体失效。

**项目内先例（源码证据）**：
- `TenantContextHolder.java:12,17`、`DataPermissionContextHolder`、`EnvContextHolder` —— 清一色 static 类 + static TTL。
- 最有说服力的是 `TransmittableThreadLocalSecurityContextHolderStrategy.java:15,20`：Spring Security 把它做成
  **可替换的策略接口实现**，内部第 20 行**依然是** `private static final ThreadLocal<SecurityContext> CONTEXT_HOLDER`
  ⇒ 框架层 context holder 的惯例是「抽象接口可以，抽象存储不行」。

**唯一有意义的中间态**（若将来要换存储介质，如 ThreadLocal → Reactor Context）：
定义 `ReversibleContextStore` 接口 + 一个 `@Bean` 适配器，静态 Holder 退化为它的默认实现。
但现在调用点只有 2 处、且都在同一 framework 包内，收益不足，属于「为未来留门」。

## 八、附问：什么场景必须用单例注入（用户追问）

**判据一句话**：注入拿「**能力**」，new 造「**数据**」。真正的判据不是「可变 / 不可变」，而是
「**换一个调用者，这个值会不会变**」—— 会变 → 不能进单例字段。

**六类必须注入的场景**（本项目实例）：无状态服务/仓储（`ReversibleUndoServiceImpl:45-48`）、
容器管生命周期的资源（`ReversibleLedgerAspect:83` 注入 `PlatformTransactionManager`）、
需要被 AOP 代理的组件（`ReversibleTool.java:11-15` + `ReversibleUndoServiceImpl:128`）、
配置只读值（`ReversibleLedgerAspect:71` `@Value`）、运行时才知道要哪个实现
（`ReversibleUndoServiceImpl:50,128` 注入 `ApplicationContext` 后 `getBean(ledger.getReverseBean(), ReversibleTool.class)`，
Bean 名存在库列里，属正当用途）、需要被容器反向发现（`List<Xxx>` 注入 / Spring AI 工具注册）。

**两个「实例字段却安全」的对照（本项目真实代码，判据的最强证据）**：
- `ReversibleLedgerAspect:81` `beanNameCache`（`ConcurrentHashMap` 可变实例字段）→ **安全**，
  因为 key 是 `Class`（自带完整身份）、value 与调用者无关。
- `ReversibleUndoServiceImpl:55-60` `reverseTransactionTemplate`（`final`，由注入的
  `PlatformTransactionManager` new 出来）→ **安全**，因为 `TransactionTemplate` 配置不可变，
  真正的事务状态在 `TransactionSynchronizationManager` 的 ThreadLocal 里。
- 反例对照：`ReversibleContextHolder.Snapshot` 的值是「当前是谁在调」→ 放实例字段必事故。

**唯一硬例外**：需要被代理的东西不能 `new`（`new` 出来的对象没有增强，事务/切面全失效）。

## 单例与上下文机制全项目梳理（19:30 起，纯讲解未改码）

**一、自定义单例只出现在「容器管不到」的地方**。全项目 `volatile` 仅 2 处（`MemberServiceImpl.memberUserApi`、
`AbstractSmsClient.properties`），均非单例模式；无手写 GoF 单例。五类用途：无状态工具类伪单例、
容器外取 Bean 的桥、跨方法传上下文、keyed 对象注册表、全局唯一资源表。

**二、ContextHolder 是 5 个类 / 6 个 ThreadLocal 字段**（此前说「6 处」系数字段，`TenantContextHolder`
占 2 个：`TENANT_ID`、`IGNORE`）：TenantContextHolder、DataPermissionContextHolder（LinkedList 栈）、
EnvContextHolder（List 栈）、TransmittableThreadLocalSecurityContextHolderStrategy、ReversibleContextHolder。
- 6 个字段**全是 TTL**，无一原生 ThreadLocal
- `static final` 保证的是 ThreadLocal **对象**唯一（否则每次 new 就是不同 key，`get()` 读不到）
- Security 那处的装配是替换策略：`YudaoSecurityAutoConfiguration` 用 `MethodInvokingFactoryBean`
  调 `SecurityContextHolder.setStrategyName(...)`，而非自己持有
- 栈式的两个（DataPermission / Env）是为方法嵌套覆盖，Tenant 存单值即可

**三、TTL 装配点（本次新发现，重要）**：`YudaoAsyncAutoConfiguration`
（yudao-spring-boot-starter-job/.../quartz/config/）用 `BeanPostProcessor` 给容器内所有
`ThreadPoolTaskExecutor` / `SimpleAsyncTaskExecutor` Bean 挂 `setTaskDecorator(TtlRunnable::get)`。
全项目**无** TtlExecutors/TtlRunnable 直接调用、**无** javaagent 配置。
- 推论 1：非 Bean 线程池不传。`CacheUtils:43` 用 `Executors.newCachedThreadPool()`，
  故 `CacheUtils:27` 那句「和『人』相关的用 buildCache」是机制结论，不是经验之谈。
- 推论 2：Reactor Flux 工具线程、RabbitMQ `SimpleMessageListenerContainer` 线程池均不受管。

**四、AiModelFactoryImpl 的 keyed 单例**：底层 Hutool `Singleton.get(key, supplier)` ——
`POOL = SafeConcurrentHashMap` + `computeIfAbsent`，无锁。芋道把 Hutool `buildKey` 抄成
`buildClientCacheKey`（`AiModelFactoryImpl:304`），一字不差；不用 `Singleton.get(Class, params)`
是因为该重载走 `ReflectUtil.newInstance` 反射构造，而这里要手组 Builder。
- key 形态 `ChatModel#TONG_YI_sk-xxx_url`，租户隔离靠 apiKey 差异自然实现
- 三隐患：① POOL 永不清理（无 TTL／无上限／无 remove 调用点），改密钥即泄漏，
  `buildSimpleVectorStore` 还遗留 Timer ② apiKey 明文进 key ③ computeIfAbsent 首次构造阻塞
- Hutool 用 `SafeConcurrentHashMap` 是为绕开 JDK-8161372（JDK8 computeIfAbsent 死循环，源自 Dubbo #2349）；
  项目跑 JDK 25 走原生分支，不受影响

**五、澄清 ReversibleContextHolder 与 ReversibleLedgerAspect 的「矛盾」**：前者讲
「工具方法 → 业务方法」这一跳（同线程，故 Holder 可用），后者讲「请求线程 → 工具线程」这一跳（丢）。
结论：**跨不过线程边界时降级为显式参数（ToolContext），而不是硬撑 TTL**。

**六、WCS / RabbitMQ 场景映射（用户新提出的落地场景）**：结论是 ThreadLocal 那套基本不需要，
真正需要的是全局状态单例 + keyed 连接池。四层载体：MQ Header（跨服务）→ 消费入口薄 ThreadLocal
（finally clear）→ 单例 ConcurrentMap<deviceCode, DeviceRuntime>（核心）→ keyed 单例缓存每设备长连接
（必须可 remove，否则会往已下线堆垛机发指令）。判别线：**ThreadLocal 装「这次是谁触发的」（短命），
单例 ConcurrentMap 装「系统里有什么」（长命）**。

**七、线程池 Bean 到底是「搬运工」还是「状态容器」（用户提问引发的澄清）**。用户的表述是
「注册到 IOC 的线程实例 / 用来保持用户登录状态和用户信息」，此处有两处概念错位需长期注意：
- **IOC 里没有「线程」这个 Bean**。`ThreadPoolTaskExecutor` Bean 是执行器对象（单例），
  它内部的工作线程由 JDK 的 `ThreadPoolExecutor` 创建管理，**不进容器**。容器单例的粒度是执行器。
- 该 Bean 的角色是**上下文搬运通道（传递）**，不是**状态容器（保持）**。它参与用户上下文
  传递（靠 TTL + TaskDecorator），但 `TtlRunnable` 执行完即 restore，线程还池时是空的。
  想「保持」应用 ConcurrentMap 注册表 Bean（对应 `WebSocketSessionManagerImpl` 形态）
  或 Redis。一句话：**线程池 Bean 是邮局，不是仓库。**

**Spring 源码证据（`ThreadPoolTaskExecutor`，注意该类在 spring-context 而非 spring-core）**：
全类**唯一**的 `taskDecorator.decorate` 调用点在 `initializeExecutor` 内匿名
`ThreadPoolExecutor` 重写的 `execute(Runnable)` 里：

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(...) {
    @Override
    public void execute(Runnable command) {
        Runnable decorated = command;
        if (taskDecorator != null) {
            decorated = taskDecorator.decorate(command);   // 唯一装饰点
            if (decorated != command) decoratedTaskMap.put(decorated, command);
        }
        super.execute(decorated);
    }
};
```

→ 装饰发生在**任务入队之前**、且在**调用线程**上执行，故 `TtlRunnable.get()` 抓的是
「提交那一刻」的上下文，不是「执行那一刻」的。对外的 `execute`/`submit` 本身不 decorate，
统一委托给这个被重写的底层 `execute`。另 `decoratedTaskMap` 用
`ConcurrentReferenceHashMap` + WEAK 引用，避免装饰后任务对象泄漏。

**八、`@Bean` 的判据与项目分布（用户问「什么改动会碰 @Bean」）**

判据一句话：**改动是否改变了「对象怎么被创建 / 怎么被装配」**。改完代码容器里的 Bean 清单
会变吗？不新增、不替换、不改造法 → 完全不用碰。反例：改方法体、加接口/表/DTO、给 Service
加新依赖（构造函数加参数）——都不会碰 `@Bean`。

**项目分布（两层，约定很硬）**：
| 层次 | 注解 | 命名 | 位置 |
| 框架 starter | `@AutoConfiguration` | `YudaoXxxAutoConfiguration` | `yudao-framework/**/config/`（41 个） |
| 业务模块 | `@Configuration` | `XxxConfiguration` | `module-*/**/framework/xxx/config/` |

**关键约定**：业务模块的配置类**统一放 `framework/` 包下，不放 `service/`**。定位是
「与框架/基础设施的胶水层」，不是业务层。新建配置类前先问「是业务逻辑还是胶水」。

**笔误纠正**：`@Configuration` 与 `@Bean` 不是同义词 —— 配置类里可以一个 `@Bean` 都没有
（只做 `@EnableXxx` / `@Import` / `@ComponentScan` / `@EnableConfigurationProperties`）。
因果是「有对象必须手工造 → 需要地方放造它的方法 → 那个地方叫配置类」，反过来不成立。

**两个真实样本**：
- `YudaoWxClientConfiguration`（module-system/framework/weixin/config/）：被第三方逼出来的。
  weixin-java 4.8.x 初始化 config storage 时无条件调 `DefaultApacheHttpClientBuilder.get()`，
  类加载引用 Apache HttpClient 4.x → 启动报 `NoClassDefFoundError`。故自行 `@Bean` 接管
  `WxMpConfigStorage` / `WxMaConfig` 创建，配 `@ConditionalOnMissingBean` 留覆盖口子。
- `DataPermissionConfiguration`（module-system/framework/datapermission/config/）：整个类只有
  一个方法，返回 **lambda**（`DeptDataPermissionRuleCustomizer`）。此时 `@Bean` 不是「造对象」
  而是「一条声明」——把 system 模块的表注册进框架的数据权限规则。必须放在 module-system，
  因为只有它知道自己的表。特征：**要动配置类，但只加几行，不动任何 Service。**

**`YudaoWebSocketAutoConfiguration` 是 `@Bean` 用法大全**（starter-websocket/config/）：
第三方类型（`WebSocketConfigurer` / `TopicExchange`）、组装逻辑（`webSocketHandler` 里
组合 `JsonWebSocketMessageHandler` + `WebSocketSessionHandlerDecorator`）、
`List<? extends WebSocketMessageListener<?>>` 收集扩展点、五套 sender
（local/redis/rocketmq/rabbitmq/kafka）靠 `@ConditionalOnProperty(sender-type)` 切换。

**闭环（本次串起前几轮）**：`WebSocketSessionManager` 单例由
`YudaoWebSocketAutoConfiguration:76` 的 `@Bean` 创建（`return new WebSocketSessionManagerImpl();`）
→ **能用 `@Bean` 造的单例，就不必手写单例模式**，这就是全项目零手写 GoF 单例的原因。

**九、`@Component` 包一个线程池 vs `@Bean` 返回线程池（用户质疑引发的修正，重要）**

上一轮给的理由「要设队列容量 / 线程名 / 优雅关闭」**不硬**——setter + `@PostConstruct` 也能设。
该理由已被用户当场指出，记录以免复犯。真正的分界线是**生命周期归谁管**。

**源码证据**：`ThreadPoolTaskExecutor extends ExecutorConfigurationSupport`；本类自身**不**实现
`InitializingBean` / `DisposableBean`，只实现 `AsyncListenableTaskExecutor` / `SchedulingTaskExecutor`，
并重写模板方法 `initializeExecutor(ThreadFactory, RejectedExecutionHandler)`
（**真正的 `ThreadPoolExecutor` 与 `TaskDecorator` 植入都在这里**）、`initiateEarlyShutdown`、
`cancelRemainingTask`。父类 `ExecutorConfigurationSupport` 实现
`InitializingBean` / `DisposableBean` / `BeanNameAware`，`afterPropertiesSet()` → `initialize()`
→ `initializeExecutor(...)`，销毁走 `destroy()` → `shutdown()`。

**四条推论**：
- A：`@Bean` 返回它 → Spring 自动调 initialize / shutdown（自动建池 + 优雅关闭）。
- B：`@Component` 包一层 → 内部对象**不是 Bean**，`InitializingBean`/`DisposableBean` 回调
  **不触发**，必须自己调 `executor.initialize()`（public，专为此场景）和 `shutdown()`。
- C：**TTL 挂不上** —— `YudaoAsyncAutoConfiguration` 的 BeanPostProcessor 只拦「是 Bean 的线程池」，
  包一层拦不到 → 异步任务里 `TenantContextHolder` 读到 null。呼应第七条装配点结论。
- D：失去 `@ConditionalOnProperty` 条件化；固定几台设备想「一台一个」，只能用 `@Bean` 方法
  声明多个同类型 Bean。

**判据**：设备数量**启动时固定**（配置 / 枚举）→ `@Bean`（生命周期自动托管）；
**运行时动态**（数据库里配的）→ `@Component` 包 `ConcurrentMap<deviceCode, Executor>`，自己管
initialize / shutdown（与 `AiModelFactoryImpl` 的 keyed 池同构）。

**表述澄清**：`@Component` 标**类**、`@Bean` 标**方法**，位置不可互换。

**十、芋道的注入规则 × RuoYi 血统（用户提问「基于 ruoyi 二次开发，什么情况用实例注入」）**

**A. RuoYi 血统的实际边界（校准用户说法，只说对一半）**
- 项目仓库名本身就是 `ruoyi-vue-pro`（GitHub `YunaiV/ruoyi-vue-pro`、Gitee `zhijiantianya/ruoyi-vue-pro`），
  代码里大量引用其 issue/PR 链接
- `@author ruoyi` 的类**集中在 system 模块的权限/字典/通知**：`DictDataService`、`DictDataServiceImpl`、
  `OperateTypeEnum`、`AuthenticationEntryPointImpl`、`NoticeDO`、`MenuDO`、`RoleDO`、`UserRoleDO`、
  `RoleMenuDO`、`PostDO`
- 结论：**血统上是 RuoYi，架构上是重写**（40+ starter、多租户、数据权限、RPC 分层、Spring AI 均为新增）。
  **注入风格属于「重写」的部分，不是继承来的。**

**B. 注入规则的硬规律（本次最有价值的发现）**
- `@Resource` 绝对主导（100+ 文件，每个 Service/Controller 2-10 个）
- `@Autowired` **全项目仅 7 处**，其中 **6 处带 `(required = false)`**
- **规则**：依赖一定存在 → `@Resource`；**依赖可能被开关关掉 → `@Autowired(required = false)`**
- **根因（技术性，非风格偏好）**：`@Resource` 是 JSR-250 注解，**没有 `required` 属性**，
  注入失败直接抛 `NoSuchBeanDefinitionException` → 依赖可能不存在时**必须**换注解
- 六个可关开关对应的注入点：`justauth.enable`→`AuthRequestFactory`（`SocialClientServiceImpl:116`）、
  `yudao.tenant.enable`（`TenantServiceImpl:59`）、`spring.ai.model.rerank`→`RerankModel`
  （`AiKnowledgeSegmentServiceImpl:86`）、`yudao.ai.web-search.enable`（`AiChatMessageServiceImpl:126`）、
  `yudao.ai.mcp.client.enable`→`List<McpSyncClient>`（`AiChatMessageServiceImpl:130`）、
  `yudao.websocket.enable`（`DemoWebSocketMessageListener:22`）
- **最强证据**：`AiChatMessageServiceImpl:109-131` 一个类里两种并存（7 个 `@Resource` + 2 个
  `@Autowired(required=false)`，各带一行开关注释）
- 与第八条呼应：`@ConditionalOnProperty` 在装配端，`@Autowired(required=false)` 是它在**注入端的镜像**

**C. 字段注入是「知情选择」**
- `@Autowired` 处都挂了 `@SuppressWarnings("SpringJavaAutowiredFieldsWarningInspection")`
  → IDEA 默认警告字段注入，芋道**显式压制**，说明知道代价
- 代价三项：字段不可 `final`（对照 `ReversibleLedgerAspect` 用构造函数注入拿 final）、
  测试须起容器无法纯 `new`、掩盖循环依赖（靠三级缓存兜底）
- 换取：100+ Service 各少写一段构造函数样板
- **唯一违规点**：`DbQueryToolFunction:59` 裸用 `@Autowired`（无 required、无 `@SuppressWarnings`），
  位于后加的 `tool/function` 包，`JdbcTemplate` 必存在故不影响功能，但未遵循项目规范

**十一、「注入实现类而非接口」的真实分布（用户澄清问题方向后的重新作答）**

**先纠正前提：芋道自己也是接口注入，与 RuoYi 的差别只是命名前缀。**
- `public interface I[A-Z]` 全项目**零结果** → 芋道接口**不带 RuoYi 的 `I` 前缀**
  （RuoYi: `ISysUserService` vs 芋道: `AiChatMessageService`）
- 唯一的 `ILogRecordService`（`LogRecordServiceImpl implements ILogRecordService`）来自
  **第三方库** mzt-biz-log，非芋道自有

**生产代码里「用实现类」只有一个场景：`getSelf()` 解 AOP 自调用。** 全项目 4 处：
| 类 | getSelf 定义 | 调用点 |
| `RoleServiceImpl` | :270 | :224、:238（`getRoleFromCache`） |
| `PermissionServiceImpl` | :342 | :104、:261（`...FromCache`） |
| `OAuth2ClientServiceImpl` | :157 | :125（`getOAuth2ClientFromCache`） |
| `AiImageServiceImpl` | :361 | :105（`executeDrawImage`） |

统一写法与注释原文：
```java
/** 获得自身的代理对象，解决 AOP 生效问题 */
private XxxServiceImpl getSelf() { return SpringUtil.getBean(getClass()); }
```
被调方法共同点：**都带 `FromCache` 后缀**，即需要 `@Cacheable` 生效。

**为什么返回 Impl 而非接口（压力测试后修正）**：不是「接口缺方法」——已核实
`getRoleFromCache` 在 `RoleService:73` **有声明**；真正原因是
`SpringUtil.getBean(getClass())` 的**类型推导**（`getClass()` → `Class<? extends RoleServiceImpl>`）
自然得出 Impl。属副产品，非刻意设计。

**为何不用另两种做法**：
- `AopContext.currentProxy()` 需 `@EnableAspectJAutoProxy(exposeProxy = true)`，
  全项目搜 `currentProxy` **零结果**（未开启）
- 自注入 `@Resource private RoleServiceImpl self` 虽 Spring 4.3+ 支持，但启动期要走循环依赖处理
- 芋道选运行时 `SpringUtil.getBean(getClass())`，完全避开启动期循环依赖

**另一个场景是测试**：`src/test` 下 15+ 处 `@Resource private XxxServiceImpl xxxService;`
（如 `ApiErrorLogServiceImplTest:34`、`FileConfigServiceImplTest:51`），因为要测具体实现，
且 `@Mock` / `@Spy` 需要具体类型。

**十二、「单例模式的开发场景」被用户批评后修正（重要，避免复犯）**

用户原评：「你这个应用场景太扯了」。批评成立。我犯了两处自相矛盾：
- **错 1**：把「Spring 容器自动解决的事」当成「会遇到单例问题的场景」。表格里列了
  「MQ 生产者 / SDK 客户端 → 单例 Bean」「本地缓存 → 单例 + Caffeine」
  「设备运行时状态表 → 单例 + ConcurrentMap」—— 这些贴个 `@Component` 就完事，
  **根本轮不到人思考单例**，与本文档第八/十条自己的论证矛盾。
- **错 2**：正文用 `ErpNoRedisDAO` 论证「唯一性该外移到 Redis」，表格里却写
  「单据号生成器 → 单例 + `AtomicLong`」（教科书答案，现实不用）。
- **后续规则**：讲「应用场景」前先用「**Spring 是否已自动解决**」过滤一遍，避免堆砌。

**修正后的准确结论**：Spring Boot 业务开发中**基本不会「主动需要写单例」**。真正会遇到
单例问题的只有四类，且都是被动的：① 接管第三方库的单例 / 静态初始化 ② 容器够不到的地方
需要唯一实例（`TypeHandler`、Jackson Serializer、静态工具类，`DictFrameworkUtils.init()`
即此妥协）③ 读 / 维护非 Spring 老项目 ④ 排障（有状态单例串数据、单例内 Map 只增不减）。

**用户的归纳（准确，采纳）**：「就是对其他第三方工具进行二次调整的时候」。

**第三方藏实例的六种方式（决定能否改造）**：静态单例（`getInstance()`）、静态代码块
（类加载即跑，weixin-java 的 `DefaultApacheHttpClientBuilder.get()` 属此类）、默认构造器里
`new`、内部 `new` 依赖（需 setter / 继承 / AOP）、静态实例池（清理策略不可控）、
`private static final` 常量。**最快识别：搜有无 `getInstance()` / `getDefault()` / 静态工厂。**

**改造决策路径（三条出口）**：
1. 有 setter / builder / 模板方法 → 改配置，不动代码
2. 构造逻辑可照抄、公开 API 够用 → 自己 `@Bean` 重造（`YudaoWxClientConfiguration` 即此）
3. 都做不到 → 包适配器隔离，自己的代码只依赖自己的接口

**关键前提**：要给第三方加 AOP，前提是实例由容器创建；它自己 `getInstance()` 出来的对象
**没有代理**，切面直接失效。

**最血泪的一类：被迫的改造发生在升级依赖时，不是功能不够时。** `YudaoWxClientConfiguration`
注释即活样本——静态初始化引用已不存在的 HttpClient 4.x → `NoClassDefFoundError` → 只能把它的
初始化逻辑照抄一遍自建 Bean。**结论：写业务时不会遇到单例问题，跟第三方库搏斗时天天遇到。**
