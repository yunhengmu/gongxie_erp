## 源码核查：路 B（per-user tool filtering）的泄漏风险
- 用户问路 B 会不会有泄漏风险，核查了 module-ai/framework 5 个真实类：
  - `module-ai SecurityConfiguration.java` L37：`/mcp`（streamable-http-endpoint）被 `permitAll()`——不强制认证，匿名请求可进。
  - `YudaoWebSecurityConfigurerAdapter.java` L151：`TokenAuthenticationFilter` 是 `addFilterBefore`，对所有请求执行（带 token 就写 loginUser，不带则 loginUser=null）。
  - `TenantSecurityWebFilter.java` L69-84：越权比对包在 `if (user != null)` 里——匿名请求下整段跳过。
  - `TenantDatabaseInterceptor.java` L42：`getRequiredTenantId()` 读 ThreadLocal 拼 SQL，不关心租户来源。
  - `TenantContextWebFilter.java` L25：从 `tenant-id` 头读租户写 ThreadLocal。
- 结论：真正的洞是「/mcp permitAll 允许匿名」，匿名 + 伪造 tenant-id 头 = 直接读该租户数据（数据越权级）；路 B 只挡 tools/list 清单、不拦 tools/call，且依赖断掉的身份链。安全顺序：先去 permitAll 强制认证 → 工具内执行级 RBAC → 最后才做路 B 清单收敛。
- 关键澄清（用户追问「原本不是 token 鉴权解决了么」）：芋道 token 鉴权（`TokenAuthenticationFilter`）**对 /mcp 也执行**，但它是「尽力解析、从不拦截」——L79 无条件 `chain.doFilter`、token 无效仅 return null 不抛错。permitAll 关的是 authorize 层的「强制认证」（`anyRequest().authenticated()` 兜底），不是 token 解析本身。即「带 token→越权比对生效（安全）；不带 token→permitAll 放行 + loginUser=null→比对跳过（漏）」。修复=删掉 module-ai SecurityConfiguration L36-38 的 /mcp permitAll，让 /mcp 落回 authenticated 兜底。
