## 追问式学习（09-19 上午，用户连续提问，均为概念澄清）

用户在补 Spring/AOP 基础，连续问了 6 个问题。有价值的澄清点：

1. **`org.springframework.ai.chat.model.ToolContext` 找不到** → 它是 `spring-ai-model` jar 里的类。
   **关键发现：用户的 Maven 仓库不在默认位置**，IDEA 的 `workspace.xml` 里配的是
   `D:\Maven\.m2\repository`（不是 `C:\Users\Administrator\.m2\repository`）。
   该目录下有 60+ 个 spring-ai artifact，且 `spring-ai-model-2.0.0-sources.jar` 存在（能看源码）。
   **教训**：查依赖先看 IDE 的 localRepository 配置，别想当然用默认路径。
2. **`ProceedingJoinPoint` 拿到什么** → 基于本机 aspectjweaver-1.9.25.1 源码列全 12 个方法；
   代码里实际用了 4 个（`getSignature` 10 处、`getArgs` 2 处、`getTarget` 2 处、`proceed` 2 处）。
   两个参数来源不同：`joinPoint` 是 Spring 注入，`reversible` 是切点表达式参数名绑定。
3. **`record`** → Java 16 语法糖；强调访问器无 get 前缀、隐式 final、与 Lombok `@Data` 对比。
4. **`TransmittableThreadLocal` 不是线程，是变量** → 三代 ThreadLocal 对比；
   **TTL 必须配 `TtlRunnable` 才生效**（光用 TTL 类等于普通 ThreadLocal）；
   芋道用 BeanPostProcessor + `setTaskDecorator(TtlRunnable::get)` 自动包装所有线程池（漂亮）。
5. **同线程 vs 跨线程** → 本质是 `ThreadLocal` 的数据存在 **`Thread.threadLocals`** 这个字段上，
   换线程就读不到。给出判断法："这个值在哪个线程 set 的？读的时候还在不在这个线程？"
6. **`PlatformTransactionManager`** → 接口只有 3 个方法；**`@Transactional` 背后干活的就是它**
   （TransactionInterceptor 调 getTransaction/commit/rollback），我们切面是手动做了一遍。

## 改动：按可读性重排 resolveContext 的来源查询顺序

用户质疑：「为什么先查 ToolContext 再查 Holder？按理说应该先查开销小的」。**用户的直觉是对的。**

原顺序是历史演进造成的（第一版只有 ToolContext，第二版追加 Holder 时没回头重排）。

**改动**：`ReversibleLedgerAspect.resolveContext()` 重排为 **先 Holder、后 ToolContext**。
文件行数 323 → 331（+8 全是注释）。`around()` 里第 1 步的注释同步调整。

**等价性推演**（改前 vs 改后）：

| 情况 | 改前 | 改后 | 等价 |
|---|---|---|---|
| Holder 有值 + 参数有值 | 用参数的值 | 用 Holder 的值 | ✅ 两者同源，值相同 |
| Holder 有值 + 参数无值 | 用 Holder | 用 Holder | ✅ |
| Holder 空 + 参数有值 | 用参数 | 用参数 | ✅ |
| Holder 空 + 参数无值 + 声明了 TC | 抛异常 | 抛异常 | ✅ |
| Holder 空 + 参数无值 + 未声明 | null | null | ✅ |

**关键依据**：标工具方法时桥接切面也会给 Holder 设值（其切点拦所有带 ToolContext 参数的方法），
且设的就是 ToolContext 里那份 —— 两个来源值相同，谁先谁后拿到同一结果。
