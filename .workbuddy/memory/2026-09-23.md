## 设计讨论（用户质疑）：`resolveReverseFunction` 的降级分支

用户质疑 `StrUtil.blankToDefault(reversible.reverseBeanName(), getDefaultReverseBeanName(target))`：
「bean 名存错了 —— 要存的不是注解修饰的那个类，而是注解值里的那个类和方法」。

**认定成立，且比第一轮判断更严重**：降级产生的值（= 正函数所在类的 Bean 名）会经
`.setReverseBeanName(ref.toExpression())` **持久化进 append-only 账本**，
一次「忘写 reverseBeanName」会把错误的冲账目标永久固化，回溯时账本看不出异常。

**同轮自查发现（我上一轮漏掉的硬缺陷）**：
`ReverseFunctionRef` 类 javadoc 声称「把 `@Reversible.reverseBeanName()` 的字符串值解析成可执行目标，
支持 `beanName` / `beanName#methodName` 两种写法」—— **与实现不符**。
入账侧 `resolveReverseFunction` 从不调用 `parse()`，直接 `new ReverseFunctionRef(注解值, reverseMethodName)`；
所以注解里写 `"a#b"` 会让 `validateReverseFunction` 执行 `containsBean("a#b")` → false → 抛「冲账 Bean 不存在」。
`#` 实际只是账本内部序列化格式（`toExpression()` → 撤回侧 `parse()` 往返）。该 javadoc 需修正。

**提出的两个独立缺陷**：
1. 留空即降级 = 把「未声明」伪装成「已声明」，错值落库 + 可能静默跑错 reverse()
2. 注解输入未走统一解析，`#` 写法与 javadoc 矛盾

**待用户裁决的方案**：A 保持现状 / **B 删掉降级**（`getDefaultReverseBeanName` + `getUniqueBeanName` +
`beanNameCache` 全删，`reverseBeanName` 空即抛，`resolveReverseFunction` 去掉 `target` 参数）/ C 显式开关
（`selfReverse` 或等价，与 reverseBeanName 互斥）。**代码未动，等指令。**
