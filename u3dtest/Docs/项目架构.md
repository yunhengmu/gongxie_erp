# 项目架构

本文说明本工程的目录结构、程序集划分与依赖方向，以及每一处为什么这样做。
目标是让结构对齐 Unity 主流工程做法，而不是一套自创的约定。

## 一、目录结构

```
Assets/
├── Scenes/            # 场景。由编辑器菜单生成，运行时代码不创建几何体
├── Prefabs/Devices/   # 设备即 Prefab，一台设备一个 Prefab
├── Settings/          # ScriptableObject 配置资产（DeviceFleetSettings）
├── Materials/
├── Plugins/           # 第三方托管 DLL（S7.Net、MQTTnet）
├── Scripts/
│   ├── Runtime/       # 运行时程序集，按模块分目录，每个模块一个 asmdef
│   │   ├── Core/          # 领域模型 + 契约，零依赖
│   │   │   ├── Domain/        设备状态机、状态枚举、设备接口
│   │   │   ├── Fleet/         编队读写契约（IFleetReadModel / IFleetCommands）
│   │   │   ├── Messaging/     跨模块消息结构体
│   │   │   └── Telemetry/     遥测快照 + 出口契约
│   │   ├── Devices/       # 设备接入：驱动、网关、通道、配置
│   │   │   ├── Device/        模拟设备与编队清单
│   │   │   ├── Gateway/       设备网关（按周期 Tick + 分发遥测）
│   │   │   ├── Transport/     ITransport 与各协议实现
│   │   │   ├── Telemetry/     遥测出口实现（内存 / 本地 JSON）
│   │   │   ├── Uplink/        VDA5050 上行出口（遥测 → 通道主题）
│   │   │   └── Configuration/ DeviceFleetSettings
│   │   ├── UI/            # 表现层：HUD、Presenter、DeviceView
│   │   └── App/           # 应用层 + 组合根
│   └── Editor/        # 编辑器程序集，只在 Editor 平台编译
└── Tests/
    └── EditMode/      # 每个运行时程序集对应一个测试程序集
        ├── Core/
        └── Devices/
```

要点：

- **Runtime / Editor / Tests 三分**，是 Unity 官方推荐的最小骨架。Editor 代码放在 `includePlatforms: ["Editor"]` 的程序集里，绝不会被打进 Player。
- **按模块而不是按类型分目录**。不再有全局的 `Scripts/Managers`、`Scripts/Utils`，而是每个业务模块自带全部层次。
- **测试镜像运行时结构**。`AgvDemo.Core.Tests` 只测 Core，`AgvDemo.Devices.Tests` 只测 Devices，与 asmdef 一一对应。

## 二、程序集划分与依赖方向

```
            ┌──────────────┐
            │  AgvDemo.App │  组合根，认识所有实现
            └──┬────┬───┬──┘
               │    │   │
   ┌───────────┘    │   └────────────┐
   ▼                ▼                ▼
┌─────────────┐  ┌──────────┐  ┌────────────┐
│AgvDemo.UI   │  │ Devices  │  │  (VContainer│
│             │  │          │  │   MessagePipe)│
└──────┬──────┘  └────┬─────┘  └────────────┘
       │              │
       └──────┬───────┘
              ▼
       ┌─────────────┐
       │AgvDemo.Core │  零依赖
       └─────────────┘
```

| 程序集 | 引用的程序集 | 职责 | 允许做的事 |
|---|---|---|---|
| `AgvDemo.Core` | **无**（`noEngineReferences: true`） | 领域模型、状态机、读写契约、消息结构 | 纯 C#，不引 UnityEngine，不引第三方 |
| `AgvDemo.Devices` | Core, MessagePipe | 设备驱动、通道、网关、配置、遥测出口 | 可引引擎与第三方库 |
| `AgvDemo.UI` | Core, VContainer, MessagePipe | HUD、Presenter、DeviceView | **只认 Core 的契约**，不认识设备实现 |
| `AgvDemo.App` | Core, Devices, UI, VContainer, MessagePipe | 应用服务 + 组合根 | 唯一允许 `new` 具体实现的地方 |
| `AgvDemo.Editor` | Core, Devices, App, UI | 生成场景与 Prefab 的菜单 | 仅 Editor 平台 |
| `*Tests` | 被测算程序集 + Core | EditMode 单测 | 仅 Editor 平台 |

依赖方向单向向内：`UI → Core ← Devices ← App`。没有任何环。

**为什么 Core 要零依赖**：`AgvDemo.Core` 设了 `noEngineReferences: true` 且 `references: []`，编译期就杜绝了「顺手引一个 UnityEngine」的可能。它是可以在纯 dotnet 下跑的，因此能离线单测（见下文）。这是整个结构里最值钱的一条约束。

## 三、分层职责

| 层 | 不该出现的东西 | 说明 |
|---|---|---|
| Core | 引擎类型、`Debug.Log`、第三方库 | 只放契约和纯逻辑。`DeviceStateMachine` 不依赖引擎，所以能单测 |
| Devices | UI 相关代码、场景查找 | 只做「设备 ↔ 数据」的翻译 |
| UI | `new` 设备、`GetComponentInParent` 找入口、静态单例 | 依赖由构造注入 |
| App | 业务规则 | 只做装配与转发 |

## 四、三个关键机制

### 1. 依赖注入（VContainer）

组合根只有一个：`ApplicationLifetimeScope`。它负责把配置、网关、通道、应用服务、场景组件全部登记进容器：

```csharp
builder.RegisterInstance(Settings);
builder.Register<DeviceGateway>(Lifetime.Singleton);
builder.Register<ITransport>(BuildTransport, Lifetime.Singleton);
builder.Register<DeviceFleetService>(Lifetime.Singleton);
builder.Register<IFleetReadModel>(r => r.Resolve<DeviceFleetService>(), Lifetime.Singleton);
builder.RegisterComponentInHierarchy<DeviceFleetHud>();
```

场景组件不再自己找入口，而是声明需要什么：

```csharp
[Inject]
void Construct(IFleetReadModel fleet, IFleetCommands commands) { ... }
```

**为什么**：对象图集中在一处，一眼能看出应用由什么组成；组件不再依赖场景层级（`GetComponentInParent` 一旦挪动节点就断）；单测里可以手工 `new` 出被测对象，不需要启动场景。

### 2. 消息（MessagePipe）

设备状态变化通过 `IPublisher<DeviceStateChanged>` / `ISubscriber<DeviceStateChanged>` 分发，替代原来的静态事件总线。

**为什么**：静态事件是全局可变状态，测试之间会互相污染，且无法追踪谁订阅了。MessagePipe 的订阅是可释放对象（`IDisposable`），生命周期跟着组件走：

```csharp
void Start() => _subscription = _stateSubscriber.Subscribe(OnStateChanged);
void OnDestroy() => _subscription?.Dispose();
```

### 3. 读写契约分离（CQRS 味道）

`IFleetReadModel`（读）与 `IFleetCommands`（写）都定义在 Core，`DeviceFleetService` 在 App 层同时实现两者，再由容器拆成两个接口暴露。

**为什么**：界面只能看见它能看见的。HUD 拿不到 `DeviceGateway`，也就无从写出「UI 直接改设备内部状态」这种代码。

## 五、相比改造前的改动

| 改造前 | 现在 | 原因 |
|---|---|---|
| 单一 `AgvDemo.Runtime.asmdef` 包住所有代码 | 按模块拆成 Core / Devices / UI / App | 改一处不重编全部；模块边界由编译器强制 |
| 按类型分目录（Domain / Devices / Presentation 平铺） | 按模块分目录，模块内再分职责 | 加功能是「加一个目录」而不是「在四个目录各加一个文件」 |
| 静态事件总线 | MessagePipe | 静态状态不可测、不可追踪、无法释放 |
| 服务定位器 / `GetComponentInParent` 找入口 | VContainer 构造注入 | 依赖显式化，场景层级不再是隐式契约 |
| UI 直接引用设备与传输实现 | UI 只引用 Core 契约 | 换界面不动设备，换设备不动界面 |
| 没有测试 | 每个运行时程序集配一个测试程序集 | 核心逻辑可回归 |
| `Core` 引用 MessagePipe | `Core` 零依赖 | 领域层能脱离引擎与第三方独立编译、独立测试 |

## 六、扩展点

| 想做什么 | 改哪里 |
|---|---|
| 接真实 PLC / MQTT / ABB 控制器 | 在 `Devices/Transport` 加 `ITransport` 实现，`TransportConfig.Kind` 增加分支 |
| 换遥测出口（推后端、写库） | 实现 `ITelemetrySink`，在组合根登记 |
| 改上行消息结构或主题 | `Devices/Uplink/Vda5050Uplink.cs`；协议细节见 [上行接口文档](上行接口-VDA5050.md) |
| 设备数量与摆放 | 改 `SimulatedFleet.Specs` 或直接在编辑器里摆 Prefab |
| 新增设备种类 | `DeviceKind` 加枚举 + `DeviceStateMachine.BuildCycle` 加流转序列 |
| 换界面框架（UGUI → UI Toolkit） | 只动 `UI` 程序集，Core 与 Devices 不受影响 |

## 七、怎么验证

编辑器在本机起不来（授权问题），所以验证走两条离线通道：

```bash
# 1. 全量编译（含 Editor 脚本与测试代码）
cd Tools/compile-check && dotnet build CompileCheck.csproj -v q --nologo

# 2. 跑单测
cd Tools/unit-tests && dotnet test UnitTests.csproj --nologo
```

两条都通过，说明语法、类型、API 用法、测试逻辑没问题。asmdef 边界与场景序列化字段仍需在编辑器里最终确认。

## 八、这个结构里没有的东西（有意为之）

- **没有自建的事件总线、对象池、状态机框架、DI 容器**。这些都交给成熟库（MessagePipe / VContainer），自建版本只会得到更差的边界情况处理。
- **没有 `Manager` / `Util` / `Helper` 这种兜底目录**。它们最终都会变成什么都往里塞的垃圾桶。
- **没有把 `MonoBehaviour` 当业务对象**。设备逻辑在纯 C# 的 `DeviceStateMachine` 里，`DeviceView` 只负责把状态画出来。
