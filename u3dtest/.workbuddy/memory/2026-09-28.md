### 四、重要发现：批处理编译卡死

`-batchmode -nographics -quit` 会卡在授权校验：
`Cannot save ULF license file: Access to the path 'C:\ProgramData\Tuanjie\Tuanjie_lic.ulf' is denied`，
日志停在 `Application.AssetDatabase Initial Refresh Start` 不再前进（跑 10 分钟无进展）。

### 六、一并修正的分层问题（发现了一处真实编译错误）

1. **`IWarehouseLayoutSource` 端口位置错误**：接口原在 `Warehouse.Infrastructure`，而消费它的
   `Warehouse.Application` 既 `using` 了它、asmdef 里又没有引用 Infrastructure
   → **这份代码在编辑器里编译不过**（因为批处理一直卡死，没被发现）。
   已把接口移到 `Warehouse.Application`（消费方），实现留在 Infrastructure，
   依赖方向变为 `Infrastructure → Application`，且 Application **不**引用 Infrastructure，
   由 Gameplay 组合根装配 —— 即依赖倒置。
2. **`Warehouse.Domain` 是空程序集**：把 `GridMath`、`IPathFinder`/`BfsPathFinder`（原 `IPathFinder.cs`
   改名 `PathFinding.cs`）从 Core 移入；领域事件 `AgvTaskAssigned`/`AgvArrived`/`AgvBlocked`
   从 `Core/EventBus.cs` 拆出到 `Warehouse.Domain/AgvEvents.cs`，EventBus 只留通用发布订阅。
3. 删除孤立文件 `Core/AssemblyInfo.meta`（内容含 `/n`，无对应文件）。
4. asmdef 引用精简：Domain = []（叶子），Infrastructure = [Application]，Application = [Core, Domain]。
   最终依赖图无环。

**取舍**：`Warehouse.Domain` 仍使用 `UnityEngine.Vector2Int`/`Vector3`。严格 DDD 应自定义坐标类型，
但这是 Unity 生态通行做法；真正的引擎耦合（MonoBehaviour / 场景）已全部挡在 Gameplay 之外。
如需零引擎依赖的领域层，可引入自定义 `Cell` 结构体（波及 5 个文件）。

**最终状态**：离线编译 0 错误 0 警告；场景 GUID 与脚本 meta 一致。

**新增传输实现**（`Devices/Transport/`）：
- `SiemensS7Transport` —— 批读批写（默认 200ms）+ 全部 IO 在 `Task.Run` 工作线程；大端字节手工编解码；点位表映射
- `MqttTransport` —— 逻辑标签直接作主题后缀；协议版本 V500；暴露发布/接收计数
- `AbbRwsTransport` —— **不需任何库**，RWS 就是 HTTP；轮转式请求 + `?json=1`
- `S7Address` —— 解析 `DB1.DBX4.0` / `DB1.DBW4` / `DB1.DBD4`
- `TransportConfig` + `TransportFactory` —— **可在 Inspector 切换通道**，换现场不改代码；S7 点位表按设备自动生成（每台 16 字节）

**排除的库（含原因）**：
- FluentModbus 5.3.2 —— 依赖 `System.IO.Ports`，**引擎不提供**，要补 3~4 个 DLL，收益不抵复杂度
- realvirtual.io —— 要 Unity 6 + AGV 路径仿真在付费版（540€）
- ROS-TCP-Connector —— 版本无阻（要求 2022.3.62f2，与本工程一致），但需 UPM Git URL + ROS2 环境，是**环境问题不是兼容问题**

**关键工程结论**：判断一个 NuGet 库能否在 Unity 用，只看两件事 ——
① 有没有 `netstandard2.0/2.1` 构建；② 依赖能否满足（引擎自带或自行补 DLL）。
索引用国内镜像 `nuget.azure.cn`（`api.nuget.org` 会 302 过去）。

**诚实边界**：三个通道**只做过编译验证，未接真机**。API 已对着真实 DLL 逐个核对。

### 九、目标明确：用户是 WCS 开发者，要让自己的 WCS 模块直连 Unity 虚拟设备
即**虚拟调试（virtual commissioning）**：用 Unity 虚拟设备替真机，让 WCS 调度逻辑先跑通。

**RabbitMQ 路径可行性（实测，非推测）**：

| 版本 | netstandard2.0 依赖 | 结论 |
|---|---|---|
| RabbitMQ.Client **7.2.2** | 6 个（含 `System.Threading.RateLimiting`、`Microsoft.Bcl.AsyncInterfaces` —— 引擎**没有**） | ❌ 排除 |
| RabbitMQ.Client **6.8.1** | 2 个：`System.Memory`（引擎垫片**有**）、`System.Threading.Channels`（**需自补**） | ✅ 采用 |

**关键事实**：
- `System.Threading.Channels` **不在 .NET Standard 2.1 里**（已用编译判定：不引包直接写 `Channel.CreateBounded` → CS0234）。必须随包提供。
  但它的 **netstandard2.1 构建零依赖**，所以只补 1 个 dll。
- `System.Memory` **在 Unity 垫片里**：`NetStandard/compat/2.1.0/shims/netstandard/System.Memory.dll`。
- Unity 的 netstandard2.1 编译面 = `NetStandard/ref/2.1.0/netstandard.dll` + `compat/2.1.0/shims/{netstandard,netfx}`。
- **实测**：RabbitMQ.Client 6.8.1 + System.Threading.Channels 7.0.0（ns2.1）在 netstandard2.1 下**编译 0 错误 0 警告**。

**架构**：WCS 是 RabbitMQ 生产/消费方，Unity 用一个 `RabbitMqTransport`（实现已有的 `ITransport`）
接入，**WCS 侧一行不用改**。虚拟设备消费指令、上报状态回 WCS。

**⚠️ 未做**：尚未实现 `RabbitMqTransport`，也**未与用户确认其 WCS 对设备侧的实际接口**
（RabbitMQ？TCP 私有报文？Modbus TCP？）—— 这决定一切，不能猜。
