## 一、先建立全局认知

### 1.1 全链路

```
① 用户发消息
     ↓
② buildPrompt 携带 messageId          → messageId 塞进 Spring AI 的 ToolContext
     ↓
③ 桥接切面写入 Holder                  → 从 ToolContext 取出，写进 ThreadLocal
     ↓
④ 业务方法 @Reversible                 → 切点命中，开始入账
     ↓
⑤ 入账切面写账本帧                     → 与业务方法同一事务
     ↓
   账本表 ai_reversible_ledger
     ↓ （用户点撤回）
⑥ undo 接口 → 五道闸门 → 逐帧冲账       → 每帧独立事务
     ↓
⑦ 薄壳 reverse() → 业务冲账动作         → 追加反向分录
```

### 1.2 四层职责

| 层 | 包路径 | 放什么 | 谁能改 |
|---|---|---|---|
| **契约层** | `framework/reversible/core/` | 注解、接口、上下文对象 | 框架 |
| **框架层** | `framework/reversible/core/aop/` | 两个切面 | 框架 |
| **数据层** | `dal/**/reversible/` | DO、Mapper | 框架 |
| **服务层** | `service/reversible/` | 撤回编排 | 框架 |
| **业务层** | 你自己的 `service/xxx/` | 正函数 + 冲账动作 + 薄壳 | **你** |

业务层要写的只有三样：**正函数上标 `@Reversible`**、**冲账动作方法**、**实现 `ReversibleTool` 的薄壳**。

## 四、两次改造的时间线

### 09-17：框架落地（10 个文件）

首次实现，但有个**设计缺陷**：`@Reversible` 只能标在 AI 工具方法上。

原因：messageId 靠方法参数里的 `ToolContext` 传递，而 `ToolContext` 只有工具方法才有。
切面因此**强制要求**方法签名里有 `ToolContext`，拿不到就抛 `IllegalStateException`。

### 09-18：桥接改造（+2 个文件，改 1 个）

**触发原因**（你指出的问题）：`@Reversible` 应该标在业务方法上，而不是 AI 工具对接层。

三条理由：

1. 同一业务操作有多个入口（AI 工具 / REST / 定时任务 / 其他 Service）。标在工具层会导致**入账与否取决于调用入口**
2. 可撤回的语义单元是**业务操作**，由业务方法定义，不是由 AI 工具定义
3. 冲账函数天然属于业务层（要写反向分录、需要 Mapper / 事务 / 领域规则）

**改法**：加一层上下文桥。

```
AI 工具方法（持 ToolContext）
    → ReversibleBridgeAspect 把 messageId 写进 ReversibleContextHolder
    → 同线程调用业务方法（标了 @Reversible，签名零 AI 概念）
    → ReversibleLedgerAspect 从 Holder 读上下文，写账本帧
```

`ReversibleLedgerAspect.resolveContext()` 改成**两级来源**，见 §5.3。

## 五、研究重点：五个关键机制

### 5.1 messageId 是怎么从对话传到切面的

**问题**：撤回要以"一条用户消息"为单位，所以每笔账都要挂上 `messageId`。但业务/工具方法执行时，怎么知道当前是第几条消息？

**为什么不能用 ThreadLocal 直接解决**：从 **请求线程**到 **工具执行线程**，`TenantContextHolder`（`TransmittableThreadLocal`）不会自动继承 —— 这是跨线程，ThreadLocal 会断。

**做法**：借 Spring AI 的 `ToolContext` 作为载体。

```java
// AiUtils.java:166
public static Map<String, Object> buildCommonToolContext(Long messageId, Long conversationId) {
    Map<String, Object> context = new HashMap<>();
    context.put(TOOL_CONTEXT_LOGIN_USER, SecurityFrameworkUtils.getLoginUser());
    context.put(TOOL_CONTEXT_TENANT_ID, TenantContextHolder.getTenantId());
    context.put(TOOL_CONTEXT_MESSAGE_ID, messageId);        // ← 关键
    context.put(TOOL_CONTEXT_CONVERSATION_ID, conversationId);
    return context;
}
```

`ToolContext` 是 Spring AI 帮你跨线程带过去的，你只要在切面里从方法参数读出来即可。

**注意一个 Spring AI 的硬约束**：2.0.1 的 `MethodToolCallback.java:125-132` 里，工具方法只要声明了 `ToolContext` 参数，传入的 context **不能为 null、也不能为空 map**，否则抛 `IllegalArgumentException`。所以 `buildCommonToolContext` 必须真的塞东西进去。

### 5.2 AOP 切点的三个坑

| 坑 | 现象 | 规避 |
|---|---|---|
| `@annotation` 匹配不到**接口**上的注解 | 注解标错地方，切面完全不触发，**不报错** | 必须标在实现类方法上 |
| Spring AOP 拦不到 **`private` / `protected`** 方法 | 同上，静默失效 | 必须 `public` |
| 与业务方法**自身的事务切面抢 order** | 事务边界不可预测 | 不用 `@Transactional`，改用显式 `PlatformTransactionManager` |

> 第三个坑在 5.4 展开。第一个坑有个隐蔽变体：如果 Bean 走 **JDK 动态代理**（实现了接口），实现类方法上的注解会丢失。Spring Boot 默认 `proxyTargetClass=true`（CGLIB），所以默认没事。

### 5.3 两级上下文来源怎么判定的

`ReversibleLedgerAspect.resolveContext()` 的完整分支：

```
① 方法参数里有 ToolContext 吗？
   有 → 用它（注解标在工具方法上的写法）
        messageId 为空 → 抛异常（fail-fast，静默跳过最危险）
   没有 ↓
② ReversibleContextHolder 有值吗？
   有 → 用它（注解标在业务方法上的写法）
        messageId 为空 → 抛异常（桥接异常）
   没有 ↓
③ 方法签名声明了 ToolContext 参数吗？
   声明了 → 抛异常（Spring AI 不该这样传，属异常配置）
   没声明 → 返回 null，表示「非 AI 入口调用」→ 跳过入账
```

**为什么"跳过入账"是对的**：业务方法可能被 REST 接口、定时任务调用，那些入口没有 AI 上下文。**没有 AI 上下文 = 不是 Agent 操作 = 无需账本**。这时不报错、不抛异常，业务照常执行。

**一个附带的防御**：即使误给冲账方法标了 `@Reversible`，因为撤回时 Holder 是空的（撤回是 REST 接口触发的，桥接切面拦的是带 `ToolContext` 参数的方法），切面会走"跳过入账"分支 —— **不会递归入账**。

### 5.4 事务边界怎么划的

**两处事务，语义完全不同**：

| 位置 | 方式 | 传播行为 | 为什么 |
|---|---|---|---|
| 入账（`ReversibleLedgerAspect`） | 显式 `transactionManager.getTransaction()` | `REQUIRED`（默认） | 必须与业务方法**同一事务**：业务失败则账不入 |
| 冲账（`ReversibleUndoServiceImpl`） | `TransactionTemplate` | **`REQUIRES_NEW`** | 每帧必须是**独立事务**：一帧失败不能影响已冲成功的帧 |

**入账切面为什么不用 `@Transactional` 注解**：注解的 order 默认也是 `LOWEST_PRECEDENCE`，会和业务方法自身的 `@Transactional` 抢 —— 谁在外层不确定，事务边界就不可预测。而且注解方式只能用 `RuntimeException` 包装原异常，会污染异常类型。改用显式 API 后，两个问题都没了。

**冲账服务为什么不能加 `@Transactional`**：加了就变成"整条消息一个大事务"，违背"每帧独立提交"的设计。

**业务侧要配合的一点**：冲账链路内部一律用默认 `REQUIRED`，**不要**用 `REQUIRES_NEW`。外层已经是新事务了，内部再开新事务会挂起外层，破坏"一帧 = 一个原子事务"。

### 5.5 并发怎么防的

**不靠分布式锁，靠状态 CAS**：

```java
// ReversibleLedgerMapper.casStatus
UPDATE ai_reversible_ledger SET status = ? WHERE id = ? AND status = ?
```

影响行数 = 1 才算抢到占位。多实例、多请求同时撤回同一条消息，只有一个能成功，其余跳过。

**帧状态是单向的**：

```
POSTED(0) --CAS--> REVERSING(10) --成功--> REVERSED(20)
                                  \--失败--> FAILED(30)
```

`REVERSING` 是**瞬态**占位。只有 `POSTED` 能被冲，其余都不可再冲。

**一个后果要注意**：如果冲账在 CAS 之后失败，该帧会被标 `FAILED` —— **永久不可再撤**。所以 §3.1 提到的 `validateReverseBean`（入账时校验冲账 Bean 可用）很有必要：把配置错误拦在入账那一刻，而不是撤回那一刻。
