## 一、一句话理解这套机制

用户发一条消息 → LLM 调用若干工具 → **每个"写业务"的工具调用自动落一条账本帧** → 用户点撤回 → **逐帧调用你写的冲账函数，追加反向分录** → 原记录一条不删。

```
用户消息(messageId=1001)
    ├─ 账本帧 #1  tool=wms_receive_create   voucher=RCV-20260917-001   POSTED
    ├─ 账本帧 #2  tool=wms_stock_move       voucher=MOV-20260917-007   POSTED
    └─ 账本帧 #3  tool=wms_receive_create   voucher=RCV-20260917-002   POSTED
                    ↓ 撤回 messageId=1001
    逆序冲账 #3 → #2 → #1，每帧独立事务，全部标 REVERSED
    账本帧一条不删，只追加冲账凭证号
```

**三个必须记住的边界**：

- 撤回的**最小单元是"一条用户消息"**（`ai_chat_message` 中 `type='user'` 行的 `id`），不是单个工具调用。一条消息触发 3 次工具，撤回就是 3 次一起撤。
- 撤回**不会**删除任何业务数据，也**不会**回写业务余额。它只是追加反向分录，让账本自己在业务侧被抵消。
- `@Reversible` **优先标在业务方法上**，不是 AI 工具对接层。AI 工具层只做参数翻译。理由见 Step 2。

## 二、接入路径：给一个操作加上可撤回（6 步）

以"WMS 收货单创建"为例。

```
Step 1  确认工具形态合格（能拿到 ToolContext）
Step 2  决定 @Reversible 标在业务方法还是工具方法，然后标上去
Step 3  Response 实现 VoucherAware（给出凭证号）
Step 4  写冲账函数 implements ReversibleTool
Step 5  确认不吞异常
Step 6  登记 ai_tool + 绑角色   ← 漏了这步 LLM 根本看不到工具
```

> **Step 2 是唯一需要做决策的一步**：注解标在**业务层**还是**工具层**。没有业务层的工具（直接在工具类里写 SQL）只能标工具层；有 Service 的一律标业务层。

### Step 1 — 确认工具形态合格

工具方法必须能拿到 Spring AI 的 `ToolContext`。**两种合格形态**：

```java
// 形态 A：BiFunction（推荐新手用，样板见 UserProfileQueryToolFunction）
@Component("wms_receive_create")
public class WmsReceiveCreateToolFunction
        implements BiFunction<WmsReceiveCreateToolFunction.Request,
                              ToolContext,
                              WmsReceiveCreateToolFunction.Response> {
    @Override
    public Response apply(Request request, ToolContext toolContext) { ... }
}
```

```java
// 形态 B：@Tool 注解方法（样板见 DbQueryToolFunction.java:66-91）
@Component
public class WmsReceiveToolFunction {

    @Tool(name = "wms_receive_create", description = "创建收货单")
    public Response createReceive(
            @ToolParam(description = "收货单号", required = true) String receiveNo,
            @ToolParam(description = "库位编号", required = false) @Nullable String locationCode,
            ToolContext toolContext) {          // ← 必须有这个参数，且放在最后
        ...
    }
}
```

> 形态 B 的 `ToolContext` 参数**不需要加 `@ToolParam`**（它不是 LLM 要填的参数），Spring AI 会自动注入。

❌ **不合格**：`implements Function<Request, Response>`（单参）。这类工具拿不到 `ToolContext`，也就拿不到 messageId，无法入账。

### Step 2 — 确定 `@Reversible` 标在哪一层，然后标上去

**两种位置都支持，选哪种取决于「有没有业务层」**：

| 标注位置 | 何时用 | messageId 从哪来 |
|---|---|---|
| **业务方法**（推荐） | 有 Service / 领域层，业务操作有明确的方法边界 | `ReversibleContextHolder`，由 `ReversibleBridgeAspect` 自动桥接 |
| AI 工具方法 | 没有业务层（工具里直接写 SQL / 调 HTTP），或这个操作只该由 AI 触发 | 方法参数里的 `ToolContext` |

**为什么业务方法是更好的选择**：同一个业务操作通常有多个入口 —— AI 工具、REST 接口、定时任务、别的 Service。标在工具层会导致 **"走 AI 入账、走 REST 不入账"**：入账与否取决于调用入口，而不是取决于业务操作本身。同一个"创建收货单"，凭什么 AI 调的可撤、人工调的就不可撤？

#### 写法 A：标在业务方法（推荐）

```java
// ===== 业务层：零 AI 概念，不知道 AI 的存在 =====
@Service
public class WmsReceiveService {

    @Reversible(reverseBean = "wmsReceiveReversibleAdapter")   // ★ 标这里
    public Long createReceive(WmsReceiveCreateReqDTO req) {    // ← 单个 DTO，不是多参
        // 纯业务逻辑：校验、写库、返回业务凭证号
    }
}
```

```java
// ===== 工具层：只做参数翻译，不标注解 =====
@Tool(name = "wms_receive_create", description = "创建收货单")
public Response createReceive(@ToolParam(...) String receiveNo, ToolContext toolContext) {
    Long tenantId = (Long) toolContext.getContext().get(AiUtils.TOOL_CONTEXT_TENANT_ID);
    if (tenantId == null) {
        return Response.error("无租户上下文,拒绝执行");
    }
    // 桥接由切面自动完成，这里什么都不用写
    Long id = wmsReceiveService.createReceive(receiveNo);
    return Response.ok(id, receiveNo);
}
```

**工具层不需要写任何桥接代码** —— `ReversibleBridgeAspect` 会拦截带 `ToolContext` 参数的方法，自动把 `messageId` 放进 `ReversibleContextHolder`，业务方法同线程读取。

#### 写法 B：标在工具方法

```java
// 形态 A：标在 apply 上（apply 是 @Override 的 public 方法）
@Override
@Reversible(reverseBean = "wmsReceiveReverseTool")   // ★ 标这里
public Response apply(Request request, ToolContext toolContext) { ... }

// 形态 B：标在 @Tool 方法上
@Tool(name = "wms_receive_create", description = "创建收货单")
@Reversible(reverseBean = "wmsReceiveReverseTool")   // ★ 标这里
public Response createReceive(@ToolParam(...) String receiveNo, ToolContext toolContext) { ... }
```

适合**没有业务层**的场景 —— 比如工具类里直接用 `JdbcTemplate` 写 SQL、直接调第三方 HTTP，没有一个可标的 Service 方法可标。此时只能标在这里。

#### 两种写法都必须遵守的四条位置约束

1. **必须是 `public` 方法**。Spring AOP 只能拦截 public 方法，标在 `private` / `protected` 上会**静默失效**。
   > ⚠️ 注意坑中坑：Spring AI 官方文档明确说 `@Tool` **可以**标在 private 方法上。所以如果你把 `@Tool` 和 `@Reversible` 一起标在同一个 private 方法上 —— `@Tool` 正常工作、`@Reversible` 静默失效，而且**不报错**。
2. **必须标在实现类的方法上**，不能标在接口方法上（见 FAQ Q2）。
3. 业务方法的签名里**不要收 `ToolContext`** —— 那是 AI 概念，收进业务层就白抽了。
4. **业务方法参数应收敛为单个 DTO**。这条不是风格建议，是**功能约束** —— 见下。

#### 为什么业务方法必须收单个 DTO

入账切面捕获入参快照时按**参数个数**分两种形态：

```java
// ReversibleLedgerAspect.java:112-114
String toolInput = bizArgs.length == 1
        ? JsonUtils.toJsonString(bizArgs[0])   // 单参 → 对象 JSON
        : JsonUtils.toJsonString(bizArgs);     // 多参 → 数组 JSON
```

而冲账函数取原始入参靠 `ReversibleContext.input(Class<T>)`，它是 `JsonUtils.parseObject(rawInput, type)`：

| 正函数签名 | `rawInput` 实际内容 | `input(DTO.class)` |
|---|---|---|
| `createReceive(WmsReceiveCreateReqDTO req)` | `{"receiveNo":"RCV-001",...}` | ✅ 可用 |
| `createReceive(String receiveNo, Long skuId, Integer qty)` | `["RCV-001",1001,5]` | ❌ 抛 Jackson `MismatchedInputException` |

多参场景下会**抛异常 → 冲账失败 → 账本帧标 `FAILED` → 永久不可再撤**。所以：

```java
// ✅ 正确：单个 DTO
@Reversible(reverseBean = "wmsReceiveReversibleAdapter")
public Long createReceive(WmsReceiveCreateReqDTO req) { ... }

// ❌ 错误：多参，冲账函数拿不到原始入参
@Reversible(reverseBean = "wmsReceiveReversibleAdapter")
public Long createReceive(String receiveNo, Long skuId, Integer qty) { ... }
```

> 参数收敛本身就是更好的设计（长参数列表是坏味道），所以这条约束不亏。
>
> 例外：**冲账只靠凭证号定位、确实不需要原始入参时，多参也能跑通** —— 此时 `input()` 不会被调用，自然不触发这个限制。但这属于"碰巧没事"，不建议依赖。

三种属性写法：

```java
@Reversible                                                 // 冲账函数就在本类里（reverseBean 留空）
@Reversible(reverseBean = "wmsReceiveReversibleAdapter")    // 冲账函数在别的 Bean 里
@Reversible(windowMinutes = 5)                              // 覆盖全局撤回窗口，5 分钟
```

> ⚠️ **标在业务方法上时，必须显式写 `reverseBean`。**
> 因为业务 Service 通常**不实现** `ReversibleTool`（薄壳是独立的 Adapter 类），留空会让切面按"正函数所在类"反查出业务 Service 的 Bean 名，而它并不是 `ReversibleTool`。
> 框架已在入账时加了 fail-fast 校验（`ReversibleLedgerAspect.validateReverseBean`），会直接报错拦住 —— 但这个错在写代码时就不该出现。
>
> `reverseBean` 留空**只适用于「正函数所在类自身实现了 `ReversibleTool`」**（同 Bean 模式）。
> 留空时切面按类型反查容器，**要求该类型在容器内唯一**；一个类里有多个可撤方法时必须显式写，否则它们会共用同一个 `reverse()`，你只能靠 `context.getToolName()` 在里面 switch。
>
> 标在业务方法上时，反查的是**业务类**的 Bean 名（不是工具类），写 `reverseBean` 时别搞混。

#### 标在业务方法后，非 AI 入口调用会怎样

业务方法可能被 REST 接口、定时任务、其他 Service 调用 —— 这些入口没有 AI 上下文。此时：

- 切面发现 `ReversibleContextHolder` 为空 → **跳过入账，直接执行业务**
- **不报错、不抛异常**，业务照常运行
- 只有 AI 触发的调用才会写账本帧

这是**设计如此**：没有 AI 上下文 = 不是 Agent 操作 = 无需账本。详见 FAQ Q10。

### Step 3 — Response 实现 `VoucherAware`（强烈建议）

冲账时要找到"冲哪一笔"，靠的就是凭证号。让返回值告诉框架：

```java
@Data
@AllArgsConstructor
@NoArgsConstructor
public static class Response implements VoucherAware {

    private Long receiveId;
    private String receiveNo;       // 业务凭证号

    @Override
    public String getBizVoucher() {
        return receiveNo;           // 例："RCV-20260917-001"
    }
}
```

> 不实现也能跑，但 `biz_voucher` 会是 `null`，冲账函数就只能从入参快照里自己推。**账本可审计的基础就是凭证号**，别省这一步。

### Step 4 — 写冲账函数

冲账函数是"正函数的镜像"，放在同一个类（或 `reverseBean` 指定的类）里，`implements ReversibleTool`：

```java
@Service   // 或 @Component，Bean 名要与 @Reversible.reverseBean 对上
public class WmsReceiveReverseTool implements ReversibleTool {

    @Resource
    private WmsReceiveService wmsReceiveService;

    @Override
    public String reverse(ReversibleContext context) {
        // 1. 只追加反向分录，绝不 UPDATE 原单
        WmsReverseRecordDO record = new WmsReverseRecordDO()
                .setSourceVoucher(context.getBizVoucher())      // 关联原凭证号
                .setReason(context.getReason())
                .setOperatorId(context.getOperatorId())
                .setReversedAt(context.getReversedAt());
        wmsReceiveService.appendReverseRecord(record);          // ← 追加，不是覆盖

        // 2. 返回冲账凭证号，框架会回填到账本帧的 reversed_voucher
        return record.getReverseNo();
    }
}
```

**冲账函数三条铁律**（违反了账就失真）：

| 铁律 | 说明 |
|---|---|
| 只追加，不修改 | 绝不 `UPDATE` 业务余额/原单状态。要抵消就加一笔反向分录 |
| 必须关联原凭证号 | `context.getBizVoucher()` 是定位"冲哪一笔"的唯一必需字段 |
| 不基于实时状态反推 | 不要"读当前库存再倒算"。要用 `context.getRawInput()` 里的**入参快照** |

需要原始入参时：

```java
WmsReceiveCreateReqDTO req = context.input(WmsReceiveCreateReqDTO.class);
```

`rawInput` 是 JSON 快照，**类型由你指定**——框架不猜类型，这是 JSON 存储的必然代价。

> ⚠️ **只对单参正函数有效**。多参正函数的快照是数组 JSON，这里会抛 Jackson `MismatchedInputException` —— 所以 Step 2 的约束 4 要求业务方法收单个 DTO。

### Step 5 — 确认不吞异常

```java
// ❌ 这样写，业务失败也会被当成成功入账
try {
    wmsReceiveService.create(request);
} catch (Exception e) {
    return new Response().setMessage("创建失败: " + e.getMessage());
}

// ✅ 让异常正常抛出，切面会回滚整笔事务，账不入
wmsReceiveService.create(request);
```

原因：切面判定"成功"的依据是 `proceed()` **没抛异常**。你吞掉异常返回错误字符串，正函数在切面眼里就是成功的。

### Step 6 — 登记到 `ai_tool`，并绑到角色上

**这一步最容易漏，但漏了前面全白做**：Java 侧写好工具类只是"Bean 存在"，LLM 根本看不到它。必须登记到 `ai_tool` 表，再绑给角色。

**① 登记工具**（表 `ai_tool`，或走后台「AI 大模型 → 工具管理」新增）：

```sql
INSERT INTO `ai_tool` (`name`, `description`, `status`, `creator`, `create_time`, `updater`, `update_time`, `deleted`, `tenant_id`)
VALUES ('wms_receive_create', '创建收货单', 0, '1', NOW(), '1', NOW(), b'0', 1);
```

`name` 填什么，取决于 Step 1 选哪条路：

| 形态 | `ai_tool.name` 填 | 参考现网数据 |
|---|---|---|
| 形态 A：`@Component("wms_receive_create")` | **Bean 名**：`wms_receive_create` | `user_profile_query`、`directory_list` |
| 形态 B：`@Tool(name = "wms_receive_create")` | **注解里的 name** | `ps_get_person_by_id`（Bean 名其实是 `personServiceImpl`） |

> 后台新增时会校验：`AiToolServiceImpl.validateToolNameExists()` 会调 `toolCallbackResolver.resolve(name)`，**解析不到直接报"工具名不存在"**。所以名字填错在这一步就会被拦住，不会拖到运行期。

**② 绑到角色**：后台「AI 大模型 → 角色管理」→ 编辑角色 → 勾选这个工具 → 保存。

**③ `tool_name` 记的是什么，取决于注解标在哪一层**：

| `@Reversible` 标在 | 账本帧的 `tool_name` | 与 `ai_tool.name` 的关系 |
|---|---|---|
| **业务方法** | **业务 Service 的 Bean 名**（如 `wmsReceiveService`） | ❌ 不一致，**不能直接 join** |
| 工具方法（`@Component("xxx")` 形态） | Bean 名（`xxx`） | ✅ 一致 |
| 工具方法（`@Tool(name="yyy")` 形态） | 注解名（`yyy`） | ✅ 一致 |

切面的解析规则是 `ReversibleLedgerAspect.resolveToolName()`：`@Tool(name)` 优先，否则按目标类反查 Bean 名。

> 标业务层时 `tool_name` 记业务 Bean 名，是**符合字段定义**的 —— `ReversibleLedgerDO.toolName` 的定义就是"正函数 Bean 名"。
> 它记录的是"哪段业务代码被触发"，审计上比工具名更有意义。
> 但**别指望它能和 `ai_tool` 表 join**：想知道"是哪个工具触发的"，得从 `ai_chat_message` 侧反查。

## 三、撤回接口怎么调

### 3.1 HTTP 接口

```
POST /admin-api/ai/chat/message/undo?messageId=1001&reason=用户误操作
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `messageId` | 是 | **传 user 消息或它的 assistant 回复消息都可以**，后端会自动归一化 |
| `reason` | 否 | 撤回原因，最长 200 字符（超出截断，不报错） |

响应：

```json
{ "code": 0, "data": true, "msg": "" }
```

> 这个接口**没有 `@PreAuthorize`**——因为它只允许撤回**自己**的消息（闸门 2 归属校验），权限判定就是"是不是我的"。同理，`conversationId` 不需要传，后端从消息反查。

### 3.2 前端怎么拿到 messageId

用户点的是消息气泡。气泡可能是 assistant 那条，前端**直接把该行的 `id` 传上来即可**：

```js
// 芋道 admin-ui：对话框里 assistant 消息行的 id
await request.post('/ai/chat/message/undo', null, {
  params: { messageId: row.id, reason: '撤回本次操作' }
})
```

传 assistant 的 id 时，后端会顺着 `reply_id` 找到对应的 user 消息——见 `ReversibleUndoServiceImpl.locateUserMessage()`。

### 3.3 撤回成功后会发生什么

1. 该消息下的所有账本帧被逆序冲账，状态变 `REVERSED`。
2. 该 user 消息 + 它的 assistant 回复被**逻辑删**（`deleted=1`）。
3. 下一轮对话的 Prompt 上下文里**不再包含这一问一答**（因为 `AiChatMessageMapper.selectListByConversationId` 走 MP 内置 `selectList(Wrapper)`，`@TableLogic` 自动过滤）。

> ⚠️ **前提依赖**：上面第 3 点成立的前提是那个 Mapper 方法**一直用 MP 内置的 `selectList(Wrapper)`**。如果哪天有人把它改成 `@Select` 注解或 XML 自定义 SQL，`@TableLogic` 就不会自动追加 `deleted=0`，被撤回的消息会**重新回到 Prompt 上下文里**——功能静默失效。改这个方法时要留意。

> ⚠️ **本期唯一需要产品拍板的点**：逻辑删后，**前端的消息列表也看不到这条消息了**。如果产品要的是"灰显 + 标已撤回"，需要额外加一个标记字段。目前实现是"直接消失"。

## 四、五道闸门与错误码

撤回请求进来后，会依次过 5 道闸门。**顺序固定**，前一道不过就不会走到后一道。

| # | 闸门 | 检查什么 | 不通过的错误码 |
|---|---|---|---|
| 0 | **归一化** | assistant 消息 → 顺着 `reply_id` 换成 user 消息 | `1_040_012_000` 消息不存在 |
| 2 | **归属** | `message.userId == 当前登录用户` | `1_040_012_001` 无权撤回他人的消息 |
| 3 | **闭合 + 窗口** | assistant 行的 `content` 已写入（说明这轮跑完了）且未超窗口 | `1_040_012_002` 操作进行中 / `1_040_012_003` 已超过可撤回时间 |
| 1 | **声明** | 有没有账本帧 | 无帧 = **降级为"仅清记忆"**，直接返回成功 |
| 4 | **状态** | 所有帧必须都是 `POSTED` | `1_040_012_004` 已冲账或正在冲账 |
| 5 | **因果** | 本会话没有更晚的 `POSTED` 帧 | `1_040_012_005` 存在更晚的未撤回操作 |

冲账过程中某帧失败：`1_040_012_006` 撤回遇到问题，已停止并转人工。

### 4.1 为什么闸门 1 和 2 的顺序看着奇怪

代码里是「先归属校验，再闭合/窗口校验，最后才查账本」。这是**故意的**：

- 闸门 1（有没有账本）放在时间窗口之后，是因为**没账本也要检查窗口**——纯聊天消息超时后同样不该允许撤回。
- 无账本时**不报错**，直接逻辑删两条消息并返回成功。这是最常见的正常路径：用户就是想撤回一句闲聊。

### 4.2 闸门 5（因果）到底在防什么

场景：

```
消息 A：帮我建一张收货单          → 账本帧：创建 RCV-001
消息 B：把 RCV-001 的货上架         → 账本帧：库位上架（引用了 RCV-001）
```

用户现在**只撤 A**。如果允许：RCV-001 被冲掉了，但 B 的上架记录还在引用它 —— 这就是**孤儿分录**。

所以闸门 5 的规则是"**会话内局部 LIFO**"：

```
本会话内存在 message_id 更大的 POSTED 帧  →  拒绝，提示"请先撤回更晚的消息"
```

| 允许撤 | 因为 |
|---|---|
| 撤回最后一条消息 | 不可能有更晚的帧 |
| 撤回第一条消息 A、第二条 B、逐条往回撤 | 撤到 A 时 B 已 `REVERSED`，不构成"未冲账的更晚帧" |
| 撤回中间的消息 B（A 之前已撤） | A 已 `REVERSED`，不算 |

| 不允许撤 | 因为 |
|---|---|
| 跳过 B 直接撤 A | B 的帧还是 POSTED，撤 A 会让 B 变成孤儿分录 |

> 注意范围：闸门 5 只在**同一个会话（conversation）内**判定。跨会话的因果依赖，本框架管不到。

## 五、配置项

### 5.1 全局撤回窗口

```yaml
yudao:
  ai:
    undo:
      window-minutes: 30   # 单位：分钟。默认 30（@Value 里的默认值）
```

- 窗口从**assistant 消息写入完成的时间**（`ai_chat_message.update_time`）起算。
- 单个工具可用 `@Reversible(windowMinutes = 5)` 覆盖。
- 一条消息下多个工具窗口不同时，**取最大值**作为这条消息的窗口。
- 设 `0` 表示**不限制**（窗口判定直接跳过）。

> 为什么窗口要"固化到账本帧上"（`window_minutes` 字段）？因为撤回时只查得到账本帧，**读不到注解**。@Reversible 是编译期元数据，运行期只有入账那一刻能看到。

## 六、账本表怎么看

`ai_reversible_ledger` 是 **append-only**：帧一旦写入，`conversation_id` / `message_id` / `tool_name` / `tool_input` **永不修改**，只允许 `status` 迁移和 `reversed_*` 回填。

### 6.1 状态迁移（单向）

```
POSTED(0) --CAS--> REVERSING(10) --冲账成功--> REVERSED(20)
                                  \--冲账失败--> FAILED(30)
```

只有 `POSTED` 能被冲。`REVERSING` 是个**瞬态**——它是 CAS 抢到的"占位"，用来防并发（多实例同时撤回同一条消息，只有一个能把 `POSTED` 改成 `REVERSING`）。

### 6.2 常用排查 SQL

```sql
-- 看某条消息触发的全部操作
SELECT id, tool_name, biz_voucher, status, window_minutes,
       reversed_voucher, reverse_reason, reversed_time
FROM ai_reversible_ledger
WHERE message_id = 1001
ORDER BY id DESC;

-- 找冲账失败的帧（需要转人工的）
SELECT * FROM ai_reversible_ledger WHERE status = 30;

-- 找卡在"冲账中"的帧（正常不会停留，出现即说明进程在 CAS 之后挂了）
SELECT * FROM ai_reversible_ledger WHERE status = 10;

-- 看某次撤回冲掉了哪些凭证
SELECT id, biz_voucher, reversed_voucher FROM ai_reversible_ledger
WHERE reverse_reason = '用户误操作' ORDER BY id;
```

> 所有查询都被多租户插件自动追加了 `tenant_id` 条件，手写 SQL 查库时注意别漏。

## 七、常见问题

### Q1：工具明明执行了，账本里没有帧

99% 是 `@Reversible` 的**位置错了**——见下一条。

### Q2：`@Reversible` 标在接口方法上，静默失效

```java
// ❌ 这样无效
public interface WmsTool {
    @Reversible
    Response create(Request request);
}
```

Spring AOP 的 `@annotation` 切点**匹配不到接口上的注解**，且**不会报错**。必须标在实现类的方法上。

### Q3：启动就报 `工具(xxx) 声明了 @Reversible，但方法签名中没有 ToolContext`

切面的 fail-fast。说明这个工具是单参 `Function<Request, Response>` 形态，拿不到 ToolContext。改成 `BiFunction` 或加 `ToolContext` 参数。

### Q4：报 `ToolContext 中缺少 MESSAGE_ID`

`ToolContext` 里没有 messageId。检查 `AiChatMessageServiceImpl.buildPrompt()` 是否把 `userMessage.getId()` 传进去（存量代码已改，见 §8.2）。如果你新增了别的调用 `buildPrompt` 的地方，记得同步。

### Q5：报 `类型(xxx) 对应多个 Bean，请显式指定 @Reversible.reverseBean`

容器里有多个同类型的 Bean，切面不知道用哪个。显式写 `@Reversible(reverseBean = "具体的Bean名")`。

### Q6：撤回时报"操作进行中，暂不可撤回"

判定依据是 assistant 行的 `content` 是否为空。流式场景下 assistant 行会**先插入空 content**，`doOnComplete` 时才回填。所以 LLM 还在流式输出时撤回会被拒。等它说完再撤。

### Q7：撤回后前端消息列表刷新，消息没了

这是**当前设计**（逻辑删）。若要保留可见性，需要增加标记字段并改前端渲染逻辑。见 §3.3 的提示。

### Q8：工具调用了两次，撤回后业务数据还在

检查冲账函数是不是"看起来冲了其实没冲"：
- 有没有真的追加反向分录？（只在 `log.info` 打印不算）
- 有没有把 `biz_voucher` 正确关联上？如果账本里 `biz_voucher` 是 `null`，冲账函数可能定位不到目标。

### Q9：账本是空的，但工具确实写了业务库

检查入口：只有走 `AiChatMessageServiceImpl` 的对话链路才会带 ToolContext。**MCP 通道**（module-ai 暴露工具给 Python 的 module-agent）目前**不经过账本**——一期没做，见文档 15 §11.3。

### Q10：`@Reversible` 标在业务方法上，REST 接口调它时账本没记录

这是**设计如此**，不是 bug。非 AI 入口（REST 接口、定时任务、其他 Service）调用时 `ReversibleContextHolder` 为空，切面**跳过入账**并直接执行业务。只有 AI 触发的调用才写账本帧。

四种情况对照：

| 情况 | 表现 |
|---|---|
| 业务方法被 REST / 定时任务调用 | 跳过入账 + DEBUG 日志。**正常** |
| 业务方法被 AI 调用，桥接正常 | 入账 ✅ |
| **工具方法**声明了 `ToolContext` 却取不到参数值 | 抛 `IllegalStateException`（异常配置，说明 Spring AI 没按预期注入） |
| **业务方法**的 Holder 有值但缺 messageId | 抛 `IllegalStateException`（桥接异常，检查 `buildCommonToolContext`） |

### Q11：标在业务方法上，但 AI 调用时账本始终无帧

说明 `ReversibleBridgeAspect` 的切点没匹配上。它依赖
`execution(* *(.., org.springframework.ai.chat.model.ToolContext, ..))` —— 匹配参数列表任意位置出现 `ToolContext` 的方法。

兜底方案：在工具方法里**显式桥接**，不依赖切点。

```java
@Tool(name = "wms_receive_create", ...)
public Response createReceive(String receiveNo, ToolContext toolContext) {
    ReversibleContextHolder.set(                                   // ← 手动桥接
            (Long) toolContext.getContext().get(AiUtils.TOOL_CONTEXT_MESSAGE_ID),
            (Long) toolContext.getContext().get(AiUtils.TOOL_CONTEXT_CONVERSATION_ID),
            (Long) toolContext.getContext().get(AiUtils.TOOL_CONTEXT_TENANT_ID));
    try {
        return wmsReceiveService.createReceive(receiveNo);          // 业务方法上标了 @Reversible
    } finally {
        ReversibleContextHolder.clear();                            // ← 必须清理
    }
}
```

`clear()` 放 `finally` 里是硬要求：工具可能在线程池线程（如 Netty event loop）上执行，线程会被复用，不清理会造成上下文串用。

> 注意：显式桥接和切点桥接**不冲突**（切点也设置一遍同样的值，幂等）。所以先加显式桥接排查，确认是切点问题后可以再删掉。

## 九、给"编写可撤回工具"的检查清单

写完一个可撤回工具，逐条对：

- [ ] 工具形态是 `BiFunction<Request, ToolContext, Response>` 或 `@Tool` 方法 + ToolContext 参数
- [ ] **已决定标注层次**：有业务层 → 标业务方法；无业务层 → 标 `apply()` / `@Tool` 方法
- [ ] 被标注的方法是 **`public`**
- [ ] 被标注的方法是**实现类的方法**，不是接口方法
- [ ] 业务方法签名里**没有** `ToolContext` 参数（有的话说明抽得不干净）
- [ ] 业务方法的业务参数**收敛为单个 DTO**（多参会让冲账函数取不到原始入参）
- [ ] `@Reversible` 里**显式写了 `reverseBean`** 指向冲账薄壳（标业务方法时必须写）
- [ ] 方法**没有** try-catch 吞异常
- [ ] `Response` 实现了 `VoucherAware`，返回真实业务凭证号
- [ ] 冲账函数 `implements ReversibleTool`，Bean 名与 `reverseBean` 对得上
- [ ] 冲账函数**只追加**反向分录，关联 `context.getBizVoucher()`
- [ ] 冲账函数返回冲账凭证号（会写进 `reversed_voucher`）
- [ ] **已登记 `ai_tool` 并绑到角色**，`ai_tool.name` 与工具名一致
- [ ] 手动跑一次：发起对话触发工具 → 查 `ai_reversible_ledger` 有帧且 `biz_voucher` 非空 → 调 `/undo` → 帧变 `REVERSED`、业务侧多出一条反向分录
- [ ] 再手动跑一次：**用 REST 接口直接调那个业务方法** → 账本无新增帧、业务正常执行（验证非 AI 入口不误入账）
